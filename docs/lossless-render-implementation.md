# 无损渲染优化实施与 Vulkan Compute 复核

> 阶段记录：正文中的实验范围、未提交状态和测试数字对应当时的工作节点。0.3.2 之后截至本次提交的最终功能与升级说明见 [更新日志](../CHANGELOG.md)。

日期：2026-09-22。基线 NeoForge 19fed7d / Forge 8e15c45，保持 0.3.3 版本和原 JAR 文件名。本轮本地实施，不提交或推送 GitHub。

## 最终进入生产的改动

- PredictionQuadBufferPool：共享的、渲染线程专用的备用 buffer/texture 池。仅复用 fence 已完成的资源，glClientWaitSync 超时设为 0；一次上传最多查询 8 个 fence，不等待忙碌缓冲，也不覆盖活动网格。
- 备用池上限 16 MiB / 128 项。不预分配；超过上限直接交由 GL 释放。活动复用容量与新数据差距最多 256 字节，避免缩小网格后长期保留大容量。
- 备用资源两秒后开始淘汰，每次清理最多 8 项。世界/资源重置清空备用池；地块卸载、缩小距离后的逐步退役以及空网格直接释放活动存储，不重新填入备用池。驱动内部在途资源可延迟物理释放，16 MiB 不是整个模组显存上限。
- 新数据上传成功后再退役旧数据；打包字节序、面片、材质、覆盖 mask 和 morph 固定点精度不变。补齐空网格释放、仅 morph 变化时重新上传及异常时临时内存释放。
- 现有聚合诊断增加 quadPool 的 spareBytes / entries / hits / misses / busy，没有新增逐帧日志。

源码位置：PredictionGpuTile、PredictionQuadBufferPool、PredictionRenderer。Forge 与 NeoForge 共享逻辑一致，保留各自事件 API。

## 没有启用的候选

精确面片实例化已接入完整地形 shader 进行实验：颜色/深度可以一致，但大网格 GPU 顶点成本退步，因此从生产路径撤回，仅保留 PredictionInstanceExperiment 等测试代码。生产 PredictionTerrainProgram、PredictionDrawRanges 和原绘制方式保持基线，不附加实例分支、owner 缓冲或新 shader 开销。

跨地块共享页的简化合批实验尚不能证明完整材质、独立 mask、morph 与透明排序下的综合收益；本次没有把它接入发布包，也没有用统一树模型替代详细植被。去重、缓存直达、空间索引本来已有，未重复改写。

## 有界缓冲池的实测

RTX 4070 Ti SUPER / NVIDIA 572.70。32 个缓冲，每轮每个缓冲连续上传/绘制两次，共 64 次更新；75%/100% 大小交替，12 轮预热、30 轮计时，策略轮换。最终生产池不等待在途使用，和上一轮无保护的原地覆盖不同。

| 单缓冲最大容量 | 旧方式完成中位数 | 有界 fence 池 | 减少 | 旧方式 / 池 CPU 提交 |
| --- | ---: | ---: | ---: | ---: |
| 48 KiB | 3.915 ms | 2.924 ms | 25.3% | 3.619 / 2.247 ms |
| 192 KiB | 5.227 ms | 3.990 ms | 23.7% | 4.954 / 3.222 ms |
| 768 KiB | 9.001 ms | 7.392 ms | 17.9% | 8.185 / 5.008 ms |

完成时间包含 CPU 提交、驱动和 GPU 等待，不是纯 GPU 时间或游戏每帧时间。所有有效缓冲字节和验证帧像素相同。本夹具复用容量恰好匹配，活动容量比为 1.0；这不包括备用池占用，不能解释为没有额外显存。

受益依赖网格更新和容量复用命中率。没有更新时，原实现本就跳过上传，所以不承诺静止时 FPS 提升。首次生成且没有可复用资源时仍需创建缓冲。真实游戏收益需看新诊断和帧时间。

## 为什么没有启用实例化

原先 512 单面片的简化实验可以减少 CPU 提交，但完整地形 shader 的 3–5 面片小网格 CPU/GPU 耗时基本持平。扩大到 4,096 面片和 2,496 面片的非连续范围后，重复 128 次，使用 rasterizer discard 隔离顶点/驱动成本，测出 GPU 退步。

最终 NeoForge 对照（ms，均为每组 128 次提交）：

| 路径 | 面片 / 范围 | CPU 索引 / 实例 | GPU 索引 / 实例 |
| --- | --- | ---: | ---: |
| 普通 | 4096 / 1 | 0.004 / 0.005 | 0.145 / 0.393 |
| 普通 | 2496 / 3 | 0.081 / 0.005 | 0.089 / 0.241 |
| Iris 接口 | 4096 / 1 | 0.002 / 0.003 | 0.145 / 0.393 |
| Iris 接口 | 2496 / 3 | 0.084 / 0.003 | 0.089 / 0.240 |

这是顶点阶段夹具，不包含完整片元、游戏场景或实际光影包成本。它足以否定“按提交数减少就默认启用”的决策。新实验留在测试目录，可继续研究更适合的批量方式，不能把本轮 JAR 宣传为已经完成植被实例化。

## 精度与验证范围

- pool 单元测试：忙碌 fence 不复用、最多 8 次查询、容量差限制、16 MiB/128 项上限、到期释放、异常回收。
- GPU 回读：面片和 morph 内容、仅 morph 变化、缩小存储、空网格释放。
- 正式普通/Iris shader 回归：Voxy 深度、地形/液体交接、花草/火焰贴图、LOD 接缝、洞口和高度过渡、GL 状态恢复。
- 实例实验额外做 1,556 次逐像素颜色/深度对照，包含 31 个面组选取及 morph。它的像素一致性不代表性能更好，也不是任意光影包实机兼容证明。
- 两仓库最终默认完整构建通过：NeoForge 914 项通过、35 项跳过；Forge 920 项通过，33 项跳过。可选 GPU 测试显式另跑，两个版本的缓冲池策略和实际 GPU 渲染测试均通过。日志见各仓库 build/lossless-*.log。测试环境覆盖不等于所有显卡和所有光影包实机验证。

## Vulkan Compute 与 FP64

Vulkan 的 shaderFloat64 是双精度支持开关，不是算力提升开关。若核函数已受显卡 FP64 吞吐限制，换 API 不会增加双精度单元。当前 VSS 的密度图实际运行在 CPU Java/Rust，不存在正在工作的 Vulkan 地形后端；当前 GPU 占用低不能作为 FP64 饱和证据。

批量 GPU 计算可能加速受支持的密度图，但需要图编译、精确随机和噪声语义、传输/同步以及 GPU 渲染争用控制。FP32 初筛加 FP64/CPU 回退还需保守误差界，不能仅凭一个固定阈值保证地表高度、洞穴、水面和材质分支一致。本轮没有更换数值精度或添加 Vulkan 后端。规范依据与详细分析见 vulkan-feasibility.md。
