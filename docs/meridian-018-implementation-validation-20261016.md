# Meridian 0.1.8 借鉴方案：实施、补充验证与打包

> 历史记录：保留当时的实现、输入与验证结果，不能据此判断当前版本的渲染架构、配置或兼容范围。 当前说明见 [文档目录](README.md)，相关旧报告见 [历史索引](history/README.md)。 本报告路径保留，供既有验证工具及证据清单引用。

日期：2026-10-16。对应“完成这个方案，继续验证未完成的内容”。两端已同步实现通过验证的改动，并各自构建新 JAR。没有替换游戏文件、启动／停止客户端或推送 GitHub。

本轮最明确的生产收益是：**接缝输入不变时，不再因为瓦片换版本就重建周边；水面实际排序不变时，不再让提交计划跟着失效。** 同时修正了正式网格东／南边缘被去噪修改的问题，并将构建成本统计接入现有内存预算。未把有明显性能或画质问题的实验加入默认渲染。

前序依据：[算法审查](history/performance/meridian-018-algorithm-audit-20261016.md)、[首轮离线测试](history/performance/meridian-018-algorithm-tests-20261016.md)。前序报告描述的是当时冻结的实现；本报告与本轮 `summary.json` 描述修改后的当前源码。

## 1. 已进入两端正式实现的修改

### 接缝按实际输入复用

- `PredictionLodSeams` 先比较覆盖、采样及接缝摘要的精确内容。瓦片对象或 revision 改变，但这些输入没有改变时，保留原接缝网格及边界遮罩，只重新绑定当前瓦片引用。
- `PredictionSeamMesh`／`PredictionSeamWalls` 支持精确内容比较，兼容原始和紧凑墙记录。没有只比较哈希来决定正确性。
- `PredictionRealBoundarySeams` 与原有后台 `PredictionSeamPreparation` 一起更新引用。当前瓦片、真实边界接缝和遮罩仍在同一事务中交接；旧瓦片引用不会因为复用长期留下。
- `Patch.rebind` 复用已经计算的几何范围，并保守包含新瓦片的深度边界；不再为了绑定版本重扫相同的接缝数据。
- 删除未用于有效复用判断的邻居数组缓存，以及重复遍历边段的步骤。真实输入改变时，仍走完整的局部影响范围更新。

比较发生在**替换输入的后台边界任务**中，不是每帧渲染时全场比较。本轮做的是精确内容复用，尚不是所有独立边段都有单独版本号；不能把它描述成已完成任意边段的最细粒度失效。

### 先保证源边界一致，再保留必要接缝

`PredictionMeshBuilder.stabilizeGeneratedSurface` 的循环上界由 `< gridSize - 1` 改为 `< gridSize - 2`，使裁剪后的东／南正式外圈与西／北一样保留原始高度，内部去噪规则继续生效。没有通过删掉真实／预测交接、不同 LOD 或水岸所需接缝来减少计算。

`PredictionMeshCodec.VERSION` 从 **13 更新为 14**。旧成品网格会按需重新生成，地形和植被放置采样缓存保持有效。不需要手工清空整个缓存；首次遇到旧成品时会有重建工作。

### 成本反馈接入已有预算

`PredictionMemoryBudget` 按 `TERRAIN`、`SURFACE`、`RESTORE` 记录成功／取消／失败、成功任务耗时、保留输出和待上传输出的高水位。管理器在发布成功或退出时完成统计，异常、取消、租约转移和重复关闭均有回归。

预约仍由同一个预算管理：**保留每任务 128 MiB 的底线，只允许根据实际输出高水位向上增加预约**，不会将累计分配量当作峰值而降低预约。入队前的检查使用对应任务类别，最终执行仍做预约检查。缓存恢复沿用原来的独立通路，不占用地形生成槽位。

现有诊断新增 `buildCosts={...}`，可供下一轮游戏采样区分任务类型。这里统计的是已发布输出和任务墙钟时间，**没有测得完整 Java／native 峰值工作区，也没有证明吞吐、GC 或 P99 帧时已经改善**。本轮没有再增加一层调度器，也没有修改服务器 `/vss chunky` 的策略。

### 水面只在实际顺序变化时推进提交版本

`PreparedPass.sortWater` 继续使用原距离比较器和稳定排序，在排序比较中检查上一次稳定排名是否发生严格逆序。成员或绘制范围改变仍会强制刷新；相等距离保留稳定顺序。没有额外无条件预扫描、近似排序或按显存页改变透明次序。

相机移动但实际水面顺序不变时，保留 submission revision，让完整 MDI 提交计划可以重放。排序经常变化时，仍按原顺序重新提交。

两端相对本轮冻结基线的 **10 个生产文件补丁内容一致**，平台 API 差异保留。另修正一处既有 CPU admission 测试夹具：手工设置空闲任务可用时，同时模拟前台规划已完成。原夹具在修改前生产源码上也有 3 个失败变体，已保留对照日志；没有放宽生产门控来让测试通过。

## 2. 相同输入的接缝 A/B

使用同一套 4×4 瓦片更新序列，修改前／后分别编译并在独立 JVM 中运行。每场景 24 次预热、61 次计量，过程中定期与完整重建 oracle 比较。下表为方法墙钟中位数，单位 ms；不是渲染线程整帧时间。

| 输入变化 | NeoForge 修改前 → 后 | Forge 修改前 → 后 | 周边地表重建次数中位数 |
| --- | ---: | ---: | ---: |
| 相同网格，仅版本变化 | 1.5101 → **0.0124** | 1.5198 → **0.0127** | 6 → **0** |
| 重新构造数组／网格，摘要内容相同 | 0.5150 → **0.0513** | 0.7633 → **0.0534** | 6 → **0** |
| 真实高度变化 | 0.4019 → 0.4189 | 0.4008 → 0.4333 | 6 → 6 |
| 真实覆盖变化 | 0.5678 → 0.4253 | 0.5215 → 0.5613 | 6 → 6 |

相同网格换版本时，NeoForge 累计 Java 分配从约 **681,840 B 降到 1,840 B／次**；Forge 从 733,056 B 降到 1,832 B。重新构造但内容一致时也降到相同量级。

真实高度变化中位数约增加 4%／8%，Forge 覆盖变化也约增加 8%；这些小差异包含内容检查及独立运行波动。收益集中在**消除输入没变的重复重建**，不能说所有接缝更新都加速。分配是累计对象分配，不等于峰值内存或显存。

原始数据：`results/<平台>/seam-baseline.csv`、`seam-before-after.csv`；保留中位数、P95、极值及更新数量的汇总见 `summary.json`。

## 3. 水面真实提交路径 A/B

测试串接当前 `PreparedPass`、完整 `PredictionIndirectBatch`、真实水面着色器和 MDI 重放。96 个水面绘制条目，每轮 64 帧、8 轮预热、31 轮正式计量。对照保留相同精确排序，只模拟旧的“水平移动就递增版本”行为。

| 轨迹 | NeoForge CPU µs／帧：前 → 后 | Forge CPU µs／帧：前 → 后 | 新路径重放帧数／64 |
| --- | ---: | ---: | ---: |
| 缓慢移动 | 33.963 → **25.164** | 30.595 → **25.461** | 64 |
| 步行 | 34.800 → **30.623** | 31.313 → **28.697** | 49 |
| 左右大幅跳变 | 46.403 → 46.139 | 42.802 → 42.664 | 0 |

表中已把 CSV 的 64 帧区间除以 64。节省的是每帧几微秒，属于避免重复提交准备的小优化，不应宣传为大幅涨帧。顺序变化频繁时几乎没有收益。

512 帧 CPU 对抗序列逐帧比较稳定排序的完整顺序与 revision，涵盖相等距离、反复移动、跳变。GPU 对照另外比较最终实际透明画面，并检查确实有水面像素；没有做全部游戏场景或真实光影包的连续画面对照。

## 4. 未完成候选的补充验证与取舍

### 紧凑属性编码：完成完整着色器验证，拒绝默认启用

上轮只完成编码和读取原语。本轮将候选解码器接到**当前完整地形顶点／片元着色器**，测试单独绘制、实际 indexed MDI，以及 Iris 接口的两种对应路径。使用 6 份历史森林网格，保留 morph、归属掩码、附加尾数据及原格式回退。

每平台完成 **216 对颜色和深度精确比较**：6 网格 × 4 路径 × 3 morph 值 × 3 掩码，并检测非空可见画面。41 轮计时／网格／路径，两个平台共保留 3,936 条正式数据。

RTX 4070 Ti SUPER 上，合并六网格样本的 GPU 中位数（µs）为：

| 路径 | 原格式 | 候选格式 |
| --- | ---: | ---: |
| 单独绘制 | **19.456** | 34.816 |
| MDI | **75.776** | 151.552 |
| Iris 接口单独绘制 | **17.408** | 30.720 |
| Iris 接口 MDI | **66.560** | 134.144 |

两端得到相同方向及相同量化中位数。上轮六网格源数据约省 19.78% 几何 payload，不代表全部 GPU 资源可省相同比例；加入 morph／mask 后比例也会变化。完整路径证明这版候选的解码开销抵消了存储收益，因此**生产编码和着色器保持原格式，不新增默认开关**。Iris 测试覆盖接口和深度约定，不等于跑过各种真实光影包。

### 自适应需求：完成动态原型，保留为实验

在独立测试 source set 内对现有 VSS planner 做压力原型，非近处细分阈值放宽为 2 倍；新增明确的 512 方块近处保护规则，望远镜焦点保留原细分规则。没有把原型 planner 接入正式调度。

每场景 4,800 帧控制序列，短期压力交替不会切换；持续 120 帧高压进入、600 帧恢复退出，3 周期恰好 6 次状态变化。检查负坐标、方向需求、焦点、近处探针、请求覆盖，以及恢复原目标。

保护规则开启后的目标变化及切换模拟为：

| 场景 | 原目标 → 压力目标 | 新增／移除 key | 临时驻留 key 峰值 | 降档＋恢复帧数 |
| --- | ---: | ---: | ---: | ---: |
| 普通 | 1,254 → 918 | 112／448 | 1,366 | 70 |
| 负坐标 | 1,254 → 948 | 102／408 | 1,356 | 64 |
| 望远镜 | 2,334 → 1,074 | 420／1,680 | 2,754 | 263 |
| 已有方向需求优化 | 1,329 → 1,230 | 369／468 | 1,698 | 106 |

这里按每帧交付 8 个 key 模拟，旧覆盖保留至新集合齐备，计数的是**空间 key，不是显存字节、实际上传时间或接缝耗时**。近处／焦点检查中没有新增降级。方向需求场景只减少约 7.45% 目标，却有切换和临时驻留代价；planner 本身也约需 1～3 ms 的合成规划区间。

因此本轮验证了滞回、保护和恢复规则的原型行为，**尚未证明画质取舍后的游戏净收益**，不作为无损优化默认打开。

### 其他方向

- 二值粗树冠：沿用上轮未通过轮廓／alpha 质量检查的结论，不进入默认渲染。
- 双遍光栅包围盒：本轮已经用真实森林采集网格、生产 meshlet bounds、生产 MDI 编码和当前地形着色器完成隔离回放；强遮挡时比直接绘制快，但总体仍不如当前单阶段 Hi-Z，不能替换生产路径。它没有接入完整 Minecraft renderer、Iris／Voxy 资源生命周期，也没有进入发布 JAR。
- JNI 批处理：现有最多 64 列已取得主要收益，不扩 native ABI。取消延迟尚未做专门测量。
- 植被暖缓存：已有机制不是新收益，不重复增加另一套模板缓存。

### 双遍光栅包围盒复测

两个仓库都通过同一个隔离 source set `rasterBoxes` 重跑了完整回放。输入为 6 份真实森林采集网格，使用生产 `PredictionMeshletBounds`、生产间接命令编码和当前地形顶点／片元着色器；36 个固定瓦片最终生成约 4,500 个命令槽、1,147,800 个候选四边形。测试覆盖 512×512 和 1,024×1,024 目标，以及开阔、75%／95% 遮挡、树冠、连续转向、90° 跳转、近裁剪面和覆盖变化 8 类场景。

比较的模式是：直接绘制、当前单阶段 Hi-Z、双遍 Hi-Z、双遍包围盒，以及保持原命令顺序的保序双遍包围盒。每个平台完成 **1,216 组**逐帧质量比较；每帧还检查 OpenGL 错误。两端均为构建成功、OpenGL 错误 0、深度差异 0、Alpha 差异 0。未保序的双遍包围盒在 `turning` 的 4 个检查帧共出现 18 条颜色差异，双遍 Hi-Z 同样出现 18 条；差异来自拆分绘制时共面材质的胜出顺序，没有形成孔洞或深度错误。保序双遍包围盒颜色、深度和 Alpha 均为 0 差异，但它需要再次绘制完整保序批次。

NeoForge 512×512 的 GPU 中位数如下，单位 ms；Forge 的方向相同（整批 976 个有效计量帧的总体中位数分别为 direct 0.76、Hi-Z 0.55、双遍包围盒 0.65、保序双遍包围盒 0.99）：

| 场景 | 直接 | 当前 Hi-Z | 双遍 Hi-Z | 双遍包围盒 | 保序双遍包围盒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 开阔 | 0.78 | **0.67** | 0.86 | 0.77 | 1.28 |
| 遮挡 75% | 0.76 | **0.15** | 0.31 | 0.23 | 0.27 |
| 遮挡 95% | 0.90 | **0.12** | 0.28 | 0.19 | 0.20 |
| 树冠 | 0.78 | **0.61** | 0.74 | 0.65 | 1.01 |
| 连续转向 | 0.73 | **0.43** | 0.60 | 0.49 | 0.79 |
| 90° 跳转 | 0.73 | **0.61** | 0.76 | 0.75 | 1.11 |
| 近裁剪面 | 0.73 | **0.67** | 0.82 | 0.77 | 1.30 |
| 覆盖变化 | 0.69 | **0.15** | 0.44 | 0.38 | 0.58 |

双遍包围盒只在强遮挡时相对直接绘制有稳定收益；在开阔、近裁剪面和视角跳转时没有净收益，且始终高于当前单阶段 Hi-Z。保序版本满足严格颜色一致性，但额外的第二次完整提交使它更慢。因此双遍包围盒目前只保留为离线替代方案和后续研究数据，不叠加到 `PredictionRenderer`，不改变默认剔除，也不生成或替换生产 JAR。复现入口为 `tools/prediction/raster-boxes-tests.gradle`，结果位于 `build-raster-boxes-20261016/results`。

上述检查**失败、错误、跳过全部为 0**。当前实现回归 452 项，加本轮接缝前后对照 4 次，共 456 次成功测试执行。生产源码相对各自冻结基线仅有列明的 10 文件变化；测试入口默认编译 LIVE 源码，必须显式加 `-PvssMeridianBaseline` 才使用旧实现，并禁止旧实现打发布 JAR。

主要覆盖：真实运行的 66→65 采样裁剪、四方向边缘、负坐标、同／混合 LOD、普通／水体／已捕获／体积列、覆盖撤销恢复、完整接缝 oracle、真实边界与 mask 原子交接、任务失败取消与预约释放、父层回退、GPU 归属撤销、生产批次与回退、Iris 深度约定，以及上述水面和编码实验。
