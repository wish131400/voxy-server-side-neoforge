# Voxy 上传结果回收竞态与 LOD 闪烁修复

日期：2026-10-05。适用于 NeoForge 1.21.1 和 Forge 1.20.1。

## 现场证据

`2026-10-05 15-08-35.mkv` 是 1920×1080、60 FPS、约 48.9 秒的录像。在视角相对稳定的约 16.78、18.63、20.48 秒，地形仍出现黑色或缺失的带状区域。录像帧率是录制帧率，不能当作游戏实际帧率。

对应客户端日志反复记录预测 LOD 交接异常：`IntArrayList.getInt(int)` 的接收对象 `this.wrapped` 为 null。已确认上传回调存在对象回收竞态，且旧异常恢复策略会扩大其影响；尚未在完整游戏中测量本次修改后的帧率，也不能仅凭录像把所有掉帧归到这一处。

## 上传批次的所有权

Voxy `AsyncNodeManager.tick()` 先上传节点数据，再通过缓存槽的 `VarHandle.compareAndSet` 归还 `SyncResults`。工作线程的 `getMakeResultObject()` 可以立即取回并 `reset()` 该对象，清空 `scatterWriteLocationMap`、释放或重新分配 `scatterWriteBuffer`。

旧 VSS 回调在缓存 CAS 成功后才读取这些数据。即使 mesh 完成列表已经单独取出，节点映射和原生缓冲区仍属于正在回收的批次，因此存在并发读取已重置数据的问题。

新回调在第一次缓存 CAS **之前**完成节点镜像读取和本批次 mesh 完成确认。此时 GPU 上传命令已经提交，渲染线程仍持有批次。第一缓存槽已满只影响 Voxy 归还对象的槽位，不改变 GPU 上传已经完成的事实，因此删除了第二槽的重复回调。

## 失败时的边界状态

节点镜像是增量索引，丢失任何一次上传差量后，后续批次无法自行补齐缺失信息。旧策略把运行时异常视作临时状态，继续使用不完整镜像，每次异常还会触发全局覆盖失效和边界重置。

新的失败分支只执行一次：记录完整堆栈、清空不完整节点镜像、暂停根据该镜像剔除预测地形，并在新的节点管理器或世界建立后恢复。诊断输出新增 `bridgeFailed`。重复异常不会反复清空覆盖缓存。

服务器的 section 清单描述数据范围；客户端已上传节点和当前帧深度负责确认实际交接。此次修复的是客户端上传节点索引的生命周期，而不是把服务器清单直接当作已绘制地形。

## 坐标键与 Forge 行为

修正前一轮对 `HashCommon.mix(long)` 的判断：它是完整 64 位的可逆置换，不会把不同坐标直接合并。恢复该混合，并让 section 索引的所有读写一致使用它，避免未混合的 packed X/Z 在 `ConcurrentHashMap<Long, ...>` 中因 `Long.hashCode = X xor Z` 形成大量碰撞树。

Forge 的 Xaero 本地 Voxy 数据回放、补图逻辑已从原有实现恢复。两个加载器同步共用修复，同时保留 Forge 的这些专有行为。

## 验证

新增回归直接调用生产 mixin 的上传处理函数，使用真实原生节点缓冲区，并在缓存发布后禁止读取映射。旧实现稳定复现读取过晚的问题。另覆盖第一缓存槽已占用、较新 mesh 编辑不被旧批次误确认，以及漏失差量后仅全局失效一次。

新增 section key 分布回归。完整构建还修正了测试环境的异步缓存关闭等待和 Forge 配置路径初始化。
