# Voxy Server Side Horizon

> 历史记录：保留当时的实现、输入与验证结果，不能据此判断当前版本的渲染架构、配置或兼容范围。 当前说明见 [文档目录](../../README.md)，相关旧报告见 [历史索引](../README.md)。

This mod combines server-synced LOD data with client-side seed prediction to bring distant landscapes into view sooner.
After joining a server, players no longer have to slowly explore the world by themselves before Voxy can show distant mountains, builds, terrain outlines, and large landscapes.

It is designed for Forge 1.20.1 and NeoForge 1.21.1 modpack servers, survival servers, building servers, and exploration servers.
If your server already uses Voxy, or if you want to give players a more impressive ultra-distance viewing experience, this version is made for you.

This is a community fork of Voxy Server Side for Forge / NeoForge, now extended with seed-based terrain prediction, an independent prediction LOD renderer, and local terrain caching.
It also lets the server prepare real LOD data for players, helping Voxy display ultra-long-distance terrain faster and more reliably in multiplayer servers.

VSS Horizon must be installed on both the client and the server. Voxy itself only needs to be installed on the client.

## What It Brings

### Seed-Based Predictive LOD

VSS Horizon lets your view reach terrain before the real chunks have loaded. Using the world seed and generation information shared by the server, the client builds an approximate preview of distant mountains, valleys, coastlines, and other landscapes, then renders them through its own LOD system. Detail adapts to distance and screen size: faraway terrain keeps its broad shape, while closer areas are progressively refined. Predicted terrain can be cached locally to reduce repeated work when you return to the same world. As real terrain data becomes available, it takes over the corresponding areas, including player builds and terrain edits that seed prediction cannot know about. Prediction is an approximation for supported world-generation setups; the server's real terrain remains the final reference.

Prediction is enabled by default, with a default range of 4,096 blocks. Its range and detail settings can be adjusted in the client configuration or VSS settings page. Server owners can control whether the world seed and generation information are shared for prediction.

### See LOD Terrain Faster After Joining

Server LOD sync gives players access to real terrain data from areas they have not personally explored.
The server can send existing LOD data to players, allowing faraway terrain to appear progressively from the player's position outward and replace predicted areas as it arrives.

### Better Voxy Experience for Multiplayer Servers

Voxy is great for ultra-long view distances, but on multiplayer servers, each player generating LOD locally can make the experience inconsistent.
This community version lets the server handle LOD sync: once an area has been visited or generated by one player, other players can see it faster later.

This is especially useful for large survival servers, city-building servers, and exploration servers.

### Friendlier for Public Servers

The default configuration is tuned to save bandwidth instead of using a large amount of network traffic right away.
Server owners can adjust send speed, LOD range, and generation strength based on their server conditions.

If your server has limited bandwidth, you can start with the default settings and test gradually.

### Xaero World Map Loading

After the client installs [Xaero's World Map](https://modrinth.com/mod/xaeros-world-map), VSS will write the distant columns sent by the server into the world map, so that the map coverage is no longer limited by the vanilla render distance. The bridging is done entirely on the client side, does not modify the protocol, and does not require Voxy to be installed; nearby chunks already loaded by vanilla are still drawn by Xaero itself.

This feature is enabled by default and can be controlled in VSS's Embeddium/Sodium settings page. To temporarily disable map writing, run `/vssclient xaero disable`; to re-enable it, run `/vssclient xaero enable`. Running `/vssclient xaero reload` will clear the client-side column existence records for all dimensions on the current server and automatically re-request the existing LOD cache.

The Xaero bridge requires version `1.40.0` or newer. Published interfaces and save behavior have been checked for `1.40.16`, `1.45.0`, and `1.46.0` on the corresponding platforms; other versions and modpack combinations still need verification. If the reflection interface is incompatible, the Xaero bridge will automatically disable itself without affecting the LOD functionality of VSS/Voxy.

### LOD Updates With the World

When players build houses, blow up terrain, or reshape the world far away, the server can notify clients to refresh the related LOD.
This helps prevent distant LOD from staying stuck in an outdated state.

### Not Just Terrain: Far Player Display

This feature is experimental. If it causes client crashes due to rendering errors, please disable it.
When far player sync is enabled, ultra-long view distances can show not only terrain, but also players far away.

For large building servers, event servers, and multiplayer exploration servers, this makes the world feel more alive.

### Works in Singleplayer and LAN

It is not limited to dedicated servers. Singleplayer worlds and LAN sessions can also use the same logic.

## Built-In Chunk Pre-Generation

Server owners can use `/vss chunky` to prepare an area in advance. It generates real Minecraft chunks and prepares real LOD data for Voxy, reusing valid cached columns where available. On dedicated servers and LAN worlds, the results are saved in the server's persistent LOD cache. In supported singleplayer sessions, they can be imported directly into the local Voxy instance. No separate Chunky mod is required.

The commands require administrator permission level 2. Enable VSS and chunk generation before starting; dedicated servers also require persistent LOD caching.

All coordinates and radii are measured in **blocks**. A center and radius select an inclusive **square** area, rounded outward to whole chunks. The radius can be `0` to `8192`; a rectangular selection can contain up to `4,194,304` chunk columns. The complete area must fit within the world border. Only one pre-generation task can be active per server.

| Command | What it does |
| --- | --- |
| `/vss chunky <x> <z> <radius>` | Starts a square selection around the specified center. |
| `/vss chunky start <x> <z> <radius>` | Explicit form of the same start command. |
| `/vss chunky here <radius>` | Starts a square selection around the command's execution position. |
| `/vss chunky rect <x1> <z1> <x2> <z2>` | Starts a rectangular selection between two corners, in either order. |
| `/vss chunky status` | Shows progress, ready/reused/failed counts, in-flight work, and elapsed time. |
| `/vss chunky pause` | Pauses new work; operations already in flight may still finish. |
| `/vss chunky resume` | Continues the paused task. |
| `/vss chunky cancel` | Cancels the task while keeping data already generated and saved. |
| `/vss help chunky` | Shows command help and examples. |

For example, the following command prepares a square centered on block coordinates `(0, 0)` with a radius of 512 blocks:

```text
/vss chunky 0 0 512
```

To prepare terrain around your current position, or select a rectangle:

```text
/vss chunky here 512
/vss chunky rect -256 -256 255 255
```

Tasks run in the command's execution dimension. To select another dimension, use `/execute`:

```text
/execute in minecraft:the_nether run vss chunky 0 0 128
```

Progress is reported every 60 seconds. Moving, changing dimension, or logging out does not cancel the task. Server shutdown stops the task; rerunning the same selection later can reuse valid saved LOD columns. Clients within the normal LOD sync range can receive ready data while pre-generation is still running.

Explicit pre-generation uses a speed-first path without VSS's usual generation, packing, and disk-queue throttles, so large tasks can place substantial load on the server. The `pause` and `resume` commands let administrators control when the task runs.

### Chinese Command Aliases

The Chinese root command is `/vss 预生成`. It supports `开始`, `当前位置`, `矩形`, `状态` (or `查看`), `暂停`, `继续`, and `取消`:

```text
/vss 预生成 0 0 512
/vss 预生成 开始 0 0 512
/vss 预生成 当前位置 512
/vss 预生成 矩形 -256 -256 255 255
/vss 预生成 状态
/vss 预生成 暂停
/vss 预生成 继续
/vss 预生成 取消
/vss 帮助 预生成
```

### Disk Cache Capacity

Dedicated-server pre-generation checks the configured LOD cache capacity before starting. If the selected area exceeds the estimated capacity, choose a smaller area or increase the cache limit.

Use `/vss disk_cache` to view the configured capacity, entry limit, and retention period. Use `/vss disk_cache <GiB>` to set the capacity to an integer from `1` to `64` GiB. The Chinese equivalent is `/vss 磁盘缓存 [GiB]`.

```text
/vss disk_cache
/vss disk_cache 10
/vss 磁盘缓存
/vss 磁盘缓存 10
```

The default server LOD cache capacity is 10 GiB. Saved LOD columns remain subject to the configured capacity and retention policy.

## What Server Owners Can Adjust

This version provides `/vss` commands and configuration files. Server owners can adjust settings based on their server needs:

- How much LOD data each player can receive
- How far the server syncs LOD
- Whether the server is allowed to automatically fill in missing LOD
- Whether clients receive the seed and generation information for terrain prediction
- LOD refresh speed
- Far player display
- Cache size and read speed
- Which areas to pre-generate with the built-in `/vss chunky` commands

Common command examples:

```text
/vss help
/vss stats
/vss bandwidth get
/vss bandwidth set_kbps <value>
/vss distance get
/vss distance set <chunks>
/vss generation enable
/vss generation disable
/vss chunky here 512
/vss chunky status
/vss help chunky
/vss disk_cache
/vss farplayers enable
/vss farplayers disable
```

## Differences from the Original Project

This is an unofficial community fork of Voxy Server Side.

The original project is mainly for Fabric / Paper / Purpur.
This fork provides versions for Forge 1.20.1 and NeoForge 1.21.1.

Main differences:

- Added support for Forge 1.20.1 and NeoForge 1.21.1
- Added seed-based terrain prediction with an independent LOD renderer
- Added local prediction caching and compressed CPU mesh storage
- Added built-in area pre-generation with `/vss chunky` and Chinese command aliases
- Added server-side persistent LOD cache
- Added compressed LOD data transfer
- Added optional far player display / sync
- Improved LOD cache invalidation for changed areas
- Improved request scheduling for Forge / NeoForge servers
- Optimized the default configuration for lower bandwidth and memory usage
- Added Forge / NeoForge modpack compatibility adjustments
- Added singleplayer LOD generation and sync support for Forge / NeoForge
