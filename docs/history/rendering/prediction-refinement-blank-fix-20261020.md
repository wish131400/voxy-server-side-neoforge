## 触发条件与原因

网格重建时，渲染器为旧画面保留原 GPU 对象，并给新网格分配另一个 GPU 对象。如果采样、接缝和归属都没有变化，后台会复用逻辑掩码，`maskChanges` 可以为空。旧提交代码只上传 `maskChanges`，因而新 GPU 对象没有收到已经存在于 `Result.masks()` 的完整值。

固定网格初始归属将 allowed=true 写成 255。这个值同时开启四个侧墙替换位，着色器于是误删还没有替代接缝的原侧墙。后续真正发生边界变化时才重新上传正确掩码，解释了加载期间漏面、随后又恢复的现象。稳定帧本身不保证恢复。

## 实现

1. 遍历本次 staged Draw，先更新归属纹理或细分覆盖树，再从 `Result.masks()` 上传完整掩码，完成后才发布新 Draw。
2. 对未 staged、但因邻居变化而受影响的 Draw，继续上传 `maskChanges`。已处理的 staged key 在增量循环中跳过。
3. 复用 `PredictionGpuTile.updateBoundaryCoverage` 现有的相等判断；已初始化且内容相同的资源不重复上传。上传预算继续记录实际传输字节。

这里没有将所有掩码固定为 128。地形位、独立植被位、合法侧墙替换位和覆盖树子节点索引都按完整事务结果保留。生产类的最小补丁保存为两个仓库诊断目录下的 `production-fix.patch`；反向应用这一个补丁后的 Renderer SHA256 与原审查基线完全一致。

## GPU 复现前后

测试调用生产 Scene、异步接缝事务、GPU 上传和正式着色器，并通过隐藏 OpenGL 窗口读回像素；没有启动 Minecraft 客户端。

| 原漏洞用例 | 修复前，两平台一致 | 修复后，两平台一致 |
| --- | --- | --- |
| 新 GPU 的完整掩码 | 255，错误 | 128，符合该用例归属 |
| `maskChanges` 条目 | 0 | 0 |
| 替换后侧墙像素 alpha | 0，面没有输出像素 | 255，侧墙保持可见 |
| 再准备 20 帧后的 alpha | 0 | 255 |
| 稳定 20 帧期间的 GPU 提交版本 | — | 不变，未重复上传掩码 |

128 只是该测试中“拥有地形、不替换侧墙”的正确值。新增回归同时验证其他合法位组合。

新增 `PredictionBoundaryCommitGpuTest`，每个平台 4 项：

- 相同接缝下替换新 GPU 对象，直绘与 MDI 均保留侧墙；稳定帧维持正确状态，后续真实边界变化正常提交。
- 同一瓦片由 8 格采样改为 1 格采样，延迟事务 20 次准备；旧 Draw/GPU 始终保留，提交后 4096 格掩码均正确。
- 替换带细分覆盖树的水体父瓦片，验证 92 个节点，包括 1 个仅保留植被的叶节点、84 个同时保留地形与植被的叶节点、4 个带合法侧墙替换位的叶节点；实际纹理、不透明 arena、水体 arena 的完整编码一致。
- 复用 GPU 对象重传网格后恢复完整掩码；移除邻居时，未 staged 的原瓦片仍在事务提交时更新其侧墙掩码。
