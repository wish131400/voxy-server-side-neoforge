# 通用装饰优化：独立原型与收益实测（2026-10-31）

后续三项优化已落入生产并完成双端验证，见[生产实施记录](generic-decoration-implementation-20261031.md)。本页保留前一阶段独立原型的数据。

本轮按照[通用装饰生成调研](generic-decoration-optimization-research-20261031.md)实现了隔离的实验原型，测试公共查询、批次组织、公共放置执行和按需计算。实验没有枚举更多树形，没有改变生产源码或生产原生库，也没有发布 JAR。

保持现有输出的最佳组合是“按需补齐装饰记录＋按用途复用原生 Raw 工作区＋单点入口”：五片新区域平均总耗时从约 4.97 秒降到 4.71 秒，配对耗时减少 5.15%、进程 CPU 时间减少 6.41%、生成线程 CPU 时间减少 5.10%。批量预取能减少约 12%～16% 总耗时，但部分植被输出不同，不能直接采用。

## 实验条件与正确性门槛

- Ryzen 7 7700，8 核 16 线程，Windows x86_64，Java 21.0.6，Minecraft 1.21.1 / NeoForge 21.1.234。
- 原版主世界、种子 42、现有实际生成配置快照。无额外世界生成模组，无渲染器、Voxy 绘制或 GPU 工作负载。
- 正式测试每种方案先运行两片预热区域，再运行五片新区域。每片目标为 16×16＝256 区块，显示采样间隔 4 格，包含装饰来源生成、合并和 Voxy 数据编码。装饰会查询额外一圈来源区块。
- 正式第 `r` 片区域的起点为区块 `(8192 + r*512, -8192 - r*512)`。每个方案创建自己的 Java 上下文和 Rust sampler，依次访问同样的新区域；同一方案在区域之间保留生产已有的上下文缓存。
- 所有方案，包括基线，都把外部任务打乱所用的熵固定为相同的种子、区块和间隔派生值；不消耗 Feature 自身的随机流。它用于消除对照中的无关随机差异，不是本轮生产改动。
- 每次 JVM 内先跑 `baseline`，再跑 `baseline_repeat`，最后跑 `baseline_tail`。收益以每片区域两个预热后重复基线的平均值作配对比较；第一次基线只用于建立输出参照，避免把较多 JIT 时间当成优化收益。
- 计时包含实际数据生产，排除上下文创建、输出哈希和日志写入。进程 CPU 时间包含生成、JIT、GC 和其他 JVM 线程；另记录生成线程 CPU 时间。
- 每片比较所有装饰方块的坐标与完整 BlockState、最终地形列及群系身份、排序后的装饰包围盒 SHA-256。重复基线必须可复现，不能只比较树的数量或肉眼截图。

收益计算为 `mean(1 - candidate_r / mean(repeat_r, tail_r))`。表中的毫秒是各区域算术平均，因此百分比可能与表中均值直接相除略有差别。方案按固定顺序运行，样本为一个种子的五片区域，没有多次独立 JVM 的随机交叉实验；几个百分点的差别应视为本机实验信号，而非普遍保证。

## 第一组：查询批次、原生群系和环境扫描

原始数据位于 `build/decoration-experiment-20261031-formal/`，使用原有随包 Windows DLL。重复基线平均耗时分别为 5,063.02、5,029.29 ms，二者均值为 5,046.15 ms。

| 方案 | 平均总耗时 | 配对耗时减少 | 配对进程 CPU 减少 | 五片输出与基线一致 | 判断 |
| --- | ---: | ---: | ---: | --- | --- |
| 原生群系替代 Java 群系 | 5,157.10 ms | -2.25% | -1.31% | 否，第 4 片不同 | 不采用 |
| 精确查询 2×2 页批量预取 | 4,429.91 ms | 12.23% | 13.95% | 否，第 2、4 片不同 | 不能直接采用 |
| 精确查询 4×4 页批量预取 | 4,262.07 ms | 15.51% | 15.04% | 否，第 2、4 片不同 | 不能直接采用 |
| EnvironmentScan 直接循环 | 5,022.23 ms | 0.41% | 1.61% | 是 | 总耗时收益很小 |
| 原生群系＋4×4 页＋扫描 | 4,458.68 ms | 11.62% | 13.16% | 否，第 2、4 片不同 | 不能直接采用 |
| 4×4 页＋扫描 | 4,371.46 ms | 13.39% | 11.43% | 否，第 2、4 片不同 | 不能直接采用 |

扫描原型只专门执行原版 `EnvironmentScanPlacement`，继续使用原有谓词和顺序。五片逐片耗时变化约 -1.56%～2.48%，没有显示出值得单独推广的总耗时收益。其他自定义类型继续原路径。

### 批量预取的收益真实，但语义门槛没有通过

4×4 页使 Java 精确批次请求平均从约 83,754 次降到 5,369.6 次，减少约 93.6%；实际提交计算的点从 83,754 增到 85,774.8，增加约 2.4%。它减少了逐次调用和准备开销，并非少算了同样比例的地形。

但是，第 2 片植被方块少了 202 个、装饰包围盒少了 211 个；第 4 片植被方块多了 356 个、包围盒多了 348 个。重复基线没有这些差异。因此，即使耗时减少达到 12%～16%，也不能称为无损优化。

代码中存在与这一现象相关的依赖：`backend/display.rs::display_points()` 使用 `reuse_exact=true`，后续显示点会优先读取已经存在的精确地表缓存。预取更多精确点，会改变之后显示采样可选择的结果；这些显示查询也会被树模型等装饰路径使用。该依赖说明目前“何时算”可能影响“取哪种结果”。尚未独立隔离证明所有差异都由这一处造成。

下一步应先使精确/显示查询的语义由调用方确定，缓存冷热只影响耗时，再重新测试批量预取。不能直接拿近似显示地形替代装饰要求的精确地形，也不能把本轮 15.51% 当成修正架构后必然取得的收益。

### 原生群系逐查询检查抓到实际差异

独立检查位于 `build/decoration-experiment-20261031-biome-check/`。每次原生查询同时调用 Java 参照，第一片预热即发现：

```text
noise/quart position: (28701, 16, -28673)
Rust: minecraft:dripstone_caves
Java: minecraft:meadow
```

这是原始群系噪声坐标，XZ 对应方块位置约 `(114804, -114692)`，Y 对应 64。当前结果足以拒绝无条件替代，但尚未确定差异来自气候计算、精度、搜索或边界平局选择中的哪一环，不能凭此认定具体根因。该检查写出了 `server-failure.txt`；启动器会捕获异常，Gradle 返回成功也不代表实验通过。

## 第二组：保持查询顺序的轻量路径

原始数据位于 `build/decoration-experiment-20261031-native/`。基线和候选使用同一自编译 DLL，通过实验配置开关分别启用，防止把换 DLL 本身当成收益。重复基线平均耗时为 4,913.16、4,946.45 ms，均值 4,929.81 ms。

| 方案 | 平均总耗时 | 配对耗时减少 | 配对进程 CPU 减少 | 五片输出一致 |
| --- | ---: | ---: | ---: | --- |
| 单点批次直接走现有单点入口 | 4,893.95 ms | 0.70% | 2.79% | 是 |
| 复用每次彻底清空逻辑状态的工作缓冲 | 4,951.44 ms | -0.46% | 2.16% | 是 |
| 清空缓冲复用＋单点入口 | 4,895.27 ms | 0.66% | 2.85% | 是 |
| 装饰记录按需补群系编号、颜色缓存 | 4,856.07 ms | 1.47% | 4.36% | 是 |
| 按需记录＋清空缓冲复用＋单点入口 | 4,794.13 ms | 2.70% | 5.12% | 是 |

单点入口减少单元素集合的通用分组开销。单纯保留分配、每次清空缓冲，没有取得总耗时收益。

按需记录保留原生返回的 10 个地表字段供装饰使用，等显示采样确实需要完整记录时，才补群系编号并准备颜色缓存。它使用同一个有界点缓存，没有另外建立大缓存，也没有取消需要的显示字段；原生地形查询的顺序保持不变。

组合方案五片的耗时减少分别为 2.30%、0.17%、3.76%、3.53%、3.74%，生成线程 CPU 平均约 4,765.62 ms，对应控制均值约 4,887.50 ms。进程 CPU 减少 5.12% 包含 JVM 其他线程，不能全部归为生成线程的改进。

## 第三组：按用途选择原生工作区

原始数据位于 `build/decoration-experiment-20261031-raw/`。此组继续保持查询顺序，不预取周边点，也不替换 Java 群系接口。

精确地表的外层工作缓冲只用于结果记录中的原生群系路由，真正密度搜索由已有 `Job` 的另一套工作区负责。原型沿用 `backend/tint.rs` 的做法，外层改用 `raw_scratch()`，复用带坐标键的纯计算中间结果；完整深度回退仍使用原实现。池上限为 8 个缓冲、总保留 16 MiB。

重复基线平均耗时为 4,933.49、4,997.71 ms，均值 4,965.60 ms。

| 方案 | 平均总耗时 | 配对耗时减少 | 配对进程 CPU 减少 | 五片输出一致 |
| --- | ---: | ---: | ---: | --- |
| 按用途复用 Raw 工作区 | 4,865.56 ms | 1.98% | 1.90% | 是 |
| Raw 工作区＋单点入口 | 4,803.14 ms | 3.26% | 4.59% | 是 |
| 按需记录＋Raw 工作区＋单点入口 | 4,707.51 ms | 5.15% | 6.41% | 是 |

最佳组合五片的耗时减少分别为 3.57%、4.96%、6.61%、5.15%、5.49%。生成线程 CPU 平均从控制的 4,948.44 ms 降到 4,693.75 ms，按区域配对减少 5.10%。所有预热与正式区域的输出都与基线一致，精确批次请求及提交点数仍为每片约 83,754；没有靠少算查询、少放装饰或改变查询顺序取得收益。

两组组合的收益不能相加。Raw 工作区替代了第二组“完整缓冲清空后复用”的处理方式，第三组单独证明了最终组合在这批区域中的收益。它比只保留分配更有效，但目前仍只通过本轮原版主世界样本，进入生产前还需验证其他维度、模组输入及并发任务。

结论是优先推广“调用方明确需求、共享中间计算、按用途保留工作区”的公共优化。树形模型已经复用，继续逐树种适配不是本轮最大的收益来源。更大空间仍在批次调用；应先消除采样结果对缓存预热顺序的依赖，再争取通过正确性门槛。

## 验证材料与适用范围

- 每组保存 `results.json`、`summary.json`、`experiment-environment.json`、逐片诊断、完整启动日志、原输入及输入/生产源码哈希清单。所有实验资源在各自目录，避免覆盖随包原生库。
- 三组输入、原始 Java/资源哈希一致；三组基线的七片区域（含预热）输出哈希逐片相同。结束后再次核对，生产 Java、资源及原始 Rust 源文件均与实验准备时一致。跨组核对结果保存在第三组的 `cross-series-validation.json`。
- 原生最后一组执行了 `cargo test --release --lib`：44 通过、0 失败、4 忽略。忽略项为需要外部输入的诊断或离线基准。既有单元测试默认不启用新增实验开关；候选路径的验证主要来自完整运行时逐片输出差分，不能把这些单元测试说成覆盖了所有优化分支。
- Java 候选及测试入口已在实际 NeoForge 运行时编译并执行；Python 脚本语法和 PowerShell 参数依赖经过检查。复现入口的各步骤已分步执行，整条 PowerShell 包装命令没有另外完整重跑。
- 当前测的是原版主世界单个种子，包含原有预测路径支持的装饰和结构；没有验证额外群系模组、数据包、自定义 Feature、下界、末地、Forge 或 Fabric。输出一致指与同一套现有预测基线一致，不代表与 Minecraft 完整区块生成完全相同。
- Java 分配指标只包含生成线程；采样的 `heapUsedMiB` 包含尚未回收对象，既不是常驻内存，也不包含原生 RSS。没有据此得出内存降低的结论。
- 没有运行游戏画面、帧时间对照、GPU 干扰测试，也没有测缓存读取速度。这些生成时间不能直接换算成 FPS。
- 本轮没有实现通用的有副作用 Feature 结果缓存或全世界细粒度依赖图，也没有为其虚构收益。纯谓词的依赖失效可以另做有范围的实验；不能缓存整次随机放置的“无写入”结果来替代实际执行。

## 复现入口

工具位于 `tools/performance/decoration-experiment/`。输入为之前完整运行时导出的 `build/generation-comparison-20261031/worldgen-profile.bin` 和 `structure-templates.json`；准备脚本复制生产源及资源并记录哈希，再仅在副本中应用补丁。输出目录必须尚不存在。

```powershell
# 第一组：随包 DLL；包含输出不一致的候选用于审查，不能据此发布。
& tools/performance/decoration-experiment/run.ps1 -OutputDirectory build/decoration-repro-batches -Inputs build/generation-comparison-20261031 -Python python

# 第二组：保持调用顺序的原生/Java 轻量路径。
& tools/performance/decoration-experiment/run.ps1 -OutputDirectory build/decoration-repro-native -Python python -Native -LeanMetadata -Modes 'baseline,baseline_repeat,single,scratch,scratch_single,lean,lean_scratch_single,baseline_tail'

# 第三组：按用途选择原生 Raw 工作区。
& tools/performance/decoration-experiment/run.ps1 -OutputDirectory build/decoration-repro-raw -Python python -RawWorkspace -LeanMetadata -Modes 'baseline,baseline_repeat,raw,raw_single,lean_raw_single,baseline_tail'
```

默认两轮预热、五片正式区域、16×16 区块。默认 JDK 路径为本机 `C:/Program Files/Java/jdk-21`，可通过 `-JavaHome` 指定；`-Python`、`cargo` 需指向可用运行时。原生构建使用本地已有 Cargo 依赖；实验 Gradle 也使用离线缓存。`-VerifyBiomes` 用于第一组原生群系逐查询检查，它会增加开销，不能把开启后的计时作为普通性能结果。

汇总器会拒绝未完成、重复基线不一致、原生库哈希不符或有运行时失败的实验。候选本身的输出差异保留在结果中，以便同时审查速度与正确性，不会因为更快而自动判定可发布。
