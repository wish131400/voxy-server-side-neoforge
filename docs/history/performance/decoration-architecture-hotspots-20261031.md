# 装饰主瓶颈复核与架构优先级（2026-10-31）

上一轮高度读取改动只减少约 1.7% 的完整生成耗时，不能解决主要瓶颈。本轮补充逐特性归属和隔离对照，重新确定投入方向。没有修改生产 Java/Rust 算法，没有发布新包。

后续已完成按需高度和局部提前拒绝的原型及完整对照，未发现可靠整体收益，原型未进入生产。详见[实现和收益验收](decoration-demand-evaluation-20261031.md)；下文的优先级是当时的待验证判断。

## 结论

主要问题是装饰对精确环境的需求没有随显示 LOD 缩减。4 格间隔的地形显示只请求 4,356 个网格点，装饰却额外向精确地表接口提交平均 85,916.8 个点。两者语义、范围不同，约 19.7 倍的点数比只说明工作规模，不能当成加速倍数。

`PredictionDecorationLevel.getHeight` 的未编辑列快速路径仍先调用 `nativeColumn`。缓存未命中时，后者通过 `RustTerrainSampler.exactSurfacePage` 请求完整十字段地表记录，再由 `proxyHeight` 读取高度。因此上一轮减少的是取得记录后的高度扫描，昂贵的记录生产仍在前面发生。

精确记录包括密度/含水层边界、表面规则、邻居高度、材料及颜色等工作。不能把接口耗时都算作纯噪声运算，也不能用未经证明的原始密度高度代替表面规则处理后的高度。

## 测量范围

Windows x86_64，完整 NeoForge 运行时，当前生产源码和原生库的隔离副本；沿用种子 42 的原始输入。每条路径两片预热、五片正式区域，每片 16×16 目标区块，显示间距 4；装饰含额外一圈，即 18×18 个来源区块。排除上下文建立、哈希和日志时间，未启动游戏渲染。

逐 Feature 记录总时间、精确地表调用时间/点数、Java 群系查询、实际群系源计算、journal 写入数和执行路径。特性时间包含它触发的查询，查询分项不能再与特性总时间相加。先触发共享缓存 miss 的特性承担成本，不能将某个特性的计时当成删除它后的收益。

使用 Java 请求坐标集合核对重复：五片正式区域的精确 JNI 提交点分别为 86,208、87,024、86,160、86,768、83,424，每片内部均没有重复的 Java 精确提交坐标。这不能排除原生内部重算、不同语义的地形重复计算或插值角点的重复求值，但排除了简单增加 Java 点缓存就能消除这些提交的假设。

## 两组诊断性跳过对照

先运行 baseline 并记录每个“来源区块 + 特性”的结果，随后用该结果预先知道哪些尝试没有写入。它依赖第一次完整执行，是诊断用的理想化对照，不是可上线的算法或普通缓存方案。

同坐标的前后重复基线均值为 4,734.39 ms/片。表中耗时下降先按每片配对，再取平均。

| 诊断路径 | 总时间 ms/片 | 配对耗时下降 | 精确提交点/片 | 输出检查 |
| --- | ---: | ---: | ---: | --- |
| 重复基线控制 | 4,734.39 | — | 85,916.8 | 全部一致 |
| 跳过可观测的 Java 群系完全拒绝尝试 | 4,411.63 | 6.84% | 85,916.8 | 5 片正式中 1 片不一致；预热另有 1 片 |
| 跳过全部无 journal 写入的 Feature 尝试 | 3,109.32 | 34.59% | 69,779.2 | 同样有输出差异 |

两条不一致均发生在 round=-1 和 round=4：前者比 baseline 多 2 个输出方块，后者少 1 个。差异原因尚未定位，可能涉及记录范围或执行/查询的其他可变状态；不能据此宣称已经确认某个生产缺陷，也不能为了性能忽略它。

这组数据说明：

1. 对当前能观测到的 Java 群系拒绝做更激进排除，只减少群系查询（132,486→44,279.8），精确地表需求没有减少。它不代表所有原生/模组特性群系过滤的理论上限。
2. 即使预先知道全部无写入尝试，剩余有效特性仍拉出约 7 万个精确点。无写入占 97.59% 不意味着能消除 97.59% 的耗时。
3. 无写入尝试累计 3.08 秒，实际跳过却只省约 1.63 秒：大量首次地形查询只是转由后续有效特性触发。只按热点特性名称逐个优化会误判收益。
4. 这不是“已优化 35%”的结果；它用于判断架构方向和量级，不能打包发布。

## 连续完成整区块精确页的对照

另一个隔离方案在某个 16×16 区块第一次缺精确页时，连续完成其中 16 个既有 4×4 页，再切换区块。目的在于验证工作区切换/逐出是否为主要成本。Feature 顺序、随机种子与显示语义均保留。

所有七片（含预热）输出摘要与 baseline 一致，但精确提交点平均增加到 95,846.4，增加 11.56%。总时间为 4,720.91 ms/片，对末尾重复基线的配对下降仅 1.32%。

该运行的前置重复基线出现明显波动：同坐标前后不改代码的控制时间差为 2.05%、5.64%、21.21%、40.61%、19.50%。直接取两个控制平均会得到表面上的 8.63% 改善，不能把它归因给候选方案。现有证据不支持该方案有稳定大收益，不进入生产；本轮不为追求小差异继续迭代。

## 后续架构工作的重点

### 第一优先：让查询只生产调用者需要的数据

围绕 `getHeight → nativeColumn → exactSurfacePage → surface_points → exterior_record` 拆分需求。只查高度时不应无条件物化完整地表记录；方块谓词需要材料时再补材料，发布颜色时再补相应元数据。共享可复用的密度角点、地形边界与只读结果，保持显示、精确、编辑覆盖的语义独立。

这是一项待验证的结构改动，不是已经证明的收益。原始密度高度与最终高度可能因表面规则、冰山、荒地、结构和特殊材质而不同；必须先建立可精确回答的能力判断，其他情况回到原接口。不能按“都是高度”笼统替换，也不应为每个模组硬编码树形。

验收同时观察完整生成时间、真正补算的精确点/层、材料与颜色生产次数、内存，以及输出一致性。减少 JNI 次数或令已生成记录上的读取更快，不足以作为主要收益证据。

### 第二优先：候选计划与环境需求一起准备

局部候选筛选需要覆盖特性可达范围和跨群系边界，保留全局 index、随机流、修饰器和终端的交织顺序。它应与第一优先的轻量环境一起工作，避免为了证明候选无效先把全部精确环境建出来。未知模组特性仍保留原路径。

单独重复“把 BiomeFilter 往前挪”或继续加纯谓词预检，不是本轮数据支持的重点。即使局部候选减少，也要确认后续有效特性没有把同一份昂贵工作重新触发。

### 第三优先：按可见结果分析特性需要的环境范围

审查哪些规则真的影响可发布的外壳，哪些查询只服务内部检查。依据数据依赖与几何作用域缩小工作，而不是按整个生成阶段删除地下特性、减少树量或降低距离。当前尚没有可发布实现，不能预告加速倍数。

本轮未测试 FPS/GPU，不能将生成时间下降转换成帧率提升，也未测 Forge 或整合包的同等收益。

## 工具和复现

新增工具位于 `tools/performance/decoration-hotspots/`，只操作新建的实验目录，不进入生产源码集：

- `prepare.py <新目录>`：复制当前实现、固定外部 shuffle 熵、注入逐特性探针及诊断分组。
- `prepare_chunk.py <新目录>`：在上述副本加入连续整区块方案。
- `summarize.py <目录> --mode baseline`：按单独模式汇总，避免混合候选和基线。
- `compare.py <目录>`：检查完成标记，保存前后控制、每片差异和输出失败；同时列出每个控制的结果与波动，不能只读取配对平均数。

运行既有 `tools/performance/decoration-experiment/experiment.gradle`，参数为对应的新实验目录、`rounds=5`、`warmups=2`、`side=16`。归属使用 `baseline`；跳过对照使用 `baseline,baseline_repeat,oracle_biome,oracle_no_write,baseline_tail`；连续区块使用 `baseline,baseline_repeat,fullchunk,baseline_tail`。计时期间不并发编译或测试。

原始证据目录：

- `build/decoration-hotspots-20261031/`：逐特性成本、完整输出摘要、源码及输入清单。
- `build/decoration-oracle-20261031/`：诊断跳过对照，包含失败输出检查和 `comparison-summary.json`。
- `build/decoration-chunk-20261031/`：连续区块对照，包含控制波动和额外采样数量。

三次运行均成功结束且完成标记为 success；这只证明实验流程结束，候选能否采用以逐片输出和性能结果为准。
