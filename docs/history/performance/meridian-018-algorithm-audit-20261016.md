## 1. 构建成本反馈：值得补，但应并入现有预算

Meridian `memory/AutomaticResources.java:37` 的决策输入包括可用物理内存、可用提交额度、堆余量、几何量、帧时间、待处理数、完成数和构建峰值。`client/lod/tile/LodWorkerPool.java:51` 读取 `MeridianNative.threadPeakBytes()`，用 `(previous*7+peak)/8` 平滑，供并发估算。原生峰值不等于 JVM 对象分配峰值，也不是完整进程峰值。

预算有 250 ms 的积压期更新与约 2 s 的稳定期更新；工作区未知时估计 64 MiB，估值限制在 8～512 MiB；队列数量随 worker 调整。它还观察完成吞吐，不过积压期会重置最佳吞吐记录，不能称为能保证最优线程数的搜索算法。积压分支优先于慢帧分支，也不保证跑图时总能保住帧时。

VSS 对照：

- `PredictionCpuBudget.java` 已将 Windows CPU 查询放到独立后台线程，并已有预约、最终检查和退避。
- `PredictionMemoryBudget.java:9` 目前每次构建固定预约 128 MiB，根据堆余量及活动预约限制任务；GC 前释放的缓存仍有等待回收的记账。不能用简单 `freeMemory` 替换这些约束。
- `PredictionRenderWorkBudget.java` 已有水面／植被／接缝通道压力反馈；`PredictionGpuResidency.java` 已有驻留预算。

实际缺口是不同构建类型的工作区、耗时和成品体积缺少统一反馈。可按“缓存恢复／粗地形／精细地形／植被／接缝”等已有任务类别记录：任务墙钟时间、能准确计量的 Java 与 native 工作区、输出字节、待上传字节。用保守高分位或带安全余量的估计更新现有预约，保留大任务例外与硬上界，不能仅用平均值当作内存保证。

验收看缺失覆盖交付延迟、完成吞吐、成品积压、内存及 GC、渲染 P95/P99。若只是把任务停住导致平均帧率变高，不计为同等交付能力的优化。该建议针对客户端预测调度，不改变用户要求速度优先的服务器 `/vss chunky` 行为。

## 2. 根据资源压力降低“需求”，避免回收后马上重建

`client/lod/tile/LodMemoryBudget.java:22` 在几何超过目标时放大细分阈值，低于目标的 75% 后逐步恢复，每次改变间隔约 2 s。`LodTileManager.java:114` 把地形缓冲和待上传网格字节一起计入；`LodTileSelection.java:125` 将其作用到非焦点区域的屏幕阈值。

这会请求更粗的地块，实际减少构建、上传与绘制需求。它不是单纯 LRU，也不是无损压缩。其目标几何预算部分来自可用系统内存，不能把这当作精确的 GPU 可用显存测量。

VSS 已有压力下停止可选精化、冷缓存和可回退细节回收。可研究的补充是：在持续资源压力下，让现有 planner 暂缓非焦点区域的细分需求，避免“回收细块→目标仍要求细块→立刻重建”。若放宽屏幕误差，必须作为明确的自适应画质策略；近处、望远镜、Voxy 覆盖撤销和必要接缝仍需可靠覆盖。应用在既有 planner 和预算里，不能旁路产生另一份 desired 集合。

## 3. 树木：模板复用与减少持续绘制是两种收益

`client/lod/feature/FeatureStampCache.java:23` 每树种最多准备 48 个模板，每个最多尝试 4 次，缓存几何及光照摘要。`LodFeatureMesher.java:158` 把放置后的模板方块加入共同 collector，`:189` 再整体网格化；不是每棵树在每次重建中重新完整模拟，也不是共享一个 GPU 模型后简单实例化。模板仍会复制到瓦片的放置结果并参与网格生成。

`LodMeshData.java:94` 的生成路径按 spacing 分层：

- spacing ≤ 2：树木 stamp。
- 2 < spacing ≤ 8：简化树干／树冠盒。
- ground plants 只在 spacing ≤ 4 构建。
- 更粗处不再沿此生成路径逐棵构造树；可由森林颜色或真实捕获的轮廓层表达。不能据此说所有来源的远树都消失。

`StampMesher.java:92` 的 Java 回退和 `:318` 后的面生成会去内部面并合并矩形。native 接口会接收整批块，但 native 内部的具体合并／光照算法仍未还原。

VSS `PredictionVegetationDisplayCache.java:155` 已先合并多个源块；`PredictionVegetation.java:346` 起已有邻接面与竖直段处理；`PredictionSimpleVegetation.java` 已有粗树形和森林颜色。地形显示档位的 `sharedFeatures` 是多个显示档复用同份 feature 范围，不是完整的树种 GPU 实例库，二者也不能混淆。

可借鉴的是真正重复的粗远景树型缓存、资源版本一致的光照／材质摘要，以及在画质允许时更少的树冠表示。模板缓存按种类、资源版本、相关生成配置建键，设容量与异步预热；不要照搬一次同步生成 48 个的突发开销。近处真实位置和模组特殊树继续使用可证明正确的数据。

模板缓存主要改善加载和重建。用户历史上的“树出现后站着仍持续低帧”要看 GPU 候选面、片元／材质成本、带宽及驻留；不能用模板生成提速回答持续绘制问题。此前 VSS 二值粗树冠有 GPU 收益，但孔隙／轮廓未达标，见 `vss-engine-render-tests-20261014.md` 和后续整合报告，不重新当作已通过方案。进一步代理应测多视角轮廓、叶面覆盖率和 alpha，而非只比面数。

## 4. 压缩：还有空间，但 16 B 不是完整成本

`client/lod/mesh/LodQuadWriter.java:24` 的基本记录为 16 B，用起点、边长、方向等表达规则面，另有材质流。`client/graphics/terrain/QuadEncoder.java:28` 对两个属性 word 做字典，成功时几何流为 `8 + 12*N + 8*U` 字节，N 为面数、U 为不同属性数；属性太多就回退。这个数字不包括材质、列外观、形变、单元索引、命令、对齐等。

`MaterialEncoder.java` 在最多 16 种值时使用 0／1／2／4 bit 索引；否则使用 8 bit 原值。`ColumnEncoder.java:19` 对每列 24 B 的**渲染外观／染色记录**做精确去重，索引为 1 或 2 B，并有原格式回退。它不是压缩完整世界密度或所有地形采样。

VSS `PredictionGpuEncoding.java:11` 已有 20 B 规则矩形／交叉面和复杂面回退，也已有颜色光照字典、实际节省门槛、worker 编码和不透明／水体分存。因此后续应统计实际命中的 20 B 记录、属性／owner／cell 重复率和复杂面比例，再试更窄属性索引或分流。20→16 B 只代表那部分记录的名义 20%，不能说总显存必省 20%；若需要新量化坐标精度，就不再是无损压缩。

编码 scratch 的复用可以继续检查，但应明确空闲释放与容量上限，避免每个线程长期保留历史最大缓冲。验收需同时计总驻留字节、上传字节、编码 CPU 与顶点解码 GPU 时间，保留不划算时的原格式。

## 5. GPU 遮挡：确实有不同算法，适合独立原型

`GlTerrainBatch.java:126` 复用可见成员、GPU allocation 和页批次；`:174` 只在初始化或 morph 距离改变时更新静态元数据。每瓦片分 4×4 共 16 个单元、7 个方向组，最多 112 条命令，`CellTable` 对应 113 个范围偏移及 16 组 bounds。VSS 已有稳定 scene 与静态提交，因此这部分不是新架构缺口。

`GlTerrainBatch.java:306` 的具体遮挡流程为：

1. phase 0：依当前视锥和历史 `SEEN` 状态，先画历史可见或近裁面附近的几何，写入本帧深度。
2. 禁止颜色和深度写入，光栅化各单元包围盒。片元用 `early_fragment_tests`，只有通过当前深度测试的片元才对可见位做 atomicOr。
3. phase 1：补画本帧测试可见且第一阶段尚未画过的几何，更新下一帧的历史位。
4. phase 2：利用可见位筛透明命令，维持其既有排序位置。

展开后的精确 GLSL 保存在审查目录：`evidence/meridian-terrain-batch-compute.comp`、`meridian-terrain-batch-box-vertex.vert` 和 `meridian-terrain-batch-box-fragment.frag`。命令使用 GPU 原子计数压缩和 `glMultiDrawElementsIndirectCountARB` 提交。

这条路径没有建立 Hi-Z 金字塔，也不把 GPU 可见性读回 CPU。它节省的工作和新增的包围盒顶点／片元、可见位 atomic、第二次派发及压缩成本应一起计量。开阔地或包围盒大量重叠的森林未必受益；透明、近裁面、morph 和相机跳变需要保守处理。

VSS `PredictionOcclusionCuller.java` 是当前帧保守 reversed-depth Hi-Z；`PredictionHiZBudget.java` 已限制主要提交周期内重建额度为 2，`PredictionGpuScene.java` 已有固定槽与分批更新。因此可做一个复用同份 scene／bounds 的替代 culler 原型，比较森林、山体、海面、快速转向、传送及 Iris 的完整 GPU 时间和画面。不要同时串上两套测试；此前命令压缩／层级原型无净收益的结论仍须保留，不能因 Meridian 采用就跳过验证。

## 6. 透明排序与批处理：有具体小切口，优先级较低

`client/graphics/terrain/TranslucentOrder.java` 缓存每面的中心，用可重用 long 数组存距离键；先整数排序，再对 float 距离相同的组以 double 距离精排。相机移动达到 `max(0.5, tileDistance*0.01)` 才重新请求排序，一个 mesh 同时最多一个排序任务，一个后台 sorter；渲染继续使用上一份索引，结果完成后交接。每次结果仍分配索引缓冲，并非零分配。透明瓦片排序与面内排序也不是一回事。

VSS `PredictionRenderer.java:494` 的水面排序按瓦片 X/Z 距离，在渲染线程执行；位置变化时即增加 pass revision。现有纯转向不会因这个位置条件重排，不能拿它解释所有转向掉帧。更低风险的切口是先检查当前相邻顺序，只有顺序改变才排序／增加版本；要保留所有依赖实际几何变化的失效。若仍是热点，再考虑不可变版本结果的后台排序。距离阈值和旧顺序会改变移动过程中的透明混合，要验证重叠水面、透明模型和 Iris，不能按显存页乱序。

Meridian 整块 `sampleGrid` 一次 JNI 与 VSS 最多 8×8 缺失列批处理也应客观比较。`RustTerrainSampler.java:332` 明确跳过可复用列、点缓存命中，并让 native batch 共享噪声／含水层上下文。扩大 batch 或跨任务收集可减少调用次数，却可能延长取消、无效计算和持有的中间数据。只改变批次规模的实验应保持同样的请求列与输出，记录总时间及取消延迟；不能简单恢复整块重复计算。

## 7. 不应作为新功能重复实施的项目

- 起伏／结构提前细分：Meridian `LodTileSamples.java:149` 使用高度跳变大于 `max(8, spacing)` 或结构标记；VSS `PredictionRelief.java` 与 `PredictionLodPlanner.java:275` 已有同类规则。这是启发式，不是所有复杂地形的几何误差保证。
- 矩形贪心合并：Meridian `LodGreedyMesher` 是常见的按相同属性扩宽／扩高，墙面使用连续段；VSS 已有 `VssLodGreedyMesher` 和扫描合并。没有发现可凭名称保证大幅提速的新算法。
- 中位数代表列：Java 粗采样取多个探针选代表列，主要解决稳定性／外观选择，并不天然减少计算；native 内部未证实。VSS 已有代表采样与保护，继续放宽采样精度可能把成本转移到接缝。
- 静态命令／固定槽／GPU 局部选择：VSS 已有，最近也修过冷建整场景阻塞。不能退回一次性全量建立，再以“常驻场景”名义重现一帧问题。
- 生成父层与捕获 mip 需区分：Meridian 捕获路径有逐级合并；生成父层仍可独立采样。它没有证明所有数据都具备 VSS 所需的同源父子及 Voxy 归属版本保证。

## 推荐落地顺序与保留门槛

1. **边界一致性回归 → 缩小动态接缝职责。** 验证正式外圈、邻块 halo、去噪、负坐标、不同到达顺序及不同 LOD。先证明能省掉哪部分补缝；Voxy 真实／预测交接、洞穴、水岸和结构边界保留专门处理。
2. **补到现有调度中的成本反馈。** 先记录再调预约，包含待上传成品，避免独立预算互相抢占或等待。保持第一层覆盖和缓存恢复可前进；测试内存不足和大任务，不以更长加载时间冒充改善。
3. **统计属性重复率、模板重复率和远景树冠成本。** 无损编码可先做；模板共享与代理分别计算生成、驻留及绘制收益。任何代理先过轮廓与 alpha 质量门槛。
4. **两阶段遮挡做替代原型。** 现有 Hi-Z 作为同画面基线，计算完整渲染区间；无稳定净收益则不进入生产。
5. **按热点再处理水面排序和批大小。** 不为降低局部函数次数增加异步状态、缓冲寿命与错误边界。

上述顺序是基于实现差异和历史 VSS 热点的建议，不是本轮的新性能测量。需要使用相同场景、画质、源数据与负载做 A/B，记录 CPU 准备／提交、GPU 各通道、候选面／命令、上传／驻留、构建交付延迟、GC 与 P95/P99，才能认定收益。
