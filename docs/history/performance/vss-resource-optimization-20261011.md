# VSS 五项优化的代码检查、收益实验与实施（2026-10-11）

> 历史记录：保留当时的实现、输入与验证结果，不能据此判断当前版本的渲染架构、配置或兼容范围。 当前说明见 [文档目录](../../README.md)，相关旧报告见 [历史索引](../README.md)。

按照“先测试，有明显收益才改”的要求，本轮只落地三类改动：局部绘制计划缓存、冷 GPU 网格的恢复条件、兼容反射查找缓存。整条 Iris MDI 原型在密集几何下变慢，生物群系本地缓存扩容在连续新区域收益不明显，两项均未进入生产代码。否定列缓存、日志和队列锁改造缺少足够的重放证据，暂缓。

两个版本以任务开始时的工作树为基线，保留此前的未提交改动。Forge 的直接回包处理与旧 Iris 包名兼容路径均保留。本轮不修改画质或生成距离，不安装游戏文件，不启动游戏客户端，不提交或推送 GitHub。

## 五项方向与决定

| 原方向 | 实际检查、候选和测试 | 决定 |
| --- | --- | --- |
| 1. 覆盖实际 Iris 绘制路径，减少逐瓦片提交 | 构建按页 MDI 原型，使用真实提交循环测全池/混合缓冲、轻/密集四种布局，并做 32 组像素对照；密集 GPU 区间退步 6–7% | 拒绝整条 MDI；保留 Iris 反射查找缓存 |
| 2. 让版本检查和局部更新有效 | 全局 GPU 驻留版本变化时，先核对当前可见网格的 packed 身份；视野外上传不再迫使可见范围、归属、显示层级全部重建 | 已实施，相关局部准备基准降低约 86% |
| 3. 减少必要预测任务的采样/装饰成本 | 检查本地与共享生物群系缓存，测试本地容量 2,048→8,192；真实原版 climate/biome 查询在连续新区域的昂贵加载数相同 | 拒绝扩容；没有更改地形/装饰生成算法 |
| 4. 减少显存淘汰/恢复往返 | 用原始驻留策略对照冷网格在后台连续细化的策略回放；CPU revision 更新不再单独触发 GPU 恢复 | 已实施；可见、近处、焦点、接缝及缺失粗回退仍可请求恢复 |
| 5. 减少请求、日志、反射与队列成本 | 缓存 Iris 字段/方法和 NeoForge 回包的精确签名方法；否定请求缺完整坐标重放，队列/日志未做可证实收益的候选 | 已实施反射缓存；其余延后 |

## 环境和统计口径

- 实验机器：AMD Ryzen 7 7700，16 个逻辑处理器；NVIDIA GeForce RTX 4070 Ti SUPER，OpenGL 4.6 / NVIDIA 572.70。
- 决策基准：独立 NeoForge 1.21.1 源码副本，Oracle Java 21.0.6。最终同步验证还使用 Forge 1.20.1 / Oracle Java 17.0.12。用户 Spark 会话是 Java 25.0.1，不能把本轮 JDK 21 基准等同于原会话的每帧耗时。
- CPU 准备与反射：20 轮预热、41 轮记录，每轮交替 A/B 顺序，报告中位数。生物群系：15 轮预热、41 轮记录，每个布局每轮 16,384 次查询。
- GPU 原型：轻布局 30 轮预热、41 轮记录；密集布局 8 轮预热、15 轮记录，每轮交替 A/B。`glFinish` 位于计时区间之外。计时使用 rasterizer discard，测提交与顶点区间，包含命令间可能的空闲，不包含完整游戏的像素着色和合成。
- CPU 基线来自任务开始时的原始类/方法体；没有通过强制清空缓存人为制造旧版成本。两平台为保留的优化各自保留原始对照类体；无收益的生物群系缓存实验测试已删除。
- 原始 CSV、决策用 JUnit XML及保留优化的复现步骤保存在 `tools/prediction/resource-experiments/`。平台同步后的复验数据单独保存，不覆盖初次独立实验数据。

这些结果分别属于局部耗时、合成 GPU 对照和策略回放。没有录制同存档同路线的游戏 A/B；它们不是 FPS、最低帧或玩家当前实际显存节省量。

## 1. Iris：提交数减少不保证密集场景更快

实际候选循环保持不透明顺序和水面远近排序，按连续显存页批量提交。测试还覆盖独立缓冲回退、颜色字典、边界掩码、morph 参数、正/反深度与 GL 状态恢复。

| 布局 | 记录数 / 不透明候选面 | CPU 中位 ms，原→候选 | GPU 区间中位 ms，原→候选 | 绘制提交数 |
| --- | ---: | ---: | ---: | ---: |
| 全池，轻几何 | 3,072 / 4,055,040 | 0.3295→0.0788 | 3.264512→0.916480 | 3,072→2 |
| 约 10% 独立缓冲，轻几何 | 3,072 / 4,055,040 | 0.3132→0.1883 | 2.791424→1.402880 | 3,072→328 |
| 全池，密集几何 | 3,072 / 41,619,456 | 0.3316→0.0945 | 23.942144→25.647104 | 3,072→2 |
| 约 10% 独立缓冲，密集几何 | 3,072 / 41,619,456 | 0.3531→0.2063 | 23.818240→25.264128 | 3,072→328 |

密集布局的 GPU 区间分别上升约 7.12% 和 6.07%。因此不能挑轻场景的数据，宣称整个 Iris MDI 都有效。原型已撤出生产源码；最终 `PredictionTerrainProgram` 和 `GlProgram` 与任务开始时一致，Iris 继续使用原直绘循环。此次没有迁移 Hi-Z 到 Iris，也没有添加未经验证的密度阈值或运行时自适应切换。

四个布局各做 8 组颜色和深度比较，共 32 组一致；检查了 SSBO indexed binding/range 与 indirect buffer 恢复，以及着色器占用 batch binding 时退回直绘。适配器模拟 Voxy fragment emission，未加载完整真实光影包。这说明合成测试下原型正确，不能证明在所有光影包中兼容或更快。

## 2. 局部绘制计划：跳过无关上传引发的重建

原 `PreparedPass` 将全局驻留版本作为必要的完整重建条件。大量后台上传即使不涉及当前可见记录，也会重新构造范围、检查显示层级和归属。

现在全局版本变化时先比较当前列表中的 packed 网格引用。可见列表和所有可见网格均未改变时，继续复用；可见网格替换、空网格变成有数据、归属 revision、submission epoch 或显示选择改变，仍走原重建。透明通道保留相机移动时的排序。缓存清理同时释放保存的 packed 引用。

3,072 条可见记录、仅全局驻留版本持续变化的基准，中位耗时 **0.5546→0.0759 ms，降低 86.31%**。这是这类缓存失效条件下的单次准备成本；相机移动、覆盖更新或可见成员变化时不能直接套用该数字。

新增回归验证了覆盖接管/撤销、同帧 morph 变化、空网格发布和清理引用。已有水草/显示测试验证相机距离、望远镜范围和网格替换继续改变实际提交范围。

## 3. 后台采样：不采用没有减少昂贵计算的扩容

候选只扩大每工作线程的本地生物群系查询表，保留共享表和查询语义，以真实 vanilla biome source / climate sampler 查询做对照。

| 查询模式 | 每轮查询数 | 2,048→8,192 条缓存，中位 ms | 判断 |
| --- | ---: | ---: | --- |
| 同一区域重复重叠查询 | 16,384 | 0.6790→0.6163 | 约 9.23%，属于较轻的缓存查询路径 |
| 持续进入新区域 | 16,384 | 33.2222→33.0132 | 约 0.63%，不足以认定明显收益 |

连续新区域中两边实际 noise loads 都是 230,155；较大的本地表只是改变本地/共享命中比例，没有减少这批昂贵采样。同步后的复验中连续新区域还出现了小幅退步，见复验 CSV。因此生产 `PredictionBiomeCache` 保持 2,048，8,192 版本及其专用对照类、基准测试均已删除。此项没有降低植被质量、切换后端或修改生成并发。

## 4. 冷网格：后台细化不再自动撤销淘汰

旧策略对冷记录执行 `revision != oldRevision` 就恢复上传。因此，即使细网格仍在视野外并有可绘制的粗级回退，后台细化也会撤销之前的淘汰。

新策略把内容变化与恢复需求分开：不需要恢复时只更新冷记录版本并累计 `deferredVersionUploads`；预算淘汰的记录在重新可见时恢复，归属淘汰的记录在 Voxy 覆盖撤销时恢复。渲染入口还允许缺失粗回退、近处 256 格、当前焦点和接缝所需的网格恢复。原来的淘汰宽限期、每次回收额度、粗级回退保护和正常上传预算保留。

64 轮 × 128 条视野外细化、每条假设 4 MiB 的策略回放：

| 指标 | 原策略 | 新策略 |
| --- | ---: | ---: |
| 累计恢复/上传决定 | 8,192 | 2,576 |
| 按假设大小折算的累计上传 | 32,768 MiB | 10,304 MiB |
| 回放结束时模拟驻留 | 512 MiB | 128 MiB |

上传决定减少 **68.55%**。这段测试没有调用实际 GPU 上传，模拟的 512→128 MiB 不代表当前存档实测省了 384 MiB，累计上传也不代表同时占用的显存。已验证重新可见、覆盖撤销和必要覆盖可恢复，不把一次 Hi-Z 遮挡当作淘汰理由。

## 5. 兼容反射：缓存解析结果，保持调用语义

新增 `ReflectionAccess`，以 `ClassValue` 持有按类缓存的字段与方法解析结果。私有字段沿继承链查找，Iris 方法仍按原来的名字/参数数目选择；NeoForge 回包仍按精确参数类型查找方法。缓存不保存接收对象，也不改变被调用方法的异常传播。服务端分发仍先检查物理端，避免专服加载客户端处理器。

49,152 次混合字段/方法查找和调用的基准中位数 **16.4709→0.7456 ms，降低 95.47%**。这是一整批重复兼容访问的耗时，不能当作每帧节省 15.7 ms 或 FPS 增长 95%。

应用点是两个平台的 Iris bridge，以及 NeoForge 的本地回包反射。Forge 回包本来直接调用，不添加这层封装；Forge 旧 `net.coderbot.iris` 兼容路径继续保留。测试覆盖继承私有字段、不同参数数目、精确签名重载、查找失败与原始异常原因。

否定列缓存需要维度、会话、dirty、新生成数据和过期撤销策略。新采样的移动窗口只有批首坐标，无法重放所有坐标并量化命中；日志和队列锁也缺少改造后的稳定收益证据。本轮不将这些候选写进生产代码。
