# 装饰柱区间与输出需求裁剪：完整 CPU 路径实验（2026-11-02）

前两项方案已做隔离原型并实际进入 Minecraft / NeoForge 的预测生成路径。结论是：**柱区间减少了约 31.74% 的装饰输出盒子，但没有测出稳定的完整路径提速；保守需求裁剪同样没有减掉主要环境查询。当前原型不适合以加载性能优化的名义合入生产。**

这里的输出一致，是与当前 VSS 预测结果一致；没有重新证明预测与真实世界生成逐块一致。本实验保留现有预测路径的放置、环境查询与装饰输出语义。

## 测试范围与基线

- NeoForge 1.21.1、Java 21.0.6、Ryzen 7 7700（8 核 / 16 线程），单条生成调用链。
- 原版主世界、种子 42。每片 16×16 个目标区块，实际装饰包含 18×18、即 324 个来源区块。
- 五片正式区域：起始区块 `(8192 + 512*r, -8192 - 512*r)`，`r=0..4`。两轮复测使用相同区域，不能计成十片独立地形样本。
- 每轮先完成两片独立区域预热，再测五片正式区域、四个模式。各模式使用独立且持续存活的 Rust / Java 上下文，目标来源区块均为新区域，没有磁盘装饰缓存。
- 基线为已验证的 `external/performance/20261102-height-production/full-run` 冻结快照。显式启用水平气候复用、干空气证明和含水层邻域复用，避免把已有优化的收益重复计算。
- 原生 DLL SHA-256：`d537950d551fe06002b27056cbe76273a7e496b0f5ef6db1dcd12e3bcd24975b`。
- 正式 D / E 轮同时设置 `document.vss_horizontal_climate=true`、执行 `context.bindHorizontalClimate(handle, document)`，并要求每行 `horizontalCopiedDelta` / `horizontalBatchesDelta` 均大于零。每片平均实际共享 59174 个气候中间值，确认优化路径实际进入；同时核对处理后运行资源中的 DLL 与冻结输入摘要一致。
- 计时包含：Rust 显示地形 → 实际结构 / 装饰放置及查询 → 地表提取、竹子和叶状态处理 → CPU 侧 Voxy Tile / 盒子 / 索引构建。
- 初始化、结果哈希和代表区段转换校验在计时外。不含客户端调度排队、磁盘读写、真实区块接管、Voxy 网格构建、GPU 上传与渲染。因此这些结果不能作为完整游戏加载时间或帧数收益。

正式计时期间已与发布负责人协调，停止其他对话的 Gradle / Cargo 构建和性能测试。

## 两项原型具体做了什么

### 1. 柱区间覆盖层与直接区间输出

`ColumnBlocks` 用 X/Z 列及纵向同状态区间保存可变装饰结果，保持精确的 `Map<BlockPos, BlockState>` 查询、覆盖、删除和冻结快照行为。提取和显示合并保留区间表达，`SpanTile` 直接将区间交给 Voxy 盒子构建，减少逐格输出盒子。

仍然保留有序放置的读取语义、事务撤销、结构保护和 JNI 待上传修改。树模型仍须执行逐格合法性预检；后续装饰和树装饰器仍可读取前面的写入。本轮没有把这些行为简化成只生成外观，也没有绕过 JNI 修改同步。当前 `putRun` 内部仍逐格处理覆盖，列/span 表达并不意味着已经消除了所有逐格工作。

这验证了“压缩覆盖层、减少 Map 往返和后续拆包整理”的原型；**尚未实现任意树模板通过一次区间操作完成全部预检、事务和后续依赖处理**。不能将这次结果推广为所有直接模板合成方案的收益上限。

### 2. 输出区域与依赖边界裁剪

将目标区域 / spacing 传入 `tileForRendering`，在所有有序 placement 完成后，仅提取输出区域所需内容。保留一格发布边界和六格叶距离传播范围，裁掉外侧地表提取、状态整理和结果复制。

这是需求贯穿方案的**保守子集**：spacing 已进入需求对象，但没有用它跳过粗 LOD 下的主 placement 候选、环境模拟或来源区块。装饰仍按生产入口的 spacing 1 保留完整占用，再由 Voxy 做粗体素覆盖；没有通过放大装饰 spacing 漏掉细树干。

实验为防止已裁剪来源数据在新需求中被误用，独立需求开始时清空装饰来源缓存。正式测量均为不重叠的新区域，因此没有借此伪造缓存命中。此策略不适合直接用于生产移动和邻接 tile 复用：正式实现仍需完整来源保存，或将需求范围 / 覆盖能力加入缓存身份。本轮没有完成这部分生产缓存设计。

## 正式性能结果

以下为两轮五片区域的平均值，地形步长 4、装饰 spacing 1；单位为每片目标区域的完整 CPU 路径耗时。

| 模式 | 完整耗时 ms | 相对基线 | 装饰及整理 ms | 当前线程 Java 分配 MiB | 装饰输出盒子 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前基线 | 3093.664 | — | 2839.209 | 530.544 | 123899.4 |
| 柱区间与区间输出 | 3115.769 | 慢 0.71% | 2863.565 | 534.833 | 84576.0 |
| 保守需求裁剪 | 3090.515 | 快 0.10% | 2838.058 | 525.014 | 123899.4 |
| 两项组合 | 3110.404 | 慢 0.54% | 2858.293 | 530.021 | 84576.0 |

上表相对值使用平均完整耗时之比。局部收益没有形成稳定总收益，执行顺序复测足以使符号翻转：

| 模式 | D 轮配对平均耗时减少 | E 轮反序配对平均耗时减少 |
| --- | ---: | ---: |
| 柱区间 | +1.13% | -2.71% |
| 需求裁剪 | +2.36% | -2.23% |
| 组合 | +1.28% | -2.44% |

D 轮配置顺序为 `baseline,span,demand,span_demand`，E 轮为 `span_demand,demand,span,baseline`；奇数区域另反转后三个模式。完整执行顺序与原始行数据已保留。由于样本量有限、模式顺序和运行状态仍有影响，这不是对小于 1% 差异的精确统计判定；足以说明不能承诺本原型有稳定的明显提速。

较早 A 轮发现旧 `FeatureHotspotProbe` 仅为 baseline 额外收集无写入候选，后续统一以 `measure` 初始化探针。最终入口审查又发现 B / C 虽设置水平缓存开关，却漏掉 Java / Rust 气候共享绑定；修正后重新完成 D / E 和第二次步长矩阵。A / B / C 以及全部 smoke 时间均不计入正式收益；预备证据目录的 `STATUS.txt` 标注了撤回原因。无预热的步长矩阵只用于正确性，不能引用其首次执行时间当收益。

## 为什么盒子少了，整体仍然没快

| 基线阶段 | 平均 ms | 完整路径占比 |
| --- | ---: | ---: |
| 显示地形 | 249.465 | 8.06% |
| 装饰、结构与整理 | 2839.209 | 91.78% |
| CPU 侧 Voxy Tile / 盒子 / 索引构建 | 4.990 | 0.16% |

装饰内部可归属的平均时间包括：Feature 执行 2580.463 ms、结构 156.626 ms、地表提取 24.586 ms、叶状态整理 24.811 ms。其余为未被这些顶层作用域单独覆盖的准备、收集和合并等工作。

精确地表查询 1449.517 ms、群系查询 188.765 ms 是上述作用域里的**嵌套时间**，不能与 Feature / 装饰时间再次相加。

关键工作量在四模式中完全相同：

| 每片平均计数 | 四模式共同值 |
| --- | ---: |
| 装饰来源区块 | 324 |
| Java 发起的精确地表点 | 85916.8 |
| 群系查询 | 132486 |
| 树模型 replay 入口 | 930.2 |
| replay 入口模型长度之和 | 99149.6 |

模型入口数和模型长度包含之后被预检拒绝的尝试，不代表全部单元都成功写入。每模式在五片正式区域共进入 4651 次模型 replay，证明测量实际进入了待优化的树模型路径。

柱区间使输出盒子减少 31.74%，但总 Java 分配增加约 0.81%。提取从 24.586 ms 降至 20.673 ms，叶状态处理从 24.811 ms 升至 27.199 ms；CPU 输出阶段从 4.990 ms 升至 7.398 ms。当前列对象、数组、兼容 Map 遍历、排序和后处理消耗了大部分局部节省。

需求裁剪省去外侧提取与复制，使 Java 分配减少约 1.04%，但未减少主要精确环境调用。组合提取时间降至 18.718 ms，也只是每片省约 6 ms，难以改变约 3.09 秒的完整路径。

`plantBytes` 是两种实现各自的缓存大小估算，不是实测保留堆：基线约 3.23 MB，列方案约 5.07 MB。不能用它声称精确的内存变化比例；它至少说明当前逐柱对象实现没有表现出应有的紧凑性，不能因为区间数减少就宣布内存优化成功。

## 正确性与真实入口检查

- `ColumnBlocks` 与 HashMap 做 16000 次随机写入 / 覆盖 / 删除对照，检查分裂、归并和不可变快照。
- 使用实际 `PredictionDecorationLevel` 检查写后读、失败撤销、结构保护、覆盖后撤销；检查负坐标边界、已捕获方块剔除、`cells` 兼容与叶状态传播边界。
- 两轮各 28 行含预热记录，共 56 行，均比较完整装饰位置 / BlockState、展开后的装饰占用和地形柱 runs；同一输入在四模式及两轮间哈希一致。
- 额外在地形步长 `1,2,4,8,16`、8×8 目标区块上做四模式矩阵，共 20 行，全部通过。各步长使用独立坐标；装饰仍是生产语义的 spacing 1。
- 每行再反射调用实际 `PredictionVoxySource.buildSection`，在 0–4 级比较代表区段的完整 32768 项映射数组；通过稳定的 BlockState / biome 映射器保留天空光和流体路径。选点由完整展开占用生成，避免合并盒子改变选点。
- 初版虽通过单位方块对照，却在真实粗 LOD 映射中失败：跨列处理顺序会影响粗体素材质，液体纵向合并会改变 cap 标记。最终原型按生产的 z、x、Y 顺序输出，液体保留逐格盒子后才通过全部正式检查。

映射检查是**代表区段**对照，没有穷举所有区域区段，也未使用客户端 GPU。测试环境仅为本机 NeoForge 原版主世界，尚未验证 Forge / Fabric、下界 / 末地和各种地形群系模组。

基线和候选诊断同样保留了七片含预热区域累计 3 次越界装饰回退、11 次结构 `getLevel` 不支持的跳过。它们没有因原型增加；本实验比较的是当前实现能生成的内容，没有把这些原有未完成分支描述为已成功生成全部真实结构。

## 采用判断与证据

第一项适合作为后续紧凑数组区间格式的研究基础；当前逐柱对象 / Map 兼容原型没有足够的速度或分配优势。第二项证明了保留输出语义的末端裁剪可行，但未实现主生成链按 LOD 减少工作量，不能称为已经完成 SeedGen 式需求生成。

后续若以明显提升加载速度为目标，验收重点应是**候选执行次数、需要的来源区块和精确环境查询是否真实减少**。仅减少输出盒子、重复证明模板已缓存或继续压缩占比不足 1% 的 CPU 输出阶段，当前测量不支持把它们作为主要突破口。是否能安全减少上游工作，需要针对依赖、随机消耗与未知 Feature 回退单独验证。

本轮没有修改生产 `src`、Rust、native 或 `lib`，未打包发布，已将结论同步给实施负责人。
