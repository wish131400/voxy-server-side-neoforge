## 统计口径和验证

按 Spark 官方 `spark_sampler.proto`、`spark.proto` 字段解码。两棵调用树均验证了有效子引用、唯一父节点、非负 self，以及线程总权重 = 根节点权重之和 = exclusive self 权重之和。服务端有 5,096 个节点，渲染线程有 8,916 个节点。

“毫秒权重”来自定时抽样，包含 native 调用、线程等待或驱动等待，不是精确每次调用耗时，更不是 GPU 计时。VSS 栈占比按 exclusive self 样本逐个检查完整调用栈去重，识别 `dev.xantha.vss.*` 与 `$vss$` Mixin 入口。

单个方法的 inclusive 权重也按栈出现去重，避免递归相加。例如渲染采样中 `PredictionSpatialIndex.intersectFrustum` 的各递归节点 inclusive 简单相加为 12,728 ms，但去重后的实际栈出现权重只有 652 ms（0.54%）。本报告不把 12,728 ms 作为该方法耗时。

VSS 后台构建的 `visibleCpuMs`、`backgroundCpuMs` 使用 `ThreadMXBean.getCurrentThreadCpuTime()`，可以估算已完成任务的真实线程 CPU 时间；阶段 `sample/surface/mesh/pack` 则使用 `System.nanoTime()`，是跨工作线程累加的经过时间，两者口径不同。任务 CPU 计数在结束时发布，窗口边缘仍有归账误差。

GPU 日志中的均值和 n 是计时器累计值。新增样本均值按 `(末均值 × 末 n − 初均值 × 初 n) / (末 n − 初 n)` 还原，并保留均值只有三位小数造成的误差边界。n 未增长的阶段不作为本窗口 GPU 数据。

## 首要问题：Iris 路径绕过普通路径的批处理与预测 Hi-Z

采样调用栈进入 `PredictionIrisBridge → PredictionRenderer.drawIris`。当前实现遍历每个 `PreparedDraw`，分别绑定 terrain/yield 缓冲、设置瓦片坐标、材质表偏移、morph 和边界参数，最后调用 `glDrawElements` 或 `glMultiDrawElements`。`drawNormalPass` 中的 MDI 重放和 Hi-Z 批次机制未用于这段 `drawIris`。

源码定位：`src/main/java/dev/xantha/vss/client/prediction/PredictionRenderer.java:1606` 为 Iris 直接提交，`:1432` 为普通 MDI/Hi-Z 提交；后台 CPU 计数来源位于 `PredictionTileManager.java:480`。

后段 24 个诊断快照：

- 当前通道提交次数中位数 **2,912.5**，范围 60–3,360；大部分地形画面达到约 2,000–3,300 次。是通道快照统计，不是逐帧平均。
- 当前通道几何范围计数中位数 **2,194.8 万四边形**，最大 **2,856.2 万**。该计数不能替代最终像素工作量。
- `indirect.planHits/planMisses/wholePlanHits/planContentChecks` 全部增量为 **0**。
- `HZB_REDUCE`、`GPU_FILTER`、`INDIRECT_SUBMIT` 的 GPU n 全部增量为 **0**。
- `opaquePageGroups=206` 等普通批次快照在整个窗口不变，同样是旧状态。不能把它当成当前 Iris 批次数。

这证明本窗口没有运行 VSS 预测的那条 MDI/Hi-Z 提交链。Voxy 自身以及其他渲染系统的剔除仍是独立问题，不能说整套游戏都没有遮挡剔除。

后段 `preparedPlans` 增 3,414、`reusedPlans` 也增 3,414。这与源码中 Iris 不透明通道组装、透明通道复用同帧计划一致；50% 的表面复用率不代表不透明场景已经获得跨帧缓存。前段普通路径为重建 4,757 / 复用 282，但两段画面和光影状态不同，不能把整个性能差异归因于单一改动。

优先优化应覆盖实际使用的 Iris 路径：静态提交计划、按页合批和批量瓦片参数，随后接入适合 Iris 深度和着色器布局的候选选择。必须保留透明排序、边界掩码、接缝/morph 与 Iris 目标缓冲的约束。继续只优化普通路径的 MDI，对本次最重的绘制支路帮助有限。

## GPU：不透明预测通道成本明显

后段计时器累计均值约 14.96–14.99 ms，但按新增样本还原，本窗口不透明通道为 **13.260 ± 0.061 ms，114 个新样本**。这是 GPU timestamp 区间，可能包含区间内提交形成的空闲，不能与其子阶段或 CPU 权重直接相加。

水面为约 0.085 ± 0.061 ms / 114 个新样本；由于累计均值舍入的误差相对很大，只能确认远小于不透明通道，不能宣称精确到 0.001 ms。深度复制约 0.098 ± 0.034 ms / 228 个新样本。抗锯齿、预测 Hi-Z、GPU 过滤、间接提交本窗口没有新计时样本。

前段普通路径的不透明新增计时为 **8.037 ± 0.035 ms / 168 个样本**，只作为早些时候的补充。两个位置、朝向、驻留量与光影路径不同，这不是同场景开关光影的严格 A/B。

## 显存与上传：不透明几何是大头，存在回收与恢复的往返

| 后段指标 | 快照范围 / 增量 |
| --- | ---: |
| VSS 几何及相关缓冲分配核算量 | **3.13–3.39 GiB** |
| 驻留记录核算量 `liveBytes` | **2.76–3.21 GiB** |
| 不透明几何载荷 | 约 **2.65–3.07 GiB** |
| 水体几何载荷 | **2.76–3.55 MiB** |
| GPU 软预算 | **1 GiB**，目标约 0.9 GiB |
| GPU 网格上传 | **3,577 次**，约 31.0 次/s |
| 预算淘汰 / 冷恢复请求 | **1,085 / 1,217 次** |
| 预算淘汰释放累计量 | **459.6 MiB** |
| 接缝表面更新 / 接缝网格构建 | **31,570 / 791 次** |

几何分配核算包括共享池、独立缓冲和接缝等，不能当成显卡全部物理显存占用；也不能用它直接认定显卡显存已满。`liveBytes` 与池的 committed 核算范围不同。

预算是软目标。当前回收保护可见、近处、接缝/回退覆盖，且限速淘汰，不能保证驻留量小于 1 GiB。这里值得优化的是受保护细节的体积、冷网格生命周期与恢复条件，而不是强行删除仍承担覆盖的网格。

1,085 次淘汰与 1,217 次恢复说明存在明显往返工作，但聚合计数不能证明每次都是同一瓦片被反复上传。3,577 次上传还包含正常精化与网格替换，也不等于上传了 3,577 个不同瓦片。

`waterDuplicationSavedBytes` 实际公式为旧 storage 基线与当前分通道 GPU storage 的差值，混入坐标格式等变化，不能把其巨大值解读为本场景真实水面节省量。`coordinateSavingUpperBoundBytes` 同样是旧格式比较上界，不能当成尚未实现的未来收益。

## Java 内存、GC 和磁盘

- 后段 Spark 结束快照：整个 JVM heap used **8.10 GiB**，committed/max **10.81 GiB**；这包含整个游戏和所有模组。
- VSS 自身的保留/预约核算量为 **3,064–4,734 MiB（2.99–4.62 GiB）**，其中工作区预约 0–1,280 MiB。不是 heap dump 的真实 retained size，也不能与 JVM heap used 相加。
- VSS 报告的堆余量最低 **1,185 MiB**，当前 safety 为 1,024 MiB。说明这段数据量较大，但不构成内存泄漏证据。
- CPU 冷缓存淘汰增 651 次、释放计数增 237.6 MiB；压缩完成增 1,701 次、累计节省计数增约 766 MiB。累计释放/节省不代表这些字节同时被占用。
- G1 的 673 次 Young、446 次 Concurrent、3 次 Old 为 JVM 约 114 分钟运行的累计计数。Young 平均 9.58 ms，Old 平均 288.67 ms；无法从这些汇总定位新采样两分钟内的 GC 暂停和 VSS 分配量。
- 预测缓存：命中增 13,712、未命中增 3,865、写入计数增 4,865，成品网格恢复增 1,775，错误增量 0；缓存读取/解码累计窗口 2.768 s，延后编码累计窗口 6.853 s。是逻辑操作与工作线程时间，未测物理读写带宽、文件增长量或 p95 I/O 延迟，不能声称没有磁盘尖峰。
- 后台阶段和渲染 Spark 都不是 allocation 记录，本次不能给出 VSS 的准确 MiB/s 分配率、对象类型分布或实际 JVM RSS。

## 服务端、网络与服务器生成

前段唯一服务端线程有 109,752 ms（91.46%）self 在 `park`，VSS 去重栈 468 ms（0.39%）。其中 72 ms 是提交磁盘任务时等待 `PriorityBlockingQueue` 的共享锁，不能算作 VSS 正在执行 CPU 运算。服务端近一分钟 MSPT 均值约 3.07 ms，p95 4.24 ms，三段窗口 TPS 约 20，最大 MSPT 14.42 ms。

服务端 VSS 主要入口：请求处理 212 ms、磁盘读取完成后的主线程回调 128 ms、tick 维护 104 ms；其余来自 dirty 通知等。请求内调试日志支路 72 ms，回包本地主机反射查找支路 100 ms，包含在入口时间中。队列锁、日志和反射值得减少，但这份证据不支持将服务端主线程列为持续低帧的首因。

前段请求窗口 115.709 s 增 73,122 列探测（约 632 列/s），后段 110.656 s 增 68,216（约 616 列/s）；两段 cacheHits/diskHits 增量都是 0，diskMisses 与请求增量相等。诊断记录 generationEnabled=false、generationInFlight=0，故本次没有 VSS 请求触发的大量服务器生成，不能评估 `/vss chunky` 满载性能。

前段批首坐标确有重复，后段由于移动批首坐标未重复，不能把新窗口每次探测都说成同位置重复。源码 `handleCacheProbeMiss` 在不允许生成时清除 miss 状态，日志也持续 `missMarked=0`，因此仍值得保存有版本/时效的否定结果，减少已确认不存在的列反复探测。dirty、维度/会话变化、服务器新生成的数据必须能及时撤销否定缓存。

这是集成服务器，同步回包有本地主机直接交付路径；探测次数不等于公网流量。Spark 没有分模组网络字节率，也没有磁盘工作线程采样，不能据此给出 VSS 的 MiB/s 网络或磁盘吞吐。两段日志的 Xaero backpressure 均为 false，本次没有小地图背压拖住同步的证据。

## 优化顺序

1. 覆盖实际的 Iris 绘制路径：缓存提交计划、降低逐瓦片 uniform/绑定次数、按页合批，并为 Iris 深度与着色器布局接入预测候选剔除。先验证批次减少，再用新增 GPU 计时判断收益。
2. 让不透明场景的版本检查和局部变化更新继续有效，控制 `Scene.prepare`、`PreparedPass.prepare`、可见列表与接缝传播；不能把透明通道的同帧复用当成不透明跨帧复用。
3. 优化必需预测任务中的地形采样、外表面、生物群系及 Java 装饰兼容。可见优先已将约 93% 的构建 CPU 放在可见分类，继续只压不可见任务收益有限。
