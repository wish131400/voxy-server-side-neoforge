结论：新版的主要剩余证据指向**整体预测几何量、显示层级选择和逐条提交成本**。这轮森林快照中的地形及雪材质远多于树叶；规则矩形约占 99%。现有共面合并显示 LOD 只覆盖极少量普通网格，不能据此认为远景已获得与 Voxy 相同的显示层级优化。

## 显示 LOD 已接入，但此次普通网格很少获得变体

3,890 个捕获网格中，只有 **30 个**包含共面合并显示变体。进一步区分后：

- **27 个是接缝网格**。生产 PreparedPass 对接缝使用原范围，不选择显示变体；这些变体不会在本通道用来减面。
- **3 个是普通网格**。它们在不透明 pass 中合计选择 17,492 面，另有 112 面水体；带变体网格占整个候选量很小。
- 只有 1 个网格持有 morph，关联候选 2,201 面。不能把“变体很少”主要归因于 morph 禁用了它们。
- tier 1/2/3 同时承担草和水草抽稀；大量条目进入这些 tier，不代表树冠或地形已经有合并变体。

为什么现有合并覆盖很少，源码及离线数据给出了几类原因：

1. **规则矩形不等于符合当前显示合并条件。** 约 **9,025,221 个地形候选面**带 `FLAG_LOD_TEXTURE_SCALE`，现有算法直接排除它们。另有约 **4,714,148 个地形候选面**带边界/地形墙标记，也被排除。两组存在重叠，不能相加。该纹理标记还用于生成阶段已经合并的地形矩形，因此排除数量不是“这些面完全没有优化”的证明，更不意味着可以直接删除保护。
2. **合并要求严格共面且属性一致。** 相邻高度不同、材质/颜色/光照不同的面不能直接合并。现有算法没有按允许的几何误差构建更粗的地形或树冠表示。
3. **合并后范围的碎片度限制。** 只替换部分原面可能留下大量短范围，算法会拒绝这种变体，以免减面换来更多命令。
4. **网格总量保护不是此次主要原因。** 小于 128 面的 1,233 个网格只关联约 7.8 万候选面；超过 131,072 面的只有 1 个网格，关联约 11.8 万候选面。

离线抽选 88 个网格，按 spacing、可合并量选取样本，并纳入全部 30 个已有变体网格。1 个包含交叉植物的网格无法从打包投影轴准确还原原始方向组，未参加重放。其余 **87 个、约 130 万原始面**使用生产合并算法重放，生成的附加几何数量与现场元数据全部匹配。

57 个未生成变体的重放样本中，18 个所有 tier 都超出碎片阈值；其余 39 个所有 tier 的净减面都不足 64。失败的 join 尝试主要发生在不共面及 flags/颜色/光照/feature 不一致的判断上。**这是分层选择的诊断样本，不是总体随机样本，不能将其比例外推到全部网格。**

普通归属仍按最细驻留数据选择（PredictionTileManager 的 coveringTile/coveringTileAtDetail）。缓存精细数据与按屏幕误差选择实际绘制表示仍未充分分离。当前共面合并很难替代 Voxy 的层级选择。

## CPU 缓存有效，仍有逐项工作和接缝构造

JFR 主窗口有 2,192 个渲染线程 Java 执行样本、191 个 native 样本，共 2,383 个。方法样本具有包含关系，不是独占耗时：

| 路径 | 样本 | 占全部渲染线程样本 |
| --- | ---: | ---: |
| 预测渲染主入口 renderStageUnpacked | 1,335 | 56.02% |
| PredictionIndirectBatch.add | 339 | 14.23% |
| ClientPredictionState.tick | 374 | 15.69% |
| Scene.prepare | 238 | 9.99% |
| PredictionLodSeams.apply | 160 | 6.71% |
| PredictionGpuResidency.used | 145 | 6.08% |
| PlanItem.matches | 143 | 6.00% |
| PredictionDisplayGeometry.build | 115 | 4.83% |

生产静态计划已经免去多数编码和逐字节比较；每帧仍遍历绘制条目，读取 arena slice、判断计划项版本/身份、统计候选、确定命令数和记录驻留使用时间。这些路径在本次 JFR 中确实出现，不应再把问题描述为“完整命令缓存尚未实现”。下一步应考虑在 pass 的结构/版本未变化时直接重放整批，并在适当的更新周期维护使用记录和命令计数；morph、覆盖撤销、资源与驻留变化仍需正确失效。

另有一条明确的不必要路径：

`PredictionLodSeams.stitch → PredictionPackedMesh.terrainRecords → PackedMesh 构造 → PredictionDisplayGeometry.build`

接缝构造发生在渲染线程，通用 PackedMesh 构造又尝试生成显示变体，而 PreparedPass 绘制接缝时不采用这些变体。应先让接缝专用构造避开这项无收益工作，再按版本整批交接逐步移走较重计算。已有局部更新和并行边界遮罩仍保留作用，不能退回每帧全量重建。

CPU 计时只抓到 3 个接缝更新样本，平均 4.263 ms；它不是每帧平均接缝耗时。JFR 捕获 10 次 GC 暂停，合计 74.716 ms、最长 16.197 ms。没有捕获渲染线程超过 2 ms 事件门槛的 monitor/park 等待；这不排除短等待或 GPU/驱动等待，也不能由后台约 7 核使用量直接计算它抢走了多少 FPS。

## 紧凑格式和轻量 shader 的证据强度

候选范围中 **15,629,526 面（99.16%）**符合规则矩形几何表示；地形和识别的树叶全部符合，特殊交叉几何约占 0.84%。这为“规则面保存起点、边长和方向”的独立格式提供了明确比例依据。

当前 32 字节格式已经压缩颜色/光照字典，四个角坐标仍占 24 字节。若坐标部分可以从 24 缩到 12 字节，主窗口末驻留矩形统计给出的理论上界约为 **450 MiB**。这还没有扣除新格式元数据、混合格式索引、对齐或兼容开销；不能承诺实际省下 450 MiB，更不能直接换算 FPS。Voxy 8 字节面记录另有共享模型、颜色与光照数据，也不是总共只读取 8 字节。

约 **93.02%** 的候选使用固定来源 cell。当前 vertex 已对固定 cell 查归属并裁掉不属于该瓦片的整面，fragment 随后仍读取归属，并执行深度、Voxy/原版覆盖和边界处理。这个结构值得研究针对明确归属、非接缝、没有特殊深度交接的普通远景路径，以及固定 cell 的重复归属读取。但固定 cell 本身不足以证明可以跳过真实深度和覆盖检查。

目前没有 shader 变体的同画面 A/B，也没有 GPU 顶点/片元忙碌计数，因此不能断言 vertex、显存读取或 fragment 中哪一项占了不透明区间的多少毫秒。

## Hi-Z 和显存现状

主窗口末自适应策略处于 `measuring-hiz`，最后一次诊断同时显示 `occlusion=off`；窗口混合了直绘和剔除阶段。旧的策略均值约 direct 5.787 ms、culled 5.837 ms，不是本窗口每帧成对比较，不能替代不透明通道 10.303 ms 的统计。

最近的剔除结果测试约 10.5 万命令、约 1,400 万候选面，隐藏约 3 万命令、459 万候选面。隐藏计数有实际作用，但它不足以证明本视角净 GPU 收益，也不足以证明算法失效。过滤/reduce 查询只覆盖部分内部调用；不能把单个查询均值乘全部批次当作整帧耗时。

主窗口 GPU 驻留字节从 1,491,146,528 增到 1,550,726,960（约 **1.39–1.44 GiB**）；几何页提交量为 2,214,592,512（**2.0625 GiB**），软预算为 1 GiB。驻留管理保留可见、近处、接缝和回退覆盖，预算不是强行截断；超预算本身不是泄漏证据。窗口只有 9 次预算淘汰和 9 次恢复，不能把全部 212 次上传都归为显存抖动。

## Voxy 的比较边界

19:26 的小型快照中，实际 Voxy NormalRenderPipeline 已驻留 2,402 个 section，已发布几何使用量 **26,221,568 bytes（25.01 MiB）**；geometry capacity 约 4 GiB 是容量，不能当作实际使用量。VSS 主窗口末对应的驻留几何与面数大得多。

这说明当前两套路径处理的数据量不同：Voxy 保存实际取得的区块数据，VSS 还为未到过的远处生成预测覆盖。同屏看起来精细，不意味着覆盖范围、候选量或驻留量相同。不能用这些不同时间的数值计算 Voxy 比 VSS 快多少，也没有测到相同覆盖数据下 Voxy 的 GPU 阶段与最终可见面数。

后续两个运行时快照的 VSS 配置均为：预测距离 8,192、fine 距离 1,536、surface 距离 512、植被 medium、performance high、树木与预测 AA 开启。Voxy sectionRenderDistance 为 16、subDivisionSize 为 64。主窗口没有同时记录配置；磁盘文件此前的 2,048 等值不能替代运行时配置，也不将后续值倒填为主窗口已证实的配置。

## 根据此次证据调整实现顺序

1. **先做可独立验证的 CPU 减负**：接缝专用构造跳过未使用的显示变体；静态 pass 版本不变时尽量按整批重放，避免逐 draw 重算命令数和重复维护驻留信息。保留覆盖撤销、动态 morph、上传和材质变化的失效机制。
2. **推进规则矩形紧凑格式**：本次 99.16% 的比例支持它作为保持几何外观的主要优化方向。通用格式继续负责交叉模型和特殊几何，先验证坐标、材质字典、mask、缓存恢复及水体偏移。
3. **实现真正按屏幕误差选择的显示 LOD**：同时覆盖地形、雪与树冠，将精细 CPU 缓存和实际 GPU 绘制表示分开。不能只继续给树叶共面合并加窗口，也不能只放松碎片阈值。对已就绪表示采用滞回、近处/望远镜恢复和统一归属、接缝版本；粗表示未就绪时继续保留已有覆盖。
4. **测量轻量 shader 路径的净收益**：从固定 cell、明确归属的普通远景开始，对照 GPU 时间及图像；混合所有权、真实边界、水面和特殊深度交接保留完整处理。
5. 在上述验证后再依据实际成本决定 GPU 有效命令压缩或更深的层级遍历。当前 44,597 个原始绘制范围中 24,185 个只有一面，完整 meshlet 分割可形成约 104,306 个命令；这一快照说明碎片化值得跟踪，但不是所有帧都使用该数量的分割命令。

验收继续使用同一位置、同一朝向和视口，记录实际候选与剔除后命令、预测不透明 GPU 区间、准备/提交 CPU、上传和长帧。另做后台空闲与活动的对照，区分持续绘制成本和细化竞争。只有完成实现后的同条件测量，才能报告 FPS 改善幅度。

## 代码与证据
