# 装饰解耦、批处理与预设资源可行性审查（2026-11-02）

可以把装饰拆成可复用的几何、环境需求、放置规则和结果提交四部分；简单几何可以穷举成资源，复杂特征更适合参数化执行计划。但本轮数据不支持“把最慢的装饰全部换成成品模型，就能省掉大部分时间”：主要成本发生在确定候选是否适用、读取地形和群系，而非构造模型。

本次是代码与已有记录的复核，外加小型几何资源枚举。没有运行新的性能基准，没有修改生产生成流程，也没有发布新包。

## 依据与测量范围

耗时采用 [当前生成耗时分布](generation-cost-distribution-20261102.md) 的同一组原始记录：`build/dependency-core-20261101-final/`，五个不同区域各重复两次，十条正式记录。NeoForge 1.21.1、原版主世界种子 42，单生成线程；每区域 16×16 目标区块，18×18 装饰来源区块，显示间距 4。平均总生成时间 **3646.79 ms/区域**，装饰阶段 **3385.66 ms**。

这组数据不包含实机渲染、磁盘读取、加载调度或整合包测试，不能换算成帧数，也不能证明 Forge 和所有群系模组的实际收益。

源码使用本项目实际依赖的 `neoforge-21.1.234-sources.jar`，配置使用配套 Minecraft 资源包。本次提取的源码与配置以及逐条 SHA256 记录在 `build/decoration-decoupling-audit-20261102/sources-manifest.json`。没有用其他 MC 版本的实现代替当前依赖。

补充汇总保存为同目录 `feature-cost-summary.json`，包含十份原始 Feature 记录的 SHA256。几何枚举保存为 `primitive-mask-inventory.json`；它只描述局部偏移，不包含实际世界放置结果，生产代码没有加载这个文件。

## 最耗时的条目究竟在做什么

下表每行的查询时间已包含在完整耗时内，不能再相加。群系候选计数来自 Java 放置过滤探针；原生内部查询没有在这里单独拆分。

| Feature | 完整 ms/区域 | 精确地表 ms | Java 群系 ms | 当前记录的关键现象 |
| --- | ---: | ---: | ---: | --- |
| 沙盘 `disk_sand` | 428.34 | 410.87 | 1.25 | 精确地表和群系合计占该条目 96.21%；圆形枚举不是大头 |
| 发光地衣 `glow_lichen` | 270.29 | 198.33 | 53.65 | 邻域、地表与群系读取占主导，平均 291.4 次写入 |
| 洞穴藤蔓 `classic_vines_cave_feature` | 226.39 | 0.00 | 201.84 | 每区域 82944 次群系检查，778.4 次通过，最终平均 3 次写入 |
| 森林岩石 `forest_rock` | 197.29 | 191.26 | 1.78 | 每区域 648 个群系候选，全部拒绝；没有进入岩石形状生成 |
| 竹子 `bamboo` | 189.25 | 未独立拆分 | 未独立拆分 | 已走原生批处理，内部查询包含在完整时间内 |
| 冰刺 `ice_spike` | 183.91 | 177.01 | 2.24 | 每区域 972 个群系候选，全部拒绝；没有进入冰刺形状生成 |
| 大型滴水石 `large_dripstone` | 161.42 | 125.05 | 30.69 | 每区域 9421 个群系候选，通过 329.6 个，最终没有写入 |
| 藤蔓 `vines` | 128.44 | 63.43 | 48.50 | 生成体本身是单方块；邻居附着和过滤才是主要工作 |
| 紫晶洞 `amethyst_geode` | 121.12 | 68.05 | 0.08 | 相对更适合研究形状场批算，但仍含环境检查 |

森林岩石与冰刺共 **381.20 ms，占总生成时间 10.45%**，却没有执行模型生成。这直接说明：即使预先保存了所有岩石和冰刺模型，也省不到这组输入里的主要成本。

这也不等于提前跳过这两个 Feature 就必然节省 381.20 ms。现有计时会把首次地表缓存未命中记到触发它的条目名下，其他有效 Feature 可能稍后仍要读取同一地表；提前拒绝也需要花费群系查询，并受随机顺序和可观察副作用约束。

沙盘扣除已计精确地表和群系后只余 **16.22 ms，占总时间 0.445%**。余项还包含放置规则、缓存和写入等工作，不是纯几何成本。在环境执行方式不变的假设下，即使全部消掉这项余量，也覆盖不了大的整体加速。沙、沙砾、黏土、草四种盘完整共 584.32 ms，其中精确地表 558.79 ms。

## 哪些可以变成预设资源

| 对象 | 可以预存或编译的部分 | 仍需现场决定的部分 | 适合的形式 |
| --- | --- | --- | --- |
| 沙、沙砾、黏土、草、冰块斑 | 离散半径的圆盘偏移、目标谓词、状态提供器计划 | 地面材质、邻居、水体、之前的编辑及状态提供器随机数 | 小型几何表 + 放置程序 |
| 森林岩石 | 三个小石团的基础偏移表 | 落地位置、随机组合及位移、原始随机消耗 | 基础石团表 + 有序组合 |
| 冰刺 | 离散高度/半径的逐层候选轮廓 | 边缘随机缺损、雪地条件、地下根部终止、稀有增高 | 参数化层模板 |
| 竹子 | 已解析的方块状态、竹竿与顶部状态组合 | 生长空间、地面、实际高度截断及灰化土盘 | 列生成内核 + 环境批查 |
| 藤蔓、发光地衣 | 朝向状态、已确认不依赖世界的固定规则 | 真实邻居附着、已有面、水体、扩散、模组钩子 | 状态表 + 邻域规则 |
| 大型滴水石 | 参数化轮廓公式、固定数值计算 | 洞穴上下界、嵌入支撑、岩浆、风偏移、逐列终止 | 编译计算内核 |
| 紫晶洞 | 已知参数下的形状/噪声场计算计划 | 绝对坐标噪声、围岩、流体、裂隙、芽体和方块状态 | 形状场批算 + 有序应用 |
| 自定义模组 Feature | 使用已支持标准实现时，可复用同类编译器 | 自定义代码可能读取任意世界数据并执行额外行为 | 标准类型编译，未知实现保留原调用 |

本轮实际枚举出圆盘半径 2–6 的 **5 张表，共 285 个 XZ 偏移**，即可覆盖所审查的原版盘形几何。纵向扫描仍须按原顺序下降；`disk_sand` 在下方为空气时应生成砂岩，`disk_grass` 会查看上方环境，不能把整个模板统一盖成沙或草。

森林岩石每个石团只有 `(i,j,k)∈{0,1}³` 的 **8 组尺寸参数，对应 5 种不同点集**，最大单团 19 个方块。这很适合预存，但它的几何本来就小。三个石团之后的随机中心位移仍应照常消耗随机数，包括最后一次没有后续几何用途的位移。

大型滴水石的形状会根据洞穴裁剪，紫晶洞噪声使用世界种子及绝对位置；把一个地方生成的最终块列表平移到另一处，通常不会得到原算法的结果。它们更适合保存“怎样生成”的执行计划。

## 为什么不穷举所有最终结果

需要区分基础形状、条件放置程序和最终方块结果。前两者常常可以复用，最后一项通常还取决于附近真实环境。

例如一个模板中若有 32 个位置各自存在可替换/不可替换两种输入，仅这个示意环境就有 `2^32 = 4294967296` 种组合；这还没有计入形状随机数、群系、流体和方块状态。这个例子说明组合规模，并不假定某个实际 Feature 的全部位置都能独立取值。

世界种子和随机状态虽然是有限的，也不代表完整模型库在存储或生成时间上可行。模组、数据包和标签还会新增条件。合理资源是小型形状、调色板和参数化规则，现场查询必要条件；相同世界相同位置已经生成过的完整结果则交给结果缓存。

直接覆盖所有模板方块会改变悬崖、水边、结构交界和其他装饰之间的结果。若未来明确接受视觉近似，可以另外评估更大范围的成品模板，但不能把它描述为原结果的无损缓存。

## 项目已经具备的部分

- [PredictionPlacementExecutor](../../../src/main/java/dev/xantha/vss/client/prediction/PredictionPlacementExecutor.java) 已将已知放置修饰器编译为计划。它按深度优先顺序执行，候选 A 的终端生成先消耗随机数，然后才产生候选 B。
- [PredictionSurfaceFeatureAdapters](../../../src/main/java/dev/xantha/vss/client/prediction/PredictionSurfaceFeatureAdapters.java) 已提供终端替换位置，目前主要处理湖泊和末地尖塔；可在这里接入经过审查的形状/规则内核。
- [PredictionTreeModels](../../../src/main/java/dev/xantha/vss/client/prediction/PredictionTreeModels.java) 已按 Feature、地面和变体缓存树模型：8 个变体、最多 256 个模型、65536 个保留方块。它复用主干和树冠，再做环境检查以及适用的藤蔓/可可处理。**这些是视觉树形变体，不是同种子所有真实树形的穷举**；不支持的自定义根部和装饰器仍走原流程。
- [RustVegetationStage](../../../src/main/java/dev/xantha/vss/client/prediction/RustVegetationStage.java) 已维护原生/Java 编辑衔接与回滚；原生装饰已经支持竹子等类型。它们不是全部仍在 Java 单方块生成。
- [PredictionVegetation](../../../src/main/java/dev/xantha/vss/client/prediction/PredictionVegetation.java) 已缓存完成的区块装饰结果，并接入磁盘缓存。已经算过的相同区域可以复用；无限新区域的首次生成不可能全部预存。

因此，不需要另造一个装饰框架，也不应把树模板再包装一遍当成新增性能收益。缺口是更多终端内核及它们共享的环境依赖处理。

## 可落地的解耦方式与批量边界

推荐在现有流程上增加以下分工：

1. **加载世界配置时编译模块。** 从真实注册表和配置提取几何、方块状态、谓词及环境需求。相同标准 Feature 实现可以覆盖采用它的不同群系模组；不能仅按模组名或 Feature 名宣称支持任意自定义实现。资源随版本、配置、标签和代码实现改变而失效。
2. **生成候选时保留随机顺序。** 继续使用当前放置计划。只有已经证明不依赖终端随机消耗和中间写入的部分，才可先收集成一批。不能简单把所有候选提前算完，再共用原来的随机对象放置。
3. **批量生产确定需要的环境。** 将多个规则共同需要的不可变地形/群系数据去重，复用已有 4×4 页及原生依赖计划。研究重点是减少实际环境计算量，而不是增设一套并行缓存。群系区域排除必须覆盖候选真正可能到达的 XZ/Y 范围与原有群系缩放语义，中心群系不构成排除证明。
4. **执行几何与条件程序。** 小型偏移表直接读取，复杂形状用编译内核计算。可独立的噪声/几何计算适合批量处理；未知世界依赖的模组逻辑仍调用原实现。
5. **依照原 Feature、候选和写入顺序提交。** 不可变基础地形可以预取；读取“当前方块”时必须叠加之前的编辑。不同装饰能互相覆盖和依附，不能对同一旧世界快照全部运算后无序合并。

这里的批量化可以用于去重、连续内存和数值计算，不等于把所有 Feature 同时放到不同线程。并发只适用于已证明输入独立的工作；已有整体区域并行仍可继续承担并行吞吐。

## 优先级与收益验收

**先验证环境与适用性模块，再扩大预设模型库。** 洞穴藤蔓的群系通过率只有 0.94%，森林岩石/冰刺的最终群系全部拒绝，说明放置前置工作值得研究；但它们也证明模型预设不能替代这些前置工作。共享准确的群系结果、证明整段候选不适用以及避免无谓的完整地表生产，都需要完整生成对照证明收益。

已存在的 [按需高度与提前拒绝实验](decoration-demand-evaluation-20261031.md) 给出了反例：最终组合完整精确点数只下降约 0.089%，相对前后控制整体变慢约 4.83%–9.52%。后来有效装饰仍会访问同一完整地表。不能因为现在重新称为模块化，就重复承诺这个拆分会加速。

盘形内核适合做规模小、语义明确的验证模块，但它的目标应是验证“环境需求—模板—有序写入”这条链路，不能以圆形枚举速度推算整体倍数。原生竹子应先拆分其内部环境与放置耗时，再决定是否值得进一步做模板。

下一轮实验至少同时比较完整生成墙钟时间、精确地表实际点数/计算工作、真实群系加载次数、分配量与原生内存，以及逐位置 BlockState/地形/体素结果摘要。随机状态延续和边界编辑也要校验。输入应包含匹配与不匹配群系、跨群系/水边/悬崖、结构交界，以及代表性自定义模组；单一种子或空场景的局部加速不足以发布。

目前没有这套组合架构的性能实测，因此不给出加速倍数。现有证据支持小型资源与规则编译的可行性，并明确将大幅提速的验收重点放在是否实际减少了占总生成约 62.89% 的已计地表/群系查询，而非模型数量。
