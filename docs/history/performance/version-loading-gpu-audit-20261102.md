# NeoForge 与 Fabric 多版本生成速度、26.3 GPU 路径审查（2026-11-02）

本轮实测当前 0.3.7 的 NeoForge 1.21.1 和全部八个 Fabric 目标，另对 26.3 执行两组 CPU/GPU 对照。结论：未观察到 Fabric 总体比 NeoForge 快数倍；当前主要时间仍在装饰。26.3 GPU 的计算确实生效，但本机细化场景没有稳定收益。代码审查和运行探针还发现 26.x 树模板沿用了失效的土壤标签准入，导致草方块上的候选直接被丢弃。

## 测量范围

- Ryzen 7 7700，8 核 16 线程；RTX 4070 Ti SUPER；Windows x86_64。
- 使用当前生产 Java 源码的独立冻结副本、已发布标准 JAR 中相同的 Windows 原生库。全部发布清单构建标识为 `20261102-storage-helper-loading`。
- 每个版本启动实际游戏服务端，由生产 `WorldgenProfileHolder` 导出本版本群系、生成器、标签和结构模板。解码时提供真实已同步注册表环境，避免 26.x 世界时钟/时间线缺失造成夹具错误。
- 种子 42，相同坐标序列；每片 16×16 个目标区块，含装饰邻域共 324 个源区块。地形采样间距 4 格，装饰间距 1 格。2 次预热，5 片不重叠区域正式计时。
- 单个生成工作线程，完整经过地形、按序装饰、地表整理及 `PredictionVoxySource.build`。26.3 从生产 `sampleDisplayRegion` 进入 GPU 路径。
- 不计启动、注册表导出、上下文/原生世界初始化、哈希、显式轮间 GC；计入生成期间实际发生的 GC。GPU 初始化和校准另列。
- **没有计入任务调度、网络、磁盘缓存、Voxy 接收/建网格/发布、画面绘制，也没有测 FPS。表中区块/秒为单线程生成等价吞吐，不能外推成 14 线程整圈加载时间。**
- 为使同版本 CPU/GPU 可复现，仅在隔离副本将 native stage 外部 shuffle entropy 固定为种子/坐标/阶段派生值；不消耗或改变 Feature 的随机流。没有降低精度、关闭植被、删减功能或修改发布包。

所有 CPU 组按累计正式时间计算，装饰约占 **91.8%–93.5%**。地形阶段通常约 0.22–0.26 秒，装饰约 3.0–3.8 秒。单独优化本片地形，即使将其成本降到零，总耗时收益也仅约 6%；GPU 实测还增加了这部分成本。

### 路径和输出差异

NeoForge 的 `PredictionDecorationLevel.getNoiseBiome` 使用 `context.noiseBiome`，Fabric 则使用 `terrain.noiseBiome`，后者由 `RustTerrainSampler` 原生实现。Fabric 1.21.1 最后一轮累计原生群系点数 957455、原生批数 927530，Java 回退计数为 0；NeoForge 原生点数 30492、批数 567，另有直接 Java 装饰群系查询，不计入原生回退计数。

对应地，NeoForge 单片 Java `horizontalCopied` 为 35640–83270，Fabric 1.21.1 为 0；后者并未消费 Java 气候节点，`deferred` 不是绑定丢失。Rust 水平缓存累计命中分别约 333 万和 849 万。26.3 同时存在原生和 Java 路径，实际产生少量跨端复制。原始诊断保留了各组完整计数，不能用 Java copied 是否大于零作为所有版本统一准入标准。

这意味着 Fabric 把群系查询移到 Rust 后仍可能被大量单点 JNI 调用消耗收益；但本轮没有隔离该变量，不能把总差值全部归因于 JNI。NeoForge/Fabric 1.21.1 的七片输出有六片哈希完全相同，另一片装饰方块数相差 3 个（223412 / 223409）。两边还存在局部越界写入处理差异，不能将本次默认路径比较称作严格相同实现的加载器 A/B。

跨 Minecraft 版本本来就有资源和生成规则变化，不要求输出哈希相同。26.x 另外存在下述缺树问题，当前速度表**不能代表同等完整画面的公平排名**。

## 26.x 树模板土壤准入错误

`src/versions/mc26/.../PredictionTreeModels.java` 和 `mc263` 的对应类均继续以 `ground.is(BlockTags.DIRT)` 作为模板准入；不满足时 `soilRejected++` 后直接返回。回放地面检查也使用同一个标签。

直接读取对应 Minecraft 客户端 JAR 的原版资源：

- 1.21.11 的 `minecraft:dirt` 标签包含草方块、灰化土、菌丝体、苔藓、泥巴等。
- 26.1 / 26.3 的同名标签仅包含 dirt、coarse_dirt、rooted_dirt。
- 26.1 原版橡树改用 `below_trunk_provider` 的 `cannot_replace_below_tree_trunk` 规则；26.3 使用 `minecraft:soil_beneath_tree` provider。旧 dirt 标签不能代表新版树能否在当地生成。

运行时只读探针在 26.3 一片 256 区块中记录到进入模板土壤判断的 241 个候选：**201 个是草方块，dirt=false，地面和上方均无流体，全部被直接拒绝；另 40 个为泥土但上方有水**。这不是推测或标签未加载：实际方块与实际标签判断均已记录。主矩阵 26.1–26.3 的七片树模板 built / hits / placed 均为 0；旧版 1.20.1 / 1.21.1 / 1.21.11 则分别构建 80 / 79 / 78 个模板。

该错误同时损害视觉正确性和优化覆盖。修复应依据新版树的实际放置/土壤 provider 语义，未知情况走原生成回退；不能简单扩大到任意实体方块，也不能把被错误拒绝的树算成加速收益。本轮仅审查和记录，没有修改生产逻辑。

## 26.3 GPU 是否实际加速

两组均确认 `ready:NVIDIA GeForce RTX 4070 Ti SUPER`、`minDisplaySpacing=4`，初始化/校准分别 823.162 / 819.603 ms，单独计时。每组七片累计实际提交 168 次，最大批 256 柱，GPU 处理 30464 柱，28 柱因末端小批回 CPU。队列等待总计 5.62 / 5.47 ms，实际 dispatch 总计约 2160 / 1994 ms。**GPU 并非仅配置打开而未执行。**

| 同版本完整路径对照 | 第一组 CPU | 第一组 GPU | 第二组 CPU | 第二组 GPU |
|---|---:|---:|---:|---:|
| 完整生成中位数 ms | 4069.078 | 4058.649 | 3923.713 | 4127.572 |
| 地形中位数 ms | 230.991 | 387.774 | 226.645 | 395.222 |
| 装饰中位数 ms | 3835.087 | 3694.720 | 3684.543 | 3729.576 |

第一组完整耗时仅减少 0.26%，第二组反而增加 5.20%，没有稳定收益；地形耗时两次分别增加 **67.87% / 74.38%**。四组同坐标的全部输出哈希完全一致，CPU/GPU 两对各七片均通过。结果不包含渲染并发，不能据此声称开启 GPU 对游戏帧时间无影响。

`VulkanPredictionCompute.validate` 用固定 64 点、固定校准位置比较 `displayDensityFloors` 与原始 GPU dispatch，并以 GPU 快于 CPU 20% 选择间距。生产入口则以 16×16 区域提交，随后 8×8 消费，经过缓存检查、排队、结果复制、Rust 群系/材质处理及必要精确回退。该选择器在本次工作负载确实选中了更慢的地形路径。

另外，校准 oracle 新建普通 Job，未启用正式 display 路径条件触发的 `reuse_density_cells`。这是代码差异，但本片 step4 与插值宽度4不一定产生跨列共享，**不能将本次退化全部归因于此标志**。仍需分别量化代表性地形、256 柱批次、生产 CPU 缓存/区间证明、GPU 总扫描量与回退重算。当前最先应改的是以实际完整区域成本选择后端，并有运行中退回 CPU 的依据。

## 最近优化覆盖

| 优化 | 当前 26.3 状态 | GPU 路径的实际含义 |
|---|---|---|
| 编译密度依赖图、表达式去重 | 有 | Rust 导出 final_density 图，shader 按依赖生成节点，重复节点复用 |
| 水平子表达式复用 | 有 | shader 使用 column_plan 判断并按坐标/volume 身份缓存；公共 Rust 与 Java 水平气候共享另行保留 |
| 插值角点复用 | 有 | 每个 shader invocation 复用同单元八角点，并核对完整嵌套 volume；不是 CPU 多列共享表的直接复制 |
| 精确高度区间/空单元证明 | CPU 有，shader 未实现等价区间跳过 | shader 仍分 256 层逐 Y 搜索，由每柱 32 lane 处理；公共 Rust 回退保留原优化 |
| 干空气证明 | 公共 Rust 有 | shader 只找密度边界，不计算含水层压力；装饰精确查询和 GPU 不适用时的回退仍受益 |
| 含水层邻域复用 | 公共 Rust 有 | 同上；无需为不执行的压力阶段复制同名 shader 优化 |
| 群系及材质中间结果复用 | 有 | GPU 高度回到 `display_density_record`，继续用 Rust 群系、地表材质和颜色路径；未将这些全部搬到 GPU |
| 冷柱筛选、区域合批、队列上限 | 有且实测进入 | 冷 mask、至少16柱、最多256柱/请求，设备最大512柱；display等待名额2、总request名额8，按FIFO合批 |
| 树模型复用 | 代码有，26.x 实测失效 | 被上述旧土壤标签硬判断挡住；不能声称全部优化都有效 |
| primitive 装饰缓存、公共有序装饰及体素整理 | 保留 | GPU 仅替换地形高度阶段，后续仍走同一生成链路 |
| 上轮 column/span 直出、需求裁剪实验 | 未进入生产 | 前轮完整路径未证明稳定收益；本轮各版本均未将其实验代码混入 |
| 真实 Voxy 数据接管、缓存/调度相关修复 | 公共源码保留 | 不属于密度 shader；本轮夹具不覆盖实际画面接管、排队或磁盘加载速度 |

主要代码入口为 Horizon 的 `mc263/.../RustTerrainSampler.java:528`、`VulkanPredictionCompute.java:145` / `:201`、`VulkanDensityDevice.java:274`；原生端为 `density/vulkan.rs`、`backend/display.rs`、`terrain.rs`。NeoForge 装饰群系调用在 `PredictionDecorationLevel.java:518`；Horizon mc121 对应实现调用 terrain。

## 证据与复现

工具位于 `tools/performance/version-loading/`，通过独立源码/资源目录和独立 server 世界执行，不写两个主项目的 `src` 或 `lib`。`matrix.py` 按顺序运行，`run.py` 支持单版本及可选只读土壤探针；`summarize.py` 汇总完成组；`archive.py` 检查冻结源码/资源哈希、发布 DLL 一致性并归档证据。

本机原始数据目录为 `external/performance/20261102-version-loading/`：formal 为主矩阵，retries 为修正夹具启动后补齐的 1.20.1/1.21.11，gpu-confirm-* 为第二组 GPU 对照，soil-probe-263 为非计时排名用的土壤计数。smoke 及失败启动不参与正式结果。最初 1.20.1 使用 Java17 启动 Gradle 不满足 Loom 的 Java21要求，1.21.11也不使用 assembleMainSources；均为夹具问题，修正后分别完整重跑。

独立 evidence 目录保存 14 组完成运行的结果、诊断、输入、清单和启动日志；已核对所有冻结文件及208个证据文件校验值。发布原生库 SHA-256：

- NeoForge：`1c1a25afec9f8fe02416873f84226d5ee9e1cba24380a1015f5de527e9c0c289`
- Fabric：`275cc9bcb11adc9483bd1aec690280617fc2cc4eefb051560f0d98b331189e19`

本轮没有打包、覆盖发布产物或修改生产功能。下一步优先修正现代树土壤准入并做完整植被正确性回归，其次修正 GPU 的实际区域准入/回退选择，再评估是否值得增加 shader 的区间跳过。跨版本游戏内完整加载时间和渲染帧时间仍需在对应客户端分别采样。
