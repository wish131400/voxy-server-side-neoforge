# 装饰按需高度与提前拒绝：实现和收益验收（2026-10-31）

已按上一轮架构审查实现 Java/Rust 按需高度原型、局部提前群系拒绝，以及原生装饰代理的懒加载高度，并完成完整生成对照。当前实现没有产生可靠的整体收益，未进入生产；本轮生产改动已恢复，未为该实验打包。

此前将这一方向列为优先项，依据是高度查询不应先物化完整地表记录。实测修正了这个判断：在本输入中，后续方块查询仍会要求几乎全部相同的完整地表记录。只将高度需求拆出来，并没有消除主要工作。

## 实际实现范围

- Rust 增加批量高度证明接口：只返回 WORLD_SURFACE/OCEAN_FLOOR 两类代理高度，不生成材质外壳、邻居地表规则和颜色记录。证明无法成立时返回未知，继续完整接口。保留表面规则、特殊地形、结构影响和顺序敏感图的回退。
- Java 装饰环境增加独立的 4×4 高度页。仅未编辑、精确地形路径使用；完整材质页、显示地形和编辑覆盖继续保留原语义。旧原生库缺少新增 JNI 时能够回退。
- 对紧邻纯方块谓词和 BiomeFilter 的情况，先按同一精确坐标进行群系拒绝；环境扫描仍只复用已知答案，不预先改变扫描终点或随机流。
- 原生装饰代理增加独立懒高度页；写入或回滚后仍按原方块环境回答。最后一组还让 Java 方块读取复用已有高度证明，直接回答顶面以上的 AIR，并先处理编辑覆盖。

这些是已实现并测量的路径。完整材料、表面规则及颜色的进一步分层生产没有在本轮完成，不能将本结论扩大成“所有按需环境方案都没有收益”。

## 运行条件与正确性

Windows x86_64，真实 NeoForge 1.21.1 / NeoForge 21.1.234 运行时；原版主世界，种子 42。每片 16×16 目标区块，显示网格间隔 4，装饰包含外围一圈，即 18×18 来源区块。每模式两片预热，第一、第三组各五片正式区域，第二组三片。固定外部 shuffle 熵，各模式使用相同区域。

三组共生成 95 片（含预热及重复控制），其中 76 片与相应基线比较，输出摘要全部一致。摘要覆盖装饰方块的完整坐标和 BlockState、地形列的群系/区间/BlockState，以及发布包围盒。这个结果只覆盖所测输入，不能证明所有模组或种子等价。

Rust 高度专项筛选运行 3 项通过、0 项失败，包括干湿/空柱与代理高度、查询前后完整材料一致、规则/特殊地形未知回退，以及原生代理写入/回滚对照。虽然一个测试名包含 stateful，没有额外构造专门的有状态图 fixture，不能据此声称已经覆盖所有顺序敏感图。

这是带探针的离线生成实验，未运行渲染；不能换算游戏 FPS、GPU 帧时间或整合包收益。Java 分配量是生成线程累计分配字节，既不是常驻堆大小，也不包括 Rust 内存。

## 第三组：复用高度回答空气

最终组合包含 Java/原生高度、提前群系拒绝，以及 Java 对已有高度证明的 AIR 回答。此组重点检查后续空气谓词能否免去完整材料页。

| 路径 | 总耗时 ms | 装饰 ms | Java 完整精确地表点数 | 额外 Java 高度接口 ms | Java 分配 MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次基线 | 5,362.77 | 5,046.25 | 85,916.8 | 0 | 513.38 |
| 前置重复基线 | 4,873.95 | 4,578.76 | 85,916.8 | 0 | 511.38 |
| 最终组合 | 5,104.34 | 4,825.30 | 85,840.0 | 756.98 | 521.17 |
| 末尾重复基线 | 4,665.02 | 4,392.46 | 85,916.8 | 0 | 511.24 |

完整精确请求点数只下降 76.8 点/片，约 **0.089%**。五片正式区域中只有一片下降 384 点，其他四片不变。对前置和末尾重复控制分别逐片配对后，平均耗时增加 **4.83%** 和 **9.52%**；这不是对均值直接相除得到的百分比。两个不改代码的控制同坐标耗时差为 0.69%–12.05%，因此不把单一百分比当成稳定回退量。

Java 线程累计分配相比两个重复控制均增加约 9.8–9.9 MiB/片。高度证明成功率高，并没有变成完整材料工作量的相应下降。

## 为什么没有兑现收益

1. 高度是装饰的一种前置需求。稍后的地表方块谓词、环境扫描和有效特性仍会读取同一片完整材料；把首次查询延后，并不等于跳过材料生产。
2. 原有 4×4 完整精确页已经批量复用。本实验多生成了一组高度页，却几乎没有省掉后续完整页，增加了缓存、对象和跨接口查询成本。
3. 提前拒绝只能排除局部候选。其他特性会触发相同环境，不能按“某特性少查了多少次”累加成整体收益。
4. 仅回答已知顶面以上的空气仍覆盖不了多数实际材料需求；第三组的完整请求量直接验证了这一点。

后续若继续做大幅优化，应证明完整材料/表面规则/颜色生产或特性依赖范围实际缩小，而不只统计高度快速路径命中率。当前数据不支持继续为这一高度拆分版本增加生产复杂度。也不能据此删除无写入特性、减少树量、降低距离或改变世界输出。

## 重现实验

`prepare_demand.py <新目录>` 从匹配清单的正式基线重建 Java 原型；`prepare_demand_native.py <新目录>` 同时重建原生源码，并加入只存在于实验副本的模式选择。补丁恢复仅在临时目录进行，核对补丁 SHA、基线 SHA 和恢复后 LF 规范文本 SHA，不修改生产源码。恢复生产后已实际验证两次准备流程成功。

准备工具不会编译原生库。使用原生方案时，必须在新目录的 `native` 下运行 release 构建，把生成库复制到该目录的 `main-resources/META-INF/vss-natives/windows-x86_64/`，并记录实验库校验值；不得把主项目 `target/release` 的实验库当作正式资源。本轮也没有为原型执行五平台发布构建。

然后使用 `tools/performance/decoration-experiment/experiment.gradle`，每次指定独立的 `--project-cache-dir` 和 `-PvssExperimentRoot`。前两组使用的模式分别为 `baseline,baseline_repeat,height,eager,combined,baseline_tail` 和 `baseline,baseline_repeat,native,combined,baseline_tail`；最终组为 `baseline,baseline_repeat,combined,baseline_tail`。正式片数为 5、3、5，预热均为 2，side 均为 16。计时期间不并发编译或运行其他重负载。

`compare.py <目录>` 必须同时检查完成标记、失败文件、逐片输出和前后控制；高度分项见各片 `feature-costs-*.json`。原始完整证据保存在：

- `build/decoration-demand-prototype-20261031/`
- `build/decoration-demand-native-20261031/`，成功日志为 `run-retry.log`
- `build/decoration-demand-air-20261031/`
- `build/decoration-demand-heights-tests.log`
- `tmp/decoration-demand-20261031/final-production-checks.json`

长期结果 JSON 保存了全部 95 片行数据、输出摘要、每片高度统计、前后控制汇总及原始输入/证据文件校验值；构建目录用于保留更详细的逐特性归属，不代替长期记录。
