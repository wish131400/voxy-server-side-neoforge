**VSS 按玩家视野优先细化：可行性评估（2026-10-10）**

结论：可行，建议先实现基于实际 LOD 视锥的细化准入与优先调度，再评估遮挡反馈。主要收益是缩短当前画面达到目标细节的时间；单个瓦片的计算速度、完整一圈的完成时间和静态 FPS 不会因此自动按比例改善。

本轮检查了 Forge 与 NeoForge 的现有调度、规划、粗细交接和渲染可见性代码，并运行两端已有相关测试。没有修改生产代码、启动客户端、做运行时性能采样或构建新的交付 JAR。下述收益模型是条件估算。

**现有实现与剩余问题**

**推荐的第一阶段**

保留现有全方向规划和可用粗覆盖，先改变昂贵细化任务的准入。按以下类别调度：

| 顺序 | 区域或任务 | 调度方式 |
| --- | --- | --- |
| 1 | 当前画面缺失覆盖、Voxy 覆盖撤销后的恢复、可见接缝和父子交接依赖 | 优先恢复可用覆盖；依赖可以处于屏幕外 |
| 2 | 实际视锥内地形与植被、建筑的目标细化 | 按屏幕影响、几何误差、距离和望远镜焦点排序，逐区域形成完整画面 |
| 3 | 视锥边缘、近期看过、移动或转向即将进入视野的区域 | 较低优先级预备，保留有限缓冲 |
| 4 | 无可见依赖的纯视野外高精度升级 | 前台有欠账时暂缓入队；有余量时再推进 |

360° 最低粗覆盖单独保留为基础工作。已有精细结果保持可用；暂缓意味着延后新计算，不意味着随镜头移开就降级或释放网格。视野外从初始粗覆盖继续升级到中程或最终精度可以延后，但应检查是否正被可见区域当作父网格、接缝或替代依赖。

具体需要联动的环节：

- 发布带维度、相机代次和时间的不可变 LOD 视锥快照，对规划中的瓦片进行保守分类。已有地形 bounds 可以收紧；未生成的区域使用保守 bounds，并计入建筑、植被和接缝。不能只读取上一帧已经绘制的瓦片，否则未生成的细瓦片永远无法成为可见候选。
- 在入队前暂缓纯视野外昂贵升级；镜头转动后移除或降级未开始任务并释放预约，再提升新视野任务。工作线程启动时复核类别与预算。已运行的任务尽量完成当前有效阶段，避免每次转动都取消并重算。
- 使用视野外保留时间、边缘保护带和有限预测，减少镜头轻微抖动时的队列反复变化。明显转向时快速更新可见分类和队列；完整四叉树规划继续节流，避免重新引入每帧扫描、排序和分配。
- 当前视野目标完成后允许合适的额外精化，区分可见欠账与被暂缓的普通后台欠账，保留空闲细化的资源和稳定时间控制。
- 加载状态分别报告当前视野地形与表面细节、全方向最低覆盖、后台欠账。当前画面的完成指标应包括 GPU 已上传且可绘制，避免只完成 CPU 网格就显示完成。
- 联动 [预生成准入](C:/Users/Administrator/Desktop/voxyserverside-neoforge-1.21.1/src/main/java/dev/xantha/vss/networking/client/PredictionGenerationPriority.java:51)。它当前等待原加载进度达到 95%，回落到 85% 以下会重新保持预测优先。如果永久暂缓屏幕外任务而沿用原完整计划进度，普通预生成可能长期等到保活窗口；应明确定义新的就绪条件，并保留覆盖和资源预算。

**遮挡后的第二阶段**

实际视锥能识别身后与画面外区域，无法确定山后、建筑背面是否可见。[当前 Hi-Z 反馈](C:/Users/Administrator/Desktop/voxyserverside-neoforge-1.21.1/src/main/java/dev/xantha/vss/client/prediction/PredictionOcclusionCuller.java:37) 只有命令和四边形总量等四个汇总计数，每 30 帧尝试采样，没有可直接给调度器使用的逐瓦片历史。

若第一阶段测量仍显示遮挡区域浪费大量生成时间，再补按瓦片聚合、异步回读的可见性历史。GPU 结果应带相机、世界和网格版本，连续多帧遮挡才降级，转身、传送或世界变化时失效。遮挡证据作为延期依据；缺失瓦片通过粗父级和保守 bounds 继续获得探测机会。回读沿用不阻塞主线程的方式。

**收益如何判断**

优先调度改变的是有效计算容量分配，而不是密度采样或网格构建算法本身。在其他成本不变且并行容量能被有效利用的假设下：当前视野细化速度的理想增益约为“优化后用于当前视野的有效工作量占比 / 优化前该占比”。

| 假设分配变化，非本次测量 | 理想增益 | 含义 |
| --- | --- | --- |
| 50% → 90% | 1.8 倍 | 当前视野等待时间理论上可缩短约 44% |
| 80% → 90% | 1.125 倍 | 当前视野等待时间理论上可缩短约 11% |

真实提升会被必要粗覆盖、交接依赖、不同瓦片成本、已运行任务、缓存恢复和上传交接限制。现有代码已有前台优先，不能根据屏幕占一圈的角度直接承诺数倍改善。

固定朝向冷进档、沿固定方向跑图最有希望获得明显提升。不断快速转身时需要的区域会逐步接近全周围，收益减小；暖缓存恢复和已有充分前台优先的场景收益也可能较小。被延期的任务后来仍要生成时，总计算量主要是推迟；只有没有再被需要的细化被避免，才会直接减少总生成量。降低竞争可能改善帧时间，但 GPU 已经成为瓶颈的静态 FPS 不能据此承诺上涨。

**验收与本轮验证**

建议新增观测：前后台实际 CPU 工作时间、队列等待 P50/P95、当前视野达到普通地形和表面目标的时间、转身到第一份可绘制细节的时间、重复入队与取消量、每帧上传量，以及 P95/P99 帧时间。比较相同种子、位置、朝向、设置和后端的冷缓存与暖缓存；覆盖固定视角、跑图、飞行、180° 转身、望远镜、高空和 Voxy 归属撤销。完整一圈完成时间单独统计。

两端各自运行的已有测试均通过：PredictionWorkViewTest、PredictionBackgroundSchedulingTest、PredictionMediumCoverageTest、PredictionIdleRefinementTest，共 13 项/仓库。这确认现有框架的分类、转向队列、局部放行、父级覆盖与细化平衡行为，没有验证上述新方案的实现或实际加速比例。

实施判断：第一阶段可以复用现有队列、CPU 预约、父级回退和接缝机制，属于中等规模的调度改造；应先量化视野内实际得到了多少有效容量。逐瓦片 GPU 遮挡反馈需要新增数据流，放在第一阶段效果评估之后。
