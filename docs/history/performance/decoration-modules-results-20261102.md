# 装饰预设与环境批量准备：完整路径实验（2026-11-02）

盘形装饰可以拆成预设几何、批量环境准备和有序条件写入，且新路径能在真实 NeoForge 运行时进入。但本轮没有测到明显的整体加速：优化临时缓冲后的按需列方案，完整区域平均约快 **0.85%**，按区域配对平均约快 **0.87%**；仅使用几何预设基本没有收益。这不足以作为大幅加载优化发布。

本轮原型全部位于隔离实验副本。没有修改生产 Java/Rust、正式原生库和发布 JAR，也没有降低装饰量、距离或精度。

## 实际实现与边界

本次验证 [装饰解耦审查](decoration-decoupling-audit-20261102.md) 中的盘形模块，不等于已经实现全部装饰的通用编译框架。

- 从资源加载半径 2–6 的五张圆盘偏移表，保持原版 X/Z 遍历顺序。
- 继续使用真实配置的半径随机采样、目标方块谓词、状态提供器、纵向扫描和 `setBlock`。继承原版 `DiskFeature.placeColumn`，保留砂岩条件、草盘邻居条件及后处理调用。
- `templates` 只替换几何枚举；`pages` 将原有 4×4 页依赖去重后每批最多 64 点；`compact` 只提前请求圆盘真正覆盖且本地未缓存的列。
- 写入仍按原 Feature、候选、圆盘列和纵向顺序进行；查询当前方块时仍叠加之前的编辑。没有对静态快照无序回写。
- Rust 使用与正式库相同的 DLL。Java 批量入口复用正式 `surfacePoints`，保持精确与显示地表分离。
- 第二轮将批量准备缓冲改为线程复用，去掉每个候选的大数组、重复页标记分配及分批数组复制。

没有加入提前群系拒绝、原生群系替换、盘形以外的新内核或多线程装饰调度。实验不借用基线生成结果跳过候选。

## 完整测试路径

运行于实际 NeoForge 21.1.234 / Minecraft 1.21.1，Java 21.0.6、Windows x86_64、原版主世界种子 42。每区域 16×16 目标区块，18×18=324 个装饰来源区块，显示间距 4，单生成线程。

计时覆盖初始显示地形、所有原有装饰和结构、候选筛选、Java/Rust 编辑衔接、装饰整理，以及最终 Voxy 输入列和包围盒构造。没有只对圆形枚举或一个孤立 Feature 做计时。

世界配置解码、上下文建立、资源加载、正确性 fixture 和结果摘要在计时之外；没有运行 Voxy 网格、GPU 上传与绘制、磁盘读取、网络或加载排队。本报告测量完整的预测数据生成链路，不能宣称已经验收实际游戏帧时间或全部加载链路。

每模式两片预热、五片正式区域。第一轮模式顺序为 `baseline,baseline_repeat,templates,pages,compact,baseline_tail`，共 42 片；缓冲复用后反向安排为 `baseline,compact,pages,templates,baseline_repeat,baseline_tail`，另 42 片。每轮内部使用相同五个区域，不是每模式都新增五个独立地区。

实验副本固定原来用于原生 shuffle 的外部熵，使各模式可比较。每个 Java Feature 执行后还读取一个校验随机数；下个 Feature 原本就重新设种，因此该读取不改变后续生成。各模式完整输出摘要还与之前正式 DLL 实验的相同七片区域逐一比较。

## 实际命中情况

三种候选模式每区域平均 **773.2 次**进入新模块、产生 **7317.2 次**方块写入，与同一轮放置探针记录的通过群系候选数及写入数逐项一致。正式输入中命中的是沙、黏土、沙砾盘；草盘和冰块斑在这些区域没有通过到终端，不能据此宣称它们的实际区域收益已经验收。

`pages` 每区域平均 **587.8 次**触发原生环境批量调用，`compact` 为 **622.6 次**；没有因不支持、环境模式或越界而回退。批量边界是最多 64 个坐标；这些都是从真实候选进入的调用，不是单独强制调用新模块产生的计数。

另外每轮运行 **360 个**正确性 fixture：真实解码注册表中的五种盘、正负坐标、区块边缘、四种随机种子、三种环境、三种模式；每个案例连续放置两次。环境包括可替换地面、空气空洞、水体、障碍，以及完全不可替换地面。fixture 只用于补充正确性，不能充当自然命中或性能证据。

两轮共 **84 片完整区域、720 个 fixture** 全部匹配，包括装饰完整坐标/BlockState、地形列/群系、Voxy 包围盒，以及 Java 随机状态延续。fixture 还对比待同步编辑的顺序。所有原始记录均无 oracle 跳过。

## 完整耗时

下面采用第二轮已复用缓冲的结果。对照为两次末尾未改动基线的均值，重复基线本身平均相差约 0.5%，各区域差异为 0.12%–1.06%。第一轮初始基线有额外预热影响，未用它单独计算候选收益。

| 路径 | 完整生成 ms/区域 | 装饰 ms/区域 | 完整精确请求点/区域 | Java 线程分配 MiB/区域 |
| --- | ---: | ---: | ---: | ---: |
| 重复基线均值 | 3688.56 | 3428.21 | 85916.8 | 519.11 |
| 仅预设几何 | 3692.48 | 3432.37 | 85916.8 | 519.06 |
| 预设 + 原有整页批量准备 | 3704.90 | 3446.32 | 85916.8 | 519.08 |
| 预设 + 按圆盘覆盖列批量准备 | 3657.14 | 3392.01 | 85377.6 | 518.99 |

按均值相除，三个候选分别为约 **慢 0.11%、慢 0.44%、快 0.85%**；按区域先配对再平均，则分别为慢 0.08%、慢 0.36%、快 0.87%。按需列方案相对两次对照的配对平均收益分别为 **1.11% / 0.62%**，五片相对合并对照为 1.51%、1.32%、0.74%、0.32%、0.46%。这些结果只支持小幅变化，不构成跨种子、跨模组的稳定收益保证。

第一轮未复用缓冲时，整页和按需方案分别比对照慢约 4.98% 和 5.26%。去掉每候选临时数组后，分配回到约 519 MiB/区域，整体回退消失。本轮不把第一轮回退泛化成所有批处理都慢，也不把第二轮约 0.9% 放大成明显加载提升。

## 为什么局部快了，整体仍几乎不变

第二轮按需方案的全部盘形条目归因时间从对照约 **679.90 ms 降到 519.37 ms**，局部减少 **160.53 ms（约 23.6%）**；但完整区域只减少 **31.43 ms**，所有条目合计的 Java 精确查询时间仅从 **1737.25 ms 降到 1712.15 ms**，约少 25.10 ms。

精确请求点只减少 **539.2 点，即 0.628%**。圆盘不再预取的部分，稍后的其他装饰仍会访问；成本会转移到后面的条目。仅看盘形函数的下降，会把这个转移当成整体省下的工作。

另外，最贵的盘形条目还包含进入终端前的高度和群系过滤。模块只在终端才知道采样半径与完整形状，无法自动省掉先前候选筛选发生的成本。

## 已经算过的噪声为什么还有查询

另运行一组独立复用诊断：两片预热、五片正式区域，额外记录精确 quart 坐标集合；这组带诊断的耗时不参与收益表。

| Java 路径计数 | 平均每区域 |
| --- | ---: |
| 到共享群系入口的 quart 请求 | 132486.0 |
| 不同 quart 坐标 | 125262.6 |
| 真正进入 `BiomeSource` 的计算 | 125262.6 |
| 底层计算所涉及的不同坐标 | 125262.6 |
| 请求中已被缓存覆盖的数量 | 7223.4 |
| 送往 Rust 的完整精确地表点 | 85916.8 |
| 上述地表点在区域内重复坐标 | 0 |

这证明所测区域内，Java 底层群系接口没有重复计算相同 quart 坐标；相同请求的缓存复用已经生效。这里计数从部分局部缓存之后开始，不能用 7223.4 除以全部装饰查询来推断整个系统缓存命中率。

它也不能证明底层密度节点、噪声角点或 Java/Rust 之间不存在重复工作：本探针统计的是接口坐标，不是每个内部数值运算。

源码上有三项区别：

1. 初始显示网格是间距 4 的结果；装饰会访问新的逐格精确位置和材质，不能直接用显示近似替换。
2. 地表颜色位置的群系，不代表任意高度的洞穴群系。`BiomeManager` 的方块群系选择还保留自己的坐标扰动语义。
3. Rust 地形与 Java 装饰的原始 `BiomeSource` 有各自的工作区和缓存。目前没有把任意 Java 群系调用统一改为 Rust 答案，之前已经测出过群系不一致。已有噪声/气候数值复用是局部依赖复用，不是所有原生计算结果都同步给 Java。

后续若做更大优化，需要进一步证明可共用的精确输入/中间值及结果一致性，或者减少真正需要计算的环境范围。再加一层同坐标答案缓存，覆盖不到本轮已经去重后的大部分新位置。

## 保留与复现

准备工具：`tools/performance/decoration-modules/prepare.py`；验证工具：同目录 `summarize.py`。原型辅助类只复制进隔离副本。实验 Gradle 配置仅增加实验资源和可选复用诊断参数，生产构建不使用。

第二轮完整原始证据位于 `build/decoration-modules-20261102-reuse/`：`results.json`、`module-summary.json`、`module-costs-*.json`、`feature-costs-*.json`、`module-fixtures.json`、`input-manifest.json`、`module-manifest.json`、`launch.log`。第一轮位于 `build/decoration-modules-20261102-formal/`，复用诊断位于 `build/decoration-modules-20261102-trace/`。

长期结果保存在 `tools/performance/decoration-modules/results-20261102.json`，包含逐片记录、模块计数、对照汇总、复用诊断、fixture 汇总与证据文件摘要。

```powershell
python tools/performance/decoration-modules/prepare.py build/decoration-modules-new
```

然后以 Java 21 运行 `tools/performance/decoration-experiment/experiment.gradle`，指定独立的 `--project-cache-dir`、`vssExperimentRoot`，五轮正式、两轮预热、side=16。模式选择 `baseline,compact,pages,templates,baseline_repeat,baseline_tail`。结束后运行：

```powershell
python tools/performance/decoration-modules/summarize.py build/decoration-modules-new
```

检查完成标记、无失败文件、输出与随机状态全部匹配，并要求模块调用与通过群系候选、写入探针一致，批量方案必须确实进入批量调用。诊断另开新目录，设 `vssExperimentReuseTrace=true`，仅运行 baseline；该诊断跳过 fixture，不能把它的计时混入性能对照。

第一轮最初启动因实验资源白名单未包含新 JSON，在测量前失败；修正实验资源配置后重跑，成功记录保存在 `launch-retry.log` 对应的 smoke 目录。未将“Gradle 成功退出”当作生成成功，后续均检查了运行时完成标记。

结束时核对两轮实验对应的 472 个生产 Java 文件和 18 个生产资源文件，全部保持原校验值；已加载的实验输出资源与正式 DLL 也逐项核对。没有向生产源码保留实验开关或为本方案打包。
