# Meridian 0.1.8 可借鉴算法：VSS 离线性能与正确性测试

> 历史记录：保留当时的实现、输入与验证结果，不能据此判断当前版本的渲染架构、配置或兼容范围。 当前说明见 [文档目录](../../README.md)，相关旧报告见 [历史索引](../README.md)。

日期：2026-10-16。对应“先对这几项做性能分析和测试”。本轮完成两个平台的实验，新增独立工具和证据，未改生产实现、构建发布 JAR 或替换客户端。

**最明确的后续方向是减少边缘不变时的接缝重算，并给现有预算补充构建成本统计。需求阈值能够减少目标数量，但改变画质且存在切换成本。紧凑编码省空间，却增加编码／解码成本；双遍光栅遮挡没有取得全面优于直接绘制的结果；二值树冠仍有明显质量问题。**

前一轮源码依据见 [算法审查](meridian-018-algorithm-audit-20261016.md) 与 [采样和边界审查](meridian-018-boundary-audit-20261016.md)。本报告没有用 Meridian 自身的游戏 FPS 或 DLL 数值速度作为 VSS 的对照。

## 范围和测量方法

- NeoForge 冻结 454 个生产 Java 文件，JDK 21.0.6；Forge 冻结 455 个，JDK 17.0.12。最终校验冻结文件未变，当前生产 Java 与各自冻结副本也一致。
- CPU 为 Ryzen 7 7700，显卡 RTX 4070 Ti SUPER，OpenGL 4.6，NVIDIA 572.70。测试在同一台机器顺序执行，没有同时运行两个基准。
- 每个平台通过 **12 项 JUnit 检查，0 失败、0 跳过**：7 项 CPU、1 项实际 planner 需求测试、2 项基础 GPU、1 项森林 GPU、1 项原生批次。总计 24 项。JUnit 成功表示实验执行和所断言的正确性通过，不表示每个候选有净收益或树冠画质已获接受。
- 六份森林几何来自历史客户端捕获；真实叶面纹理、源面顺序和属性保留。CPU 边界、接缝、构建、水面排序及二维树木块集属于合成工作负载，GPU 双遍遮挡使用程序化几何。它们都不等于当前存档的整帧负载。
- CPU CSV 中的 `cpu_ns` 是被测方法的**主机墙钟区间**，不是线程 CPU 计时；`allocated_bytes` 是 ThreadMXBean 累计 Java 分配量，不是峰值存活内存、进程 RSS、native 工作区或显存。
- GPU 记录使用 `GL_TIME_ELAPSED`，模式交替，包含测试路径的派发／绘制。CPU 准备与 GPU 工作会重叠，不能相加换算 FPS。本机结果具有约微秒级离散，个别 1–2 微秒差异不宜解读为稳定产品收益。
- Java 生产输入在测试前冻结；资源和少量测试引导／Voxy stub 使用仓库文件，汇总时记录其哈希。该限制已写入验证清单。所有原型都在实验 source set 中，正常发布 source set 不包含它们。

所有下述主要数字为中位数。完整组的样本数、P95、最小及最大值在 `tools/prediction/meridian-algorithms-20261016/summary.json`（历史本地输出，不随源码分发），原始 CSV、108 张森林 PNG／平台及 JUnit XML 在实验目录 `results/neoforge` 和 `results/forge`。

## 1. 边缘去噪和接缝版本失效

独立边界候选由 VSS 自己的 `PredictionMeshBuilder` 副本修改：只把去噪循环的上界从 `gridSize - 1` 改到 `gridSize - 2`，保护裁剪后正式格子的东／南外圈。没有复制 Meridian 的反编译实现。

用例覆盖间距 1／2／4／8、普通／已捕获／surface-only 三种标记、东／南方向。当前实现会在间距 2／4 把外圈孤立高度 96 改成 64；候选保留 96，内部对应高度处理相同，保护标记保持有效。这里验证的是具体后处理差异，尚未验证完整相邻地块、不同 LOD、河岸／洞穴／结构／Voxy 动态交接。

| 去噪耗时 | NeoForge 当前 → 候选 | Forge 当前 → 候选 |
| --- | ---: | ---: |
| 间距 2 | 0.1234 → 0.1181 ms | 0.1191 → 0.1160 ms |
| 间距 4 | 0.1245 → 0.1196 ms | 0.1179 → 0.1143 ms |

最终运行中，少遍历一圈约省 3–5 µs，量级很小，独立类的 JIT 热度也会影响这种微基准。**这没有证明总接缝或帧时改善**，不能据此删除动态接缝。它的价值首先是验证源边缘一致性。

另用 4×4 个地块、交错高度 64／80 的接缝场景，保持网格、采样、边缘和 mask 完全相同，只建立新的瓦片对象／revision，调用实际 `PredictionLodSeams.apply`。41 轮、16 次预热，最终 patch 与完整重建逐字一致。

| 接缝更新 | NeoForge | Forge |
| --- | ---: | ---: |
| 无变化 delta | 0.0009 ms，32 B | 0.0011 ms，32 B |
| 新版本、相同边缘 | **1.4627 ms，733,040 B** | **1.4596 ms，733,056 B** |

相同边缘的新版本仍重算中位 6 个 surface。它证实了可避免的重复工作，但**本轮没有实现安全跳过逻辑，也没有把两行之差当作可承诺的逐帧收益**。下一步应在现有版本体系里区分边段内容／邻接依赖变化与无关网格版本；覆盖、流体、父子交接、材质和形变等实际依赖变化仍须失效。边段签名应在构建／发布时形成，避免每帧重新扫描来判断“没变化”。

证据：`border-correctness.csv`、`border-timing.csv`、`seam-version-cost.csv`。

## 2. 构建成本反馈：有差异，尚不能据此降低内存预约

65×65、间距 2，调用实际 Java 网格构建；每类 12 次预热、31 次计量。下面是 NeoForge 数据：

| 合成地形 | 构建耗时 | 累计 Java 分配／次 |
| --- | ---: | ---: |
| 平地 | 0.765 ms | 1.84 MiB |
| 缓坡 | 1.669 ms | 4.03 MiB |
| 高度频繁变化 | 2.555 ms | 18.50 MiB |
| 带水面 | 2.629 ms | 7.04 MiB |

同样大小的输入，累计分配相差约十倍。因此按任务种类／输出量记录成本比统一平均值更有信息。这里没有执行噪声生成、完整植被、缓存恢复、native 工作区或进程峰值监测，**不能把这些数字当成 128 MiB 固定预约的替代值**。

48 个混合网格任务，2 次预热、7 次计量，交替 1／2／4 worker：

| Worker 数 | NeoForge 总墙钟 | Forge 总墙钟 |
| --- | ---: | ---: |
| 1 | 50.60 ms | 49.17 ms |
| 2 | 28.46 ms | 27.17 ms |
| 4 | 18.22 ms | 17.65 ms |

NeoForge worker 区间总和由 50.03 ms 增到 65.76 ms，说明更高并发并非零额外成本；区间里还含调度／GC 等等待。没有同时运行游戏渲染，不能据此选择客户端线程数。建议先将耗时、可计量工作区、输出和待上传积压纳入**现有**预约与预算诊断，再测高分位工作区及覆盖交付时间；不新增一套调度器。本实验不调整 `/vss chunky`。

证据：`build-calibration.csv`、`build-concurrency.csv`。

## 3. 压力下调整需求：有效，但不是无损优化

直接调用当前 `PredictionLodPlanner`，原屏幕阈值 128，候选分别放宽为 256／512。保留视距、树木和 stored-detail 设置，测试 4K／16K／65K 视距、负坐标、望远镜及有方向视锥的场景。

| 场景 | 原阈值目标瓦片 | 2 倍阈值 | 4 倍阈值 |
| --- | ---: | ---: | ---: |
| 4,096 方块，无方向视锥 | 1,268 | 596 | 452 |
| 16,384 方块，无方向视锥 | 1,254 | 840 | 546 |
| 65,536 方块，无方向视锥 | 1,254 | 1,104 | 642 |
| 16,384 方块，负坐标 | 1,254 | 882 | 552 |
| 16,384 方块，望远镜 | 2,334 | 996 | 717 |
| 16,384 方块，有方向视锥 | 1,329 | 1,230 | 1,047 |

两个平台返回数量一致。所有场景的地平线圆内抽查点没有丢失 owner，也没有在同一检查点出现父子双 owner；恢复原阈值后得到原来的完整有序列表。它只验证选择器的空间覆盖，不是动态 GPU 交接无缝的证明。

重要限制：

- 不能只报无方向视锥的 33.0% 减量；有方向视锥场景的 2 倍阈值仅减少 **7.45%**。实际客户端还取决于 Voxy 覆盖、视角、现有内容及 planner 的分层／数量上限。
- 在相机周围 ±256 方块的 17×17 探针中，无方向视锥的 4 倍阈值使 65／289 个点比原来更粗；负坐标场景为 33／289。测试中的望远镜中心探针没有变粗。必须有明确近处及焦点保护，不能默认全局乘 4。
- 16K 无方向视锥的 2 倍阈值会新增 138 个 key、撤销 552 个；有方向视锥场景会新增 369 个、撤销 468 个。频繁改变阈值可能制造构建／上传／接缝抖动，不能仅看最终数量。
- 目标更少不代表 planner 自身更快。有方向视锥时，NeoForge 中位区间从 1.536 ms 增到 2.038 ms，Forge 从 1.544 ms 增到 2.558 ms；该候选的主要潜在收益是后续需求减少。

这轮没有实现压力控制器、滞回、GPU 回收或加载 A/B，也没有测显存变化。若继续，应作为可选自适应画质研究，复用现有 desired 集合、保留旧粗覆盖与事务交接，按持续压力低频调整，并限制恢复速度。

证据：`demand-pressure.csv`。

## 4. 无损属性压缩：节省约 19.8%，解码并不更快

先测“把 flags 和 cell／颜色索引组成一对再建字典”，六份捕获网格的属性组合都过多，无法取得净节省，已保留在 `rejected-pair-dictionary`，不作为成功结果。

后测 VSS 独立原型：保留 3 个精确坐标 word，使用 1 个 word 打包 flags 字典索引、实际 cell 位数和颜色索引位数，附 flags 字典及原始颜色／异常面尾部；总位数或总长度不划算时回退。

| 捕获网格 | 当前完整上传数据 | 候选数据 |
| --- | ---: | ---: |
| 1511 | 1,103,040 B | 883,928 B |
| 739 | 986,736 B | 791,380 B |
| 732 | 608,032 B | 487,280 B |
| 1476 | 601,200 B | 481,992 B |
| 2001 | 386,816 B | 312,204 B |
| 359 | 183,744 B | 147,400 B |
| **六份合计** | **3,869,568 B** | **3,104,184 B（少 19.78%）** |

全量 CPU 往返逐字一致，包含原尾部、虚拟回退地址；补测零属性位宽、32 位边界、超位宽、过多 flags 和不支持原格式的回退。六份真实网格都执行了两种 GPU 读法，逐记录 checksum 一致，没有因“不符合格式”而跳过整个测试。

代价也明确：NeoForge 六份编码区间中位数之和从 6.395 ms 增到 8.320 ms，Forge 从 5.763 ms 增到 7.642 ms。这是六个独立组件计时的加总，不是游戏一帧。额外分配约等于多一份候选输出。

GPU 使用独立重复读／重建属性的 compute kernel，候选从约 5.1–7.2 µs 增到 6.1–8.2 µs；不是完整顶点、材质、morph 和片元 shader 集成。**压缩收益已验证，FPS 收益未验证，默认启用依据不足。** 六份选样不能代表所有地形，也不能把 19.8% 直接外推为总显存节省比例。

证据：`attribute-encoding.csv`、`attribute-read-gpu.csv`。

## 5. 植被缓存和粗树冠：缓存已有，二值代理仍不接受

64 棵合成橡树、6,976 个方块，比较当前 VSS 的整块合并、已有缓存命中、局部失效后重建，输出块集合一致，完整块集合比较放在计时之外：

| 已有路径 | NeoForge | Forge |
| --- | ---: | ---: |
| 直接合并 | 1.744 ms | 1.463 ms |
| 缓存命中 | 0.0175 ms | 0.0146 ms |
| 失效后重建 | 1.785 ms | 1.425 ms |

这是现有缓存能力的验证，不能再当成新优化收益。没有把完整世界生成中的树种模板模拟替换掉，也没有实现新的 GPU 树实例库。

另外用六份历史森林数据重跑 2／4 方块二值树冠代理。源叶面和所有代理都使用一致的 CUTOUT 标志、真实叶纹理及当前生产提交／着色器，避免旧输入中源面与代理材质不一致。对每种表示，6 网格 × 3 距离 × 2 朝向 × 3 表示，共 108 对直绘／MDI 颜色和深度一致检查通过。**不同表示之间允许近似，另行统计质量，不能把上述一致检查当成代理画质合格。**

| 满足距离保护的视角 | 按源像素加权 IoU | 新增覆盖／源覆盖 | 丢失覆盖／源覆盖 |
| --- | ---: | ---: | ---: |
| 2 方块代理，1,024 方块远 | 0.820 | **21.98%** | 0% |
| 2 方块代理，4,096 方块远 | 0.799 | 25.14% | 0% |
| 4 方块代理，4,096 方块远 | 0.651 | **53.71%** | 0% |

主要问题是填实树叶孔隙。4,096 方块处所有源图合计仅 175 个覆盖像素，单像素很敏感；1,024 方块处共 2,903 个源覆盖像素，也有明确的填充。4 方块代理在 1,024 方块处超过位移门槛，其性能数字不能作为可启用收益。

GPU 确实有减量，但有反例：NeoForge 在 1,024 方块、强制 Hi-Z 时，2 方块代理各样本的 GPU 区间约从快 20.5% 到慢 14.6%；4,096 方块处约快 4.0%–25.6%。Forge 也出现近处变慢、远处无收益的样本。小离屏负载、不同网格间 GPU 时钟波动、极少像素都限制了外推能力。

历史图像：同一裁剪范围，左为源几何，右为两方块代理，使用最近邻放大六倍。原文件为 `tools/prediction/meridian-algorithms-20261016/forest-canopy-comparison.png`（本地输出，不随源码分发）。

**当前二值粗树冠继续保留为反例，不进入默认画面。** 若研究下一版，需要同源体积、覆盖率和多视角轮廓约束。树种模板缓存只可能改善生成／重建，不能用来承诺树出现后持续低帧得到修复。

证据：`vegetation-reuse.csv`、`engine-forest.csv`、`engine-forest-quality.csv`、`forest-*.png`。

## 6. 双遍光栅包围盒与当前 Hi-Z

独立实现“历史可见先画 → 当前深度光栅化 box／atomic 标记 → 补画”，与实际 `PredictionOcclusionCuller` 及直接 MDI 比较。统一 2,048 条命令，每条 64 个四边形，512² 目标。24 次预热、61 次计量，三路径交替。

下面为 NeoForge 的完整被测 GPU 区间，单位 µs：

| 程序化场景 | 直接绘制 | 当前 Hi-Z 原语＋绘制 | 双遍 box 原型＋绘制 |
| --- | ---: | ---: | ---: |
| 开阔 | **27.648** | 48.128 | 39.936 |
| 前景遮住 75% 屏幕 | 27.648 | 41.984 | **24.576** |
| 镂空表面 | **27.648** | 48.128 | 40.960 |
| 连续转向 | **28.672** | 53.248 | 45.056 |
| 90° 视角突变 | **28.672** | 50.176 | 44.032 |

Forge 得到相同方向的结果。box 在这些场景均比该 Hi-Z 测试路径省时，但除了强遮挡场景，直接绘制更快；强遮挡相对直接绘制也只省约 3 µs。当前工作量下，省下的几何未必能抵消测试成本。

每场景取 3 个计量帧，两个剔除路径各与直接绘制比较，共 **30 对颜色及深度，逐项无差异／平台**。这只覆盖选取的有限帧，不能证明所有相机／包围盒条件均安全。

范围限制：Hi-Z 路径使用一次实际 pyramid 重建与过滤；没有复现完整 renderer 中跨提交共享、直绘选择策略和有限阶段重建。box 有自己的第一阶段深度与历史可见状态，两者比较的是这个独立完整区间；不是只比较一条 dispatch。没有接入真实森林 scene、Iris、水面、morph、Voxy 归属、近裁面专项及资源生命周期。

**结论是保留为替代路径研究，不替换生产 Hi-Z。** 更合适的下一次 GPU 实验应使用真实工作量的重复森林／山体 scene，并与已有直绘选择一起评估；不能仅因 box 胜过这个 Hi-Z 原语组合就宣称游戏会涨帧。

证据：`occlusion-gpu.csv`、`occlusion-quality.csv`。

## 7. 水面排序：顺序变化稀少时有小收益

1,028 个合成瓦片中心，256 帧轨迹，比较每次完整稳定排序与“先检查相邻顺序，只在逆序时调用原排序”。距离计算和比较方式与当前瓦片排序一致，没有按显存页改排序。128 帧额外等距离／重复距离／成员交换用例逐帧比较完全相同，普通计时轨迹的最终列表也一致。

NeoForge 中位区间：

| 轨迹，256 帧总量 | 原完整排序 | 先检查再排序 | 实际调用排序 |
| --- | ---: | ---: | ---: |
| 极慢移动 | 0.6912 ms | 0.3804 ms | 256 → 19 |
| 步行 | 0.9700 ms | 1.0248 ms | 256 → 255 |
| 来回远移 | 9.3216 ms | 9.3144 ms | 256 → 256 |
| 周期交换成员 | 0.6899 ms | 0.3787 ms | 256 → 32 |

极慢移动只省约 **1.21 µs／帧**，不是每帧省 0.31 ms。Forge 同样在步行时略慢。静止控制也有明显组件差异，但生产本来就有相机不变时跳过排序的条件，不能将它计为新收益。

测试没有串接 renderer 的成员／版本、静态提交计划重放和透明合成，因此尚未量化“顺序不变时不传播 revision”可能带来的下游收益。后续若继续，应优先测实际 revision 重建量，而非直接再加异步排序系统；顺序经常改变时需要避免无条件先扫一遍。

证据：`water-sort.csv`。

## 8. 原生批次：当前 64 列已吃到主要批处理收益

使用两个仓库当前自带 DLL（哈希相同），从仓库原版 worldgen fixture 组装固定文档。种子 0／917、间距 1／4／64，每组 256 列，相同顺序、相同输入。对 surface／display 两条 API 比较每次 1／8／64 列，独立 world、32 个异地预热列，交替批大小，每组 5 次正式计量。

每个平台得到 180 条正式计量；surface 全输出逐字一致，display 在这些输入上与 64 列的输出差异也均为零。没有把不同采样质量的 API 互相比成“提速”。DLL SHA256：`03447c3f2ad8ef552a1449bb81c1d69c1e04de8e682fe9d91360afaa607b97d5`。

NeoForge display 的 JNI 总区间：

| 种子／间距，256 列 | 每批 1 列 | 每批 8 列 | 每批 64 列 |
| --- | ---: | ---: | ---: |
| 0／1 | 7.342 ms | 5.505 ms | 5.369 ms |
| 0／4 | 36.650 ms | 34.848 ms | 34.277 ms |
| 0／64 | 47.007 ms | 46.351 ms | 46.550 ms |
| 917／1 | 5.193 ms | 2.591 ms | 2.424 ms |
| 917／4 | 15.430 ms | 14.660 ms | 14.457 ms |
| 917／64 | 26.933 ms | 26.668 ms | 24.866 ms |

64 相对 8 的收益约 -0.4% 到 6.8%；Forge 约 -2.9% 到 6.8%，跨运行波动足以影响小差异。种子 0、间距 64 时，一轮里的最长单次 JNI 区间中位数从约 2.58 ms 增到 14.36 ms。它不是取消延迟；native 自己也能在列边界取消，本轮没有直接测取消响应。

现有 VSS 运行路径已经最多用 8×8＝64 列，并跳过缓存命中，因此不能把 1→64 的收益再次认领。当前 native ABI 入口明确只接受最多 64 列；本轮没有改 ABI、测试整块更大批次或跨任务合批。现有结果不支持把“减少 JNI 次数”作为优先改造目标。

证据：`native-batch.csv`、`inputs/native-overworld.json`、`inputs/vss_native_core.dll`。

## 后续实施建议

1. **优先验证边段一致性和接缝依赖版本。** 已定位到相同边缘重复更新的成本；先补真实邻块／不同 LOD 回归，再将不相关版本变化隔离。源边段变化时仍及时更新，不能通过延迟正确更新换分数。
2. **在现有预算内增加成本反馈。** 当前试验支持“任务成本不同”，未支持降低固定预约；下一步测真实任务高分位工作区、待上传字节、交付延迟与渲染帧时，不重复新增预算层。
3. **自适应需求只按可选画质功能研究。** 2 倍是值得继续的实验点，不是已经选定默认值。补近处保护、滞回和恢复预算，测动态切换净成本；不能把目标数量直接换算显存。
4. **压缩以存储收益立项，完整 shader 集成后再选默认。** 当前 decode kernel 和编码 CPU 都变慢，保留不划算时回退；不因名义 16 B 就默认更快。
5. **暂不启用二值树冠，不替换 Hi-Z，不扩大 native 批次。** 三者各有未解决质量、净收益或接口问题。水面只在实际下游重建计数证明值得时继续。

这些是本轮证据支持的优先级，生产优化尚未实施，没有修复后 FPS、实际显存下降或游戏长帧改善的承诺。
