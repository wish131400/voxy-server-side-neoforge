**VSS 缩小后无法恢复粗显示：Spark 分析、修复与收益验证（2026-10-12）**

已找到并修复一处明确缺陷：新细化网格保留的 morph 数据被当成永久进行中的过渡，导致地形和植被无法恢复屏幕像素 LOD。修复后，真正处于过渡的网格继续保留原范围；过渡结束、投影缩小时，可以重新选择已有安全粗表示，实际缩短 MDI 范围。另修复了残留望远镜瓦片让无关区域整体进入昂贵归属计算的问题。两个仓库已同步，组件 A/B 正收益，完成打包。

细网格仍可缓存供下次放大使用。普通父子归属仍优先保留最佳可用覆盖；本轮没有改成按距离任意换粗父瓦片。无安全粗变体、近处、接缝或混合归属仍保守使用完整几何，所以不能承诺所有区域都会在缩小后恢复同一面数，更不能把减少提交量等同于立即释放显存。

**缩小后为何继续保持细节，以及本轮修复**

上一轮已经让实际投影参与屏幕误差和提交范围选择，但测试主要覆盖已有 payload 的缩放，遗漏了新细化网格长期保留 morph 的路径。

1. `PredictionMorph` 的动画持续约 350 ms。动画结束后，morph 数组仍留在网格里用于上传、缓存与顶点数据；“有这个数组”并不代表“动画还在播放”。
2. 原 `PreparedPass` 只要发现 `packed.morph()!=null` 就强制源细节，植被也受同一永久条件限制；`PredictionPackedMesh.drawRanges` 再次因为这个字段非空禁止使用地形显示变体。缩小恢复了像素比例，仍无法选中粗范围。
3. 单纯换成时间检查还不够：镜头、投影和网格不变时缓存可能一直复用，错过动画到期。现在记录最早过渡截止时间，到期刷新一次，随后恢复快速缓存路径。
4. 细化归属的普通瓦片快路径原来检查整个 snapshot 是否含任何 scoped tile。一块已生成的望远镜瓦片就让世界其他地方的普通瓦片也逐 chunk 计算。现在利用已有父子 family 索引，只让实际受影响区域继续走精确路径。

生产改动只有 `PredictionRenderer.java`、`PredictionGpuTile.java`、`PredictionPackedMesh.java` 三个文件。本轮基线是已有未提交优化的工作树，不是 Git HEAD。归档保存两平台起始文件和各自的 `production.patch`；Forge 的事件 API、矩阵栈、Java 17 等差异均保留。

新增诊断会在定期 debug 中输出 opaque/water 的 `passCache`：`sourceCandidates`、`terrainCandidates`、`displayCandidates`、`afterVoxy`、距离带、保留 morph 数量、活跃 morph 数量、到期刷新次数、混合归属和无地形粗变体数量。它们可以区分“缩小仍被保护”“已经减少范围”和“后台仍在增加源网格”。

**剩余瓶颈与实机核对**

本轮保留了有明确正收益的显示恢复和局部归属快路径；没有重推此前无收益的持久映射回读实验。可见性回读 3.40%、大量直绘及几何页切换、上传与接缝刷新、受保护驻留仍需后续单独衡量。不能直接强迫所有回退范围走 MDI，也不能直接删掉细网格或保护覆盖。

用户自行换包后，同位置、同朝向按“普通视野 → 放大等待细化完成 → 缩小并静止一秒 → 再放大”核对。缩小时应观察 passCache 的源面与显示面分离，活跃 morph 到期后退出，MDI/direct 候选面相应变化；再放大恢复需要的细范围。若无地形粗变体或混合归属数量很高，仍会保留部分完整网格，这可以用新增诊断继续定位。

这次没有在换包后的真实存档采集新 FPS，因此组件 GPU 和归属 CPU 的大幅下降不能换算为固定 FPS 提升或最差帧改善幅度。
