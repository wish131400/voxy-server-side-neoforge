## 已确认的问题

### 1. 细节名额在任务已经启动、读取缓存和预约内存后才检查

初次管理器快照中，线程池累计完成 103754 个任务，`noDetailSlot=76616`。这项计数表示任务启动后发现没有细节名额而退出，不是成功构建数量。另有 CPU 拒绝计数包含入队前检查，不能与线程池完成数直接相除。

旧路径先预约 CPU、发布任务、由工作线程取得 CPU 和内存并读取缓存，然后才检查细节/植被名额。名额不足会退出、清掉 pending，后续调度再次发布相同任务。

改为在入队前预约细节/地表名额。名额随任务保留，完成、队列取消、优先级重新插入、暂停、关闭和执行器拒绝均通过同一个幂等释放对象处理。删除工作线程内原来的两段名额争抢代码。首次覆盖和成品缓存恢复继续使用原有通道，CPU 和内存的最终安全检查仍执行。

### 2. 相同目标的周期计划被当作全新的需求发布

旧实现每次接受计划都重新发布列表，重置 `foregroundWorkPending`、预览状态和加载进度，并要求重做视野需求。即使计划成员、归属、细节档位和地表目标完全一致，下游异步加载结果也会因列表身份改变被拒绝。

初次快照为 `loadingJobs=16195`、`loadingCommits=2485`、`loadingDiscards=13709`，另有一项仍在途；约 84.6% 已请求结果被丢弃。这包含居民网格、上传和视角等合法变化导致的丢弃，不能全部算作相同计划问题。

现在比较实际计划成员、叶子、归属、地表范围、各档细节目标和 medium 前沿。相同目标保留原发布身份和已有完成状态；实际目标改变仍发布新状态。成员顺序的无意义变化也不会重置计划。

### 3. 无内存压力时也遍历和排序全部驻留瓦片

现场在约 7100 个驻留瓦片、约 1800 个计划目标、没有构建任务运行时，仍持续提交计划和调度任务。调度器每次为全部居民建立回收列表、检查祖先覆盖并排序，后续内存预算通常并不使用结果。

JFR 的后台规划线程有 440 个执行样本，其中 245 个包含 `PredictionSchedulePreparation.build`；回收排序和相关比较器在调用栈中出现。这是抽样分布，不能解释为精确时间占比。

现在由不可变调度输入携带当时是否存在内存回收需求。没有需求时跳过整个回收扫描和排序；有压力时仍生成候选，执行回收前继续验证当前预算、居民版本和祖先覆盖。若压力在快照之后才产生，后续正常调度刷新候选。

### 4. 大幅移动没有立即撤销旧需求

旧实现需要等待正常的每 5 tick 刷新，快速移动时每 10 tick，才能请求新坐标计划；在新计划接管前，旧位置还可能被当前 desired 集合或宽限期视为仍需计算。

现在相机单次水平或垂直移动超过 128 方块时，立即撤销旧位置的未开始任务、旧预备候选和规划结果，清除旧需求宽限期，并请求当前坐标计划。已生成居民网格保留；运行中的生成在现有阶段检查点判断是否仍被需要。单独的导航代数避免旧任务因传送取消后被错误记为 30 秒生成失败；传送不改变地形内容版本。

这里没有强行中断本机调用中的原生计算，因此已经进入原生调用的任务仍需到检查点才能让出工作线程。

## 复现与回归

最初四个新增用例在改动前全部失败，原始 XML 保存在 `before-results/`。修复后的六个用例覆盖：

1. 相同计划保持加载完成状态，允许已经计算的加载结果提交。
2. 无压力时不建立回收候选，有压力时仍有安全候选。
3. 40 次名额不足的重复请求不进入执行器；旧细节仍被阻塞时，新的首次粗覆盖可以发布；名额释放后可立即重试细节。
4. 传送在非周期 tick 立即请求当前坐标，取消旧需求并保留居民回退。
5. 重排队任务保留名额所有权，暂停会释放排队名额。
6. 执行器拒绝后释放细节和 CPU 预约。

## 仍需保留的判断边界

初次渲染快照统计到 GPU 几何 live 约 2.20 GiB、已提交几何页约 2.41 GiB，而软预算为 1 GiB；CPU 居民约 7284，当前计划约 1839。预算保护、粗级回退和植被交接会限制可直接回收的对象。该现象表明驻留仍有优化空间，本轮没有把软预算变为硬上限，也没有证明已解决全部显存占用。

本轮消除了四条有复现证据的加载/调度浪费。截图中的固定天空孔洞也可能涉及网格内容或真实像素交接；本轮未取得新包在该视角的连续游戏帧，不能宣称全部漏面已消失。
