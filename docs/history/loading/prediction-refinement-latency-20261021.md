## 修复内容

### 1. 让附近细节获得实际的调度机会

此前 `PredictionTileManager.workPriority` 和异步 `PredictionSchedulePreparation.Input.priority` 在遇到可见区域时，先进入屏幕误差优先级分支并返回，绕过后面的本地完成轮次。远方有较大屏幕误差时，本来用于穿插完成近处网格和地表内容的规则失效。

另外，轮次计数只统计首次跨过 32 网格，后续 32→64 等升级不计数；在只剩最终精度任务时，`previewWorkPending` 又可能提前关闭本地轮次。

修复将本地轮次判断移到通用可见优先级之前；所有实际提高网格精度的合格地形完成都会计数；达到原有 16 次轮次门槛后，让附近待完成任务插入。高速移动、望远镜、遮挡区域和必要覆盖仍沿用各自的约束。主线程最终准入与后台准备使用相同规则。

新增回归在旧代码上失败，在修复后通过，覆盖“远方屏幕误差大”“已满足本地轮次”“预览阶段结束后仍有最终细节”三种状态。

### 2. 保留旧树木时，只生成一次派生几何

此前地形升级先打包并生成完整显示 LOD，然后 `retainFeatures` 拼入旧树木、建筑等 feature，又重新执行合并、显示 LOD 和派生编码准备。第一套派生数据随即丢弃。

现在先在工作线程拼接新地形和需保留的完整 feature，再统一合并、生成显示档位及编码。旧的独立 `retainFeatures` 入口仍服务于已完成缓存的交接；正常新建路径直接使用组合打包入口。原始几何、颜色、UV、光照、来源单元映射、边界摘要、feature 完成状态和 morph 包围范围保持一致。

新增样例使用 64×64 区域、100 棵树，并比较旧双次加工与新单次加工。交替执行、预热后取 9 轮中位数，包含 GPU 存储准备及无损压缩。断言完整 canonical words、派生档位、四档绘制范围和边界摘要相同。耗时是工作线程的经过时间，不是整个世界的加载时间；后台其他进程会影响绝对值。

最终测量数值保存在本仓库 `build-refinement-latency-20261021/results/feature-compose-worker.csv`，对应 JUnit 标准输出中 `FEATURE_COMPOSE_AB` 一行。初次独立 NeoForge 对照为 23.819→15.764 ms、14.530→8.487 MiB 临时分配；Forge 初次对照为 22.288→14.648 ms、14.531→8.488 MiB。最终构建中的配对测量如下：

| 平台 | 旧双次加工中位数 | 新组合加工中位数 | 临时分配 |
| --- | ---: | ---: | ---: |
| NeoForge 1.21.1 | 31.289 ms | 19.414 ms | 14.528→8.486 MiB |
| Forge 1.20.1 | 23.382 ms | 15.155 ms | 14.531→8.488 MiB |

两个平台 CPU 回归有部分并行执行，绝对耗时存在机器负载差异；每组内部仍交替比较旧、新路径。临时分配减少约 42% 更稳定。这不代表游戏帧率提高相同比例。

### 3. 解除已覆盖区域中粗层升级的上传优先权

此前上传候选先判断同键 GPU 是否存在，再对所有候选统一按 LOD 从粗到细排序。这会把有父级回退的近处细化，继续排在远处粗层更新之后。

新的 `PredictionUploadSelection.order` 按实际上传完成的驻留覆盖排序：

1. 还没有可绘制覆盖的区域优先；同类中先上传较大的父级，建立基本覆盖。
2. 已有回退覆盖的更新按现有工作优先级和距离排序，允许附近细化及时上传。

新增回归使用真实驻留状态，验证顺序为“缺覆盖父级→缺覆盖子级→已有覆盖的近处细化→已有覆盖的远处升级”。上传的瓦片数、字节和时间预算未放宽。

### 4. 先接收已完成的交接，再引入下一份输入

此前 `finishBoundaries` 先读取新的原版地表边界并递增版本，然后才轮询后台结果。如果细化事务已经完成，但原版又发布了另一份边界快照，结果会被当作旧版本丢弃。画面继续保留粗地形，重新排一次边界任务。

现在在接收新上传、改变 Scene 地形记录、采纳下一份原版边界快照前，先尝试提交仍匹配当前版本的已完成结果。新的边界输入随后仍正常处理。未完成的交接继续使用旧几何；真实过期的版本仍被拒绝，没有通过超时强制提交。

新增 OpenGL 回归精确复现“细化已完成→无关远处原版边界更新→本帧准备”。修改前仍选择旧 GPU 网格，回归失败；修改后及时选择细化网格，同时继续处理新边界事务。旧地形等待期间的保留、完整 GPU mask 初始化、水面和细分覆盖也在相关回归中验证。

## 为什么后台解耦后仍然会发生

后台执行解决了大量计算直接压在客户端线程的问题，但任务仍有准入、优先级、重复加工、上传和原子交接等依赖。之前的实现留下了优先级分支覆盖及完成结果的接收顺序问题，不能仅凭“任务在线程池执行”判断可见进度已经解耦。

本次没有取消避免空洞、重复绘制和接缝闪烁所需的交接条件，也没有扩大线程池。CPU 负载继续决定生成准入；FPS 仍仅用于诊断，不用于限制预测加载。

## 验证与交付

两个仓库使用 `tools/prediction/refinement-latency-tests.gradle` 隔离构建输出。CPU 回归覆盖调度、渐进加载、CPU 租约、feature 交接、缓存恢复、压缩、父子覆盖和规划生命周期；OpenGL 回归覆盖边界提交、粗细交接、水面、MDI、植被和体素档位。`verifyModules` 继续作为必需检查。

最终结果均为零失败、零跳过：

| 检查组 | NeoForge 1.21.1 | Forge 1.20.1 |
| --- | ---: | ---: |
| 本次新增 CPU 回归 | 3 | 3 |
| 相关 CPU 回归 | 211 | 211 |
| OpenGL 回归 | 11 | 11 |
| 模块架构检查 | 11 | 11 |
| 模块生命周期回归 | 276 | 276 |
| 协议与列过滤回归 | 64 | 66 |

部分模块回归与专项回归覆盖相同测试，不将这些数字相加作为独立用例数。NeoForge 在最终修正测试驱动后，另单独重跑了 13 项渐进加载测试，全部通过。两个生产 JAR 均已构建并完成制品检查，Forge 已完成重混淆。

旧渐进加载测试中有几处仍假设同步规划，或假设一次受时间限制的准入调用一定填满窗口。修改前快照复现相同失败后，测试改为在截止时间内收集异步规划结果或重复泵送受限准入，再检查原有并发上限和最终完成断言。没有放宽生产准入，也没有删除这些断言。

交付产物目录为各自仓库的 `lib/refinement-latency-20261021`，构建标识 `refinement-latency-20261021`：

- NeoForge：`vss-0.3.5-neoforge-1.21.1.jar`
- Forge：`vss-0.3.5-forge-1.20.1.jar`（完成 reobf）
- `SHA256SUMS.txt`：最终 JAR 校验值。
- `verification.json`：每个验证任务的测试数、跳过和失败数，以及协议、类版本、原生资源和打包检查结果。

制品检查脚本为 `tools/prediction/refinement-latency-20261021/verify_artifact.py`。检查更新后的六个生产类、Java 21/17 类版本、协议、构建标识、原生资源一致性、Forge 的 LZ4 嵌套依赖和 reobf，并排除测试类及观察器。

仍需用新包在游戏内确认用户报告位置的首次细化时间和连续显示节奏。本次没有在运行的游戏中加载修复后的类，因此没有宣称“几分钟等待”已降到某个秒数，也没有给出修复后游戏 FPS。
