# Meridian 后续方案：成品网格缓存与跨地块绘制实验

> 阶段记录：正文中的实验范围、未提交状态和测试数字对应当时的工作节点。0.3.2 之后截至本次提交的最终功能与升级说明见 [更新日志](../CHANGELOG.md)。

日期：2026-09-22。范围：NeoForge 1.21.1 工作区中的独立实验，不是已接入正式渲染器的功能。没有修改发行 JAR、同步 Forge、提交或推送 GitHub。

## 结论

优先推进成品网格缓存。三个合成样例中，读取文件并批量恢复几何/接缝数组，相比从已经解码的缓存输入重建网格，耗时下降 77.9%–85.2%，线程临时 Java 分配下降 85.0%–86.6%。这是缓存命中后的网格阶段收益，不能换算成进入世界总耗时或 FPS。

共享缓冲区和跨地块 MDI 也值得继续，但先作为候选路径。128 地块完整栅格化样例的 CPU 提交减少约 0.008–0.175 ms；多区间提交收益更明显。部分顶点测试的 GPU 耗时反而增加约 1–3 微秒（约 4%–7%），不能宣布所有显卡、所有场景都更快。没有改变四边形数量，也没有采用每四边形一个 instance 的旧实验。

这两项不加速首次访问时的密度、地表规则和植被计算。GPU 遮挡及持久映射上传环尚未在本轮实现或计入收益。

## 测试方法与边界

- Ryzen 7 7700、RTX 4070 Ti SUPER、NVIDIA 572.70 / OpenGL 4.6、JDK 21。
- 每类实验运行三个独立测试 JVM；每场景 31 次计时取中位数，再对三个 JVM 的中位数取中位数。
- 缓存实验每场景预热 8 轮，四种模式交错执行；GPU 实验预热 30 轮，基线/候选路径交替执行。GPU 实验串行运行。
- 缓存样例为水体/悬崖、小地块、带树木的精细地块；调用实际 PredictionMeshBuilder、compactForRendering 和 prepareGpuPayload。
- GPU 实验使用完整生产顶点/片元着色器，修改地块参数、载荷寻址及遮罩纹理层的来源；普通路径与 Iris 接口路径分别测试。Iris 使用确定性的测试输出函数，不等于运行实际光影包。
- 所有缓存读取都经过 Files.readAllBytes，但重复读取受操作系统文件缓存影响；没有清空系统页缓存，不能当作物理磁盘冷启动测速。
- 基线从已解码的采样、植被输入开始；输入缓存 IO/解码、整世界调度、资源 ID 重映射、缓存失效检查、正式对象重建及 GPU 上传都不在缓存对照中。
- GPU 计时区间不包括候选集合整理、命令重建、排序及遮罩生成；这些仍需生产接入后评估。局部更新输入提前准备，两条路径上传相同字节数。

## 成品网格缓存结果

时间单位 ms；分配为当前测试线程的每次临时 Java 分配（十进制 MB），不是游戏常驻内存。

| 样例 | 四边形 | 从缓存输入建网格 | 文件读取 + 批量恢复 | 耗时下降 | 建网格分配 → 恢复分配 | 压缩记录大小 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 小型水体/悬崖 | 1,154 | 1.9388 | 0.2867 | 85.2% | 1.805 → 0.271 MB | 15,666 B |
| 精细水体/悬崖 | 17,271 | 7.8281 | 1.7314 | 77.9% | 27.308 → 3.725 MB | 181,123 B |
| 精细地形/植被 | 19,183 | 8.2785 | 1.7239 | 79.2% | 29.654 → 3.983 MB | 200,800 B |

同一记录用逐字段 DataInputStream 恢复，分别为 0.5301 / 5.3186 / 5.4938 ms；批量解码用 ByteBuffer 数组读取，代价是额外解压缓冲，因此比逐字段恢复分配更多，但仍明显少于重新建网格。它说明解码方式同样重要，不能只更换文件后缀或压缩格式。

使用 zlib level 1，三个记录未压缩大小分别为 78,861 / 1,174,561 / 1,253,857 B。编码和压缩 CPU 耗时分别为 0.6524 / 5.3838 / 5.7681 ms，**不含文件写入**。这些样例复用一次所省的建网格 CPU 时间已大于一次编码成本，但不代表包含磁盘 IO 后必然一次回本。首次访问不会因为写入缓存而变快，应在后台、受预算限制地保存。

一致性覆盖：完整 packed words、地形/水体绘制区间、精度过渡浮点数组和高度边界、接缝顶面/颜色/存在标志/平面/偏移/墙数组。逐字段和批量解码均验证损坏、截断记录会失败。没有删几何或改变采样精度。

当前实验把运行时材料 ID 原样保存，仅验证同一资源环境中的恢复；正式实现需要世界/维度/生成器、资源包/图集、格式/算法、颜色和植被设置、真实地形变化的失效身份。不能跨资源重载直接复用旧 sprite ID。当前 Voxy 驻留范围和真实区块遮罩必须重新计算，不能缓存旧的动态裁切结果。

新增磁盘负担是上述成品记录；不能与现有输入缓存大小混为一谈。输出几何数组仍需驻留，实验没有证明常驻内存减少 85%。

## 跨地块绘制结果

128 个独立地块，保留原 indexed quad。原路径逐地块绑定载荷/遮罩、设置 uniform，再使用生产 submitRanges；候选路径共享载荷缓冲和遮罩数组纹理，以 gl_BaseInstance 查询每地块参数，再执行一次 MDI。保留地块及区间顺序。

下面为每地块 32 个四边形、256×256 实际栅格化样例。两个可见区间场景选择了两个不连续面组，合计绘制一半四边形；只比较每行的改前/改后，不跨行比较工作量。

| 路径/状态 | CPU 提交原路径 → MDI（ms） | GPU 原路径 → MDI（ms） |
| --- | ---: | ---: |
| 普通、单区间、静态 | 0.0098 → 0.0014 | 0.016384 → 0.013312 |
| 普通、双区间、静态 | 0.1754 → 0.0002 | 0.015360 → 0.012288 |
| 普通、单区间、更新 1/16 地块 | 0.0158 → 0.0085 | 0.021504 → 0.019456 |
| 普通、双区间、更新 1/16 地块 | 0.1966 → 0.0046 | 0.020480 → 0.017408 |
| Iris 接口、单区间、静态 | 0.0100 → 0.0011 | 0.014336 → 0.011264 |
| Iris 接口、双区间、静态 | 0.1711 → 0.0002 | 0.013312 → 0.011264 |

CPU 的极小数值只代表异步提交返回时间，不能称为 GPU 完成时间。CSV 另存包含 glFinish 的完成时间，但强制同步改变流水线，也不能用它推算游戏 FPS。

另外测试每地块 1,024 / 4,096 个四边形，关闭栅格化以隔离顶点与驱动开销，避免重复几何造成不真实的片元过绘制。这些数据不能冒充完整渲染帧：

- 普通路径，4,096 四边形、单区间、静态：GPU 0.077824 → 0.074752 ms，约减少 3.9%。
- 同场景，双区间：GPU 0.050176 → 0.041984 ms，约减少 16.3%。
- 1,024 四边形、双区间、静态：普通 GPU 0.016384 → 0.017408 ms，Iris 接口 0.014336 → 0.015360 ms，分别慢约 6.3% / 7.1%。局部更新也存在微小 GPU 回退。
- 大地块更新的 CPU 耗时仍主要由上传决定，单区间时 MDI 没有带来数量级收益。共享提交不能代替后续上传优化。

每次 JVM 做 24 组初始颜色/深度对照，另做 24 组局部地块内容更新后的对照，覆盖普通/Iris、32/1024/4096 四边形、单/双区间、不透明/混合；要求画面非空、局部更新确实改变画面。全部逐像素颜色和深度一致。混合测试保持固定顺序，并不覆盖任意重叠透明地块排序。

场景包含每地块独立遮罩、材质平均色选项和高度 morph。尚未验证真实 Voxy 复杂交接深度、正式接缝提交、实际光影包、所有透明组合及 AMD 驱动。

逻辑载荷大小相同；实验不是显存压缩。128 地块新增参数表 8 KiB，间接命令单/双区间约 2.5/5 KiB。正式分页容量、碎片、遮罩纹理分配和上传环另有成本，当前没有测实际驱动显存分配。实验同时保留新旧两套缓冲用于对照，不能将进程显存总量当成候选路径占用。

## 后续接入顺序

1. 成品网格缓存：沿用区域索引，增加成品记录及完整失效身份，命中时直接恢复；仍动态应用真实区块/Voxy 交接。先测试相同世界退出重进的精细 LOD 就绪时间和峰值分配。
2. 共享 arena/MDI：保留原路径作为能力/兼容回退，增量维护地块参数及命令；用真实场景比较 CPU 提交、GPU 与总帧时间，再决定默认启用条件。
3. 只有确认真实场景瓶颈后再加入 GPU 遮挡或持久映射上传环；本轮没有测量这两项。
