# 命令预生成 LOD 的增量交付修复（2026-10-06）

用户观察到命令计数已经增加，但画面往往到预生成结束后才出现新的 LOD。本仓库对应的命令是 `/vss chunky`。本轮没有复现用户所述的完整实机操作，因此不把下述代码缺陷认定为该次现象的唯一原因。

## 已确认的链路缺口

`ChunkyGenerationService` 原本已逐列调用 `PersistentColumnWriter.writeConfirmed`，成功计数在列确认可持久读取后增加（也包含复用的有效磁盘列）。它没有等待整个任务结束才落盘的规则，计数也不代表客户端已收到或渲染。

但原交付路径存在两个缺口：

- 新写入的列只进入 `PlayerRequestState` 的预加载队列。严格 LOD 客户端不会通过 `ExistingColumnPreloader` 消费该队列，预加载读回本身也不构成完整的网络交付。
- 磁盘中已有有效列的复用路径直接完成工作项，不通知客户端。客户端如果此前收到 `NotGenerated`，特别是关闭自动生成时，可能一直保留“不可用”状态，无法及时发现新数据。

## 修改

- 新增 `ChunkyColumnAvailability`，合并已确认列的位置及持久化版本，单包最多 1024 列；每个服务器 tick 刷出未满批次，整批任务完成前即能通知。
- 新写入确认成功和磁盘复用成功都进入同一通知路径。写失败、失效数据和未完成写入不会发出可用通知。
- 只通知同维度、同步距离内、已注册且尚未确认该版本的客户端。使用现有 `DirtyColumnsS2CPayload`，携带实际存储版本，不生成新的脏版本，也不通过 `markDirtyColumn` 清掉刚写好的服务器缓存。
- 客户端沿用现有版本刷新流程，解除此前的不可用状态/退避，再按正常请求队列拉取持久数据。重复通知不会取消同版本的在途刷新，旧的无数据响应不能取消新请求。
- 通知在任务完成判断前刷出，最后不足一批的数据也会交付；取消时清除待发通知。

生成并发、CPU 配额和加载限额未调整。完整列仍走原来的网络请求、解码和 Voxy 导入流程，通知本身不等于已显示。距离之外的数据仍仅保存在服务器，进入同步范围后才请求。区域扫描仍从区域一角按行开始，并未改为以玩家为中心；大区域预生成早期可能尚未处理到当前视野。服务器满载也仍可能造成 tick、网络及导入延迟。

## 验证和成品

两个版本分别执行 7 组、50 项定向回归，均为 50 通过、0 失败、0 跳过，且 assemble 成功。覆盖首列在区域未完成时通知、复用与新列版本、超过三包的批量边界、客户端版本/距离过滤、取消清理、无数据后的重新请求、重复通知、过期响应，以及现有持久化确认与索引逻辑。这里只运行所列定向测试，不宣称全仓库测试通过。
