# 高空交接黑带：真实深度约定与水面回退（2026-10-05）

本轮继续检查高空俯视时出现、地面视角不明显的黑带。用户最终澄清：**开启预测后 FPS 约为关闭时的一半**。本轮没有把先前误解的开关方向当作结论。

## 当前客户端证据

PID 31584，Java 25，NormalRenderPipeline + MDIC，3840×2066 渲染目标；实例中的 VSS JAR 与上轮交付一致，SHA-256 为 `c6a9e7891f0a6c35b9ff60c0230364b6a487705739d0ce5d807b3f5710b1baa2`。Voxy 为实例内 `voxy-0.2.15-beta.jar`。安装包的字节码和 GLSL 均直接读取，不把上游其他 Minecraft 版本当作本机实现。

固定视角约为 `(-3409.518, 169.909, -1050.584)`。`capture-6` 记录主画面各阶段、原始 Voxy 深度、矩阵及索引纹理。预测不透明阶段之前为海水，之后出现黑色海底/植被；这把主要异常定位到了预测交接。

### 1. 声明的投影范围不等于纹理实际的深度编码

安装版 `RenderProperties.getRenderProperties()` 硬编码 `isZero2One=true`；其顶点着色器直接输出 MVP 结果，但当前 GL clip depth mode 为 `GL_NEGATIVE_ONE_TO_ONE`。同一个水面像素，按声明解释 Voxy 深度得到 Y≈−41.76；按实际 raster 映射解码得到 Y≈62.89，多个像素稳定落在同一海面高度。预测海底约为 Y=30～50，因错误的遮挡距离被绘制在已经合成的海水上。

Voxy 最终合成又用源端宏转换目标端的 vanilla projection；两端约定不同，主深度也不再表示真实海面。这是当前交接开始借用深度、强制合成写深度之后暴露的兼容问题。

修复：

- Normal 管线完成前读取真实 `GL_CLIP_DEPTH_MODE`，供该帧的源深度反投影使用。
- 只补丁已知 Normal final-blit shader：源深度按真实 raster 约定解码，目标按 Minecraft 1.21.1 的 `[-1,1]` 投影转换成窗口深度。远端仍保留非清空的最后深度格，零 alpha 和空白深度仍丢弃。
- 借用的 `PredictionVoxyDepth.Frame` 记录同一实际约定。原有无 GL 的属性解析入口仍保留用于兼容路径和测试。
- 不修改 Voxy 的全局投影、traversal/HiZ 或 Iris shader pack 的约定。

`capture-7-correct-depth` 临时替换一帧的借用深度解释，大块黑带消失；下一帧自动清空/恢复。`capture-8-control` 恢复旧行为后黑带重现。`capture-9-correct-main` 进一步通过生产深度播种/导出路径临时修正主深度，验证了同一现象。这些是受控诊断帧，不是重启加载新 JAR 后的游戏验证。

### 2. 水面与海底沿同一视线落在不同索引列

深度修正后剩下短小的黑线。`capture-10-edge` 的 128×128 边界裁剪中，识别到 630 个残留暗绿像素：原始主深度和 Voxy 深度在这里均为空。相机射线与 Y≈62.89 的水面相交处，索引却全部为 `255`；射线继续落到预测海底时，索引为未知 `0`。

因此发生“索引裁掉预测水，Voxy 边缘没有实际水面像素，远处预测海底仍存在”。把边界统一扩大若干区块只是另一种距离假设，不能让二维存在性索引变成逐像素证明。

修复仅让**仍驻留的混合瓦片中的水面**绕过索引硬裁剪，使用已有的真实深度、同面容差与遮挡顺序交接。固体、熔岩、冰仍保留稳定区域所有权；完整内部瓦片的 CPU 退休策略保留。没有重新生成全部已覆盖区域，也没有用清空索引来永久关闭区域交接。

`capture-11-fluid-fallback` 只在一帧水面阶段临时把 GPU 索引内部值降为边缘值，随后立即恢复。暗线消失；这是对水面分支的单帧证据。修复没有声称消除 Voxy 自身边界水体断面的所有颜色差异。

## 客户端性能采样

30 秒 JFR 与 6 次状态快照保存在证据目录；快照覆盖 20.032 秒、相机坐标保持一致。

| 指标 | 结果 |
| --- | --- |
| 6 次滚动 FPS | 72.0、70.0、71.1、70.8、70.5、71.7 |
| 预测渲染帧 | 1,404 |
| 平均提交四边形 | 7,050,633 / 帧 |
| 平均绘制调用计数 | 509.96 / 帧 |
| 瓦片构建 / 网格上传 | +246 / +190 |
| 准备计划 / 复用计划 | +133 / +1,270 |
| GC 暂停 | 合计 76.59 ms，最长 8.48 ms |

提交量包括最终会被深度/所有权拒绝的几何，并非屏幕可见四边形。JFR 中仍有覆盖解析、边界网格、提交和 Xaero 工作；包含式堆栈统计不能相加或当作耗时百分比。

另做四阶段、各 8 秒的渲染对照：原始 → 修正借用深度 → 暂时跳过预测绘制 → 原始。每阶段丢弃首秒的帧间隔；原本的后台生成和用户配置保持，临时状态在帧尾及结束时恢复。该窗口受约 30 FPS 限制，无法用于整体 FPS 的前后提升比较。

计时数组的窗口差量（不是会话累计平均）显示：

| 预测 GPU 阶段 | 原始 | 修正借用深度 |
| --- | ---: | ---: |
| 不透明绘制 | 7.577 ms | 7.258 ms |
| 水面绘制 | 0.565 ms | 0.227 ms |
| 深度播种 | 0.083 ms | 0.083 ms |
| 抗锯齿 | 0.333 ms | 0.169 ms |

采样数有限，世界时间/后台进度仍在变化，抗锯齿差异不能单独归因于深度修改。能够支持的结论是：预测绘制本身有显著 GPU 成本，尤其是几百万四边形的不透明阶段；修复深度减少部分无效像素，但没有消除几何提交成本，也不足以承诺 FPS 翻倍。没有修改用户的视距、线程档位或画质。
