# 预测 LOD 后台上传准备：2026-10-06

本次按“优先减少渲染线程工作，不通过降低加载并发稳定帧率”的要求，加入工作线程准备、本机内存暂存和缓冲复用。OpenGL 调用仍在现有渲染线程执行；工作线程无需 OpenGL 上下文。

## 实现

- 新增 `PredictionUploadStaging`。后台将不透明网格、定点地形过渡数据及水面网格一次写入可直接交给 OpenGL 的本机缓冲区。渲染线程通过所有权转移取得缓冲区，两次上传结束后归还。大数组复制及过渡格式转换不再发生在暂存命中的渲染帧内。
- 接入正常生成、磁盘完整网格恢复、压缩 CPU 网格恢复。前两条在发布地形前完成可选暂存；压缩恢复先发布 CPU 数据，再尝试本机暂存，避免要求渲染线程等待附加准备。
- 本机暂存可独立于 CPU 压缩网格暂存存活。有可直接上传的本机数据时，不因原始数组被淘汰而重新排队解压。
- 暂存是可选加速。达到容量限制、大块数据超过容量或额外本机分配失败时，保留原有可用上传路径，不新增等待帧或推迟已就绪网格。渲染线程生成的接缝也保留原来的即时路径，保持所有权交接顺序。
- 继续使用现有 GPU 页、独立水面存储和缓冲池，两个 pass 均成功上传后再替换旧 GPU 资源。
- 使用 epoch 和独立填充票据处理重置、任务取消及同一对象重新准备。正在复制、正在上传的缓冲区不能被回收或改写；旧世界的工作不能回填新世界的暂存。

暂存池最多保留 32 MiB 本机内存、128 个缓冲区。这个上限包括后台正在填充、排队待用、渲染线程持有及空闲待复用的内存；按需分配，不预占 32 MiB。它属于系统内存，不增加 GPU 网格字节数。世界/资源重置释放未使用的内存，已取得所有权的缓冲区在使用结束后释放。

本次未调整 CPU/FPS 限流、生成和缓存恢复并发、细节/距离、16 块 / 4 MiB / 2 ms 上传软预算，也未改变磁盘缓存格式。目标是减少分配和主线程复制造成的帧时间尖峰。代码层面没有以延缓加载来换帧率，但后台复制仍有成本；满载时的实际加载吞吐和游戏帧率必须用同一路线实测，不能据此保证完全没有变化或预测提升幅度。
