## 优先问题 1：提交前归属过滤的全局失效

跑图 JFR 共 2582 个 Render thread 执行/原生样本：

- PreparedPass.prepare：906（35.1%，包含子调用）。
- PredictionSubmissionCoverage.filter：760。
- PredictionOwnershipRuns.filter：738（28.6%）；其中直接落在该方法的样本 731。
- Scene.prepare：440；PredictionVisiblePlan.select：209。
- PredictionIndirectBatch.add：181。

这些是采样计数，不是精确耗时百分比，各调用链不能相加。静止 JFR 574 个渲染线程样本中，没有 ownership filter 样本。

PredictionSubmissionCoverage.update 在相机越过任一轴的 8 方块 cell、Snapshot 对象改变或半径改变时 cache.clear。PredictionExactCoverageMask 的快照刷新受 250 ms 最小间隔控制；数据 revision 更新时会产生新 Snapshot。两种因素都可能使大量 mesh 在随后的准备中同步重新执行 ownershipRuns.filter。没有分别记录两类失效次数，无法判断各自占比。

过滤本身在渲染线程逐 run 检查球形视距与完整 XZ 覆盖；即使最后返回原范围，也已经遍历并分配了临时数组。它正确地省掉重复几何提交，但其缓存策略把移动时的成本集中在主线程，是本次最明显热点。

建议分离静态覆盖证明与动态距离证明，增加整 mesh 无交集/完整覆盖的保守快速路径，按受影响区域更新缓存。覆盖撤销必须立即恢复几何；不能以简单延长旧缓存寿命作为修复。后台结果必须带版本并在发布时验证，过期结果保留绘制。

## 优先问题 2：移动排序导致下游重建

PredictionVisiblePlan 在水平位置变化时更新距离，并从 TreeSet 删除、重新插入可见条目，随后发布新 List。当前 pass/page 缓存依赖可见列表身份，因此这会继续推动下游准备。20.2 秒内 1034 帧全都发布列表，累计 949901 次距离排序插入，约 919 次/帧。

建议将不透明批次稳定顺序与精确距离排序分开，用保守距离桶控制前后顺序，避免微小平移让全部批次变化。水的透明顺序必须独立保留；不能把整套排序直接删除。网格增加、删除与覆盖变化继续增量处理。

## 优先问题 3：大量临时对象和 GC

跑图约 60 秒内 Render thread 的 ThreadAllocationStatistics 差分为 6230.9 MiB（约 6.1 GiB，约 104 MiB/s）；静止约 25 秒为 1328.8 MiB（约 53 MiB/s）。这是累计分配，不是存活内存或泄漏。

跑图 ObjectAllocationSample 加权估算中：BatchSlot.upload 的 byte[] 约 1714.4 MiB，OwnershipRuns.filter 约 415.8 MiB。前者在批次内容变化时每次 new byte[]，保留一份副本供下一帧比较；相机数据稳定化没有解决成员和顺序改变后的分配。

建议保留可扩容的缓存容量与有效长度，更新内容时复用数组，配合稳定批次和版本检查，减少复制和分配。分配采样结果是估计值；线程分配计数差分更适合总体比较。

跑图 JFR 记录 91 个 GCPhasePause，合计 597.7 ms，最长 17.475 ms；静止 4 个，合计 16.226 ms，最长 6.296 ms。暂停会增加部分帧延迟，但平均约 1% 的暂停占比不足以独自解释持续掉帧。

## 后台与其他限制

跑图时 vss-prediction-overworld 多个同名工作线程活跃，线程分配计数合计约 10633.9 MiB；JFR 样本涉及植被生成、Java placement/biome 查询、Rust surface/display 采样。原版集成服务器与 C2ME 也在生成新地形。静止对照没有同样生成负载。这些是额外 CPU 和内存压力，不能一概归为 OpenGL。

进程 CPU 均值跑图约 46.2%，静止约 3.83%，均为整机归一化，不代表渲染线程占用或单核饱和度。

上传采样的 UPLOAD CPU 均值约 0.129 ms/采样事件，当前没有证据把大网格上传列为第一主因。不过首块上传可超出软预算，稀疏统计不能排除个别未命中的长上传。SEAMS 仅 6 个样本，均值 1.605 ms，也不足以认定全部尖峰来自接缝。

结论：优先修复归属缓存全局失效、移动重排传播和 BatchSlot 临时分配；随后复测后台生成竞争与个别上传/交接尖峰。现有相机/morph 参数调整有效，但未覆盖上述路径。本次未修改两端源码，未宣称帧率修复。
