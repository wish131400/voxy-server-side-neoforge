# 增量渲染后的实机转动视角采样

2026-09-21，NeoForge 1.21.1，游戏 PID 40320，Java 25，RTX 4070 Ti SUPER。
游戏加载源指向 `mods/vss-0.3.1-neoforge-1.21.1.jar`，文件 SHA-256 为
`1f6dbaaaa31032744923f721e1b9551cb9ade726ca18db6546d7334430176ea9`，与上一轮产物一致。

## 方法

90 秒 JFR、每秒在渲染线程读取诊断计数、相机位置/旋转、前台/暂停状态、线程 CPU 与分配累计量。VSS GPU timestamp 保持每 30 帧采样，不同步等待查询。临时诊断属性在采样完成后恢复。

记录中存在后台暂停与短暂移动，因此只比较位置固定且游戏在前台、未暂停的区间：

- 静止：UTC 17:23:49.911630400–17:23:54.939791100，5.028 秒，678 个预测帧。
- 转动：UTC 17:23:56.984890900–17:24:14.210122500，17.225 秒，885 个预测帧。
- 这两个区间相机位置相同；朝向不同，因此可见内容不完全相同。不是关闭/开启 VSS 的控制实验。
- 垂直同步关闭，帧率上限 260，原版视距 5 chunks，原始鼠标输入开启，窗口模式。

VSS CPU/GPU 计时不是整个游戏帧时间，不可直接相加成完整帧预算；GPU timestamp 测的是命令间隔，驱动调度可能影响结果。

GPU 利用率在静止区间五次读数为 67/68/69/71/67%。转动区间只有初段三次完整读数 42/33/24%；CSV 后续最后一行不完整，因此不能把这些数值当成完整 17 秒的平均 GPU 利用率。

整段 90 秒 GC pause 事件共 14 个（含极短阶段事件），合计 50.587 ms，最大 6.076 ms；没有超过 16.67 ms 的 pause 事件。不支持将持续转动掉帧解释为长时间 GC 停顿。

## 剩余热点与判断边界

转动区间渲染线程有 333 个执行/原生方法采样，其中：

- 86 个叶栈在 `GLFW.glfwPollEvents → JNI.invokeV`。
- 39 个叶栈在 VSS 可见计划调用的 `Frustum.cubeInFrustum`。
- 38 个叶栈在 `GLFW.glfwSwapBuffers → JNI.invokePV`。
- 154 个采样调用链包含 VSS；这是包含式计数，不能与其他层的包含式统计相加，也不是精确时间比例。
- 静止区间只有 81 个样本，其中 36 个为 swap，未捕获到 pollEvents 样本；静止窗口较短，应避免过度精确推断比例。

用户确认鼠标处于 2000/4000/8000 Hz 高回报率档位。输入事件热点与这一信息吻合，但高回报率是否为主要原因仍需 1000 Hz 对照。不能仅凭原生调用栈分清 GLFW、驱动及原生回调中的全部开销。

上一轮接缝/场景复用已经在这个转动窗口生效；剩余 VSS 工作包括约 3,800 次可见性访问/帧、约 1,840 次地块绘制提交/帧和逐地块参数设置。后续可评估让距离顺序独立于可见集合，减少旋转造成的树节点插入/删除，并用保守的分组裁剪减少逐地块检查。跨地块正式合批仍需真实材质/透明顺序下的测量，不能引用简化原型证明一定有收益。

目前证据支持主线程输入/渲染提交与原生等待共同限制帧率，GPU 没有持续被填满；不能直接归因于预测生成线程不足。首轮 1000 Hz 对照请求已发出；其后台录制仍处于暂停画面，尚无用户确认完成的有效对照结果。

原始证据位于本地 `build/turn-followup/`：`game.jfr`、`snapshot-*.txt`、`windows.json`、`turn-hotspots.txt`、`still-hotspots.txt`、`report.txt` 和 `gpu.csv`。本轮调查没有修改生产渲染代码或重新打包 jar。
